### 3.3 AI 链工程层：两道数学上绕不过去的墙

**墙 1：截断–超时互斥（P0）**

- 实测生成速率 **p50 = 130 tok/s**（p10 97 / p90 168，n=67 成功调用）。
- 开场 cap 4800（`constants.js:83-94`）÷ 130 tok/s ≈ **36.9s** > 超时 32s（`constants.js:66-77`）。
- 于是同一份输出只会二选一：**写满 → `finish=max_tokens` → `LLM_FINISH_ERROR`**；或**32s 到点 → `LLM_TIMEOUT`**。
- 证据：29 次截断、13 次超时；成功调用里也有 88%/93%/95% 占用的（04:16 red 4235/4800、15:37 red 4462/4800、15:06 blue 4580/4800）。
- **重试把 cap 抬到 1.5×（4800→7200），但 timeout 不抬**（`chain.js:327-329`）→ 第二次更不可能写完。
- 代价：4/4 的 `DEBATE_INCOMPLETE` 全部由开场失败导致。

**墙 2：链预算零余量（P0）**

### 3.4 闸门层：0.5 是唯一活跃的闸门，但不是主因

- `scorecard.js:71` 硬编码 `confidence < 0.5`；`confidence = min(opening, response)`。`thresholds.min_confidence`（:134）只是展示值，不参与判断，且**不能用 envelope 配置**。
- 阈值有三处不一致：scorecard 0.5 / decision 语义 0.55（`semantics.js:156`）/ 服务端 `strong_min_confidence 0.65`（`risk/config.py:61`）。
- **提示词从未定义 confidence**：全文只有 3 处提到；红蓝开场与决策指令里**根本没提**；`schemas.js:11` 只有 `{0..1}` 无 description；`chain.js:278-286` 的 `constraints` **没有 `min_confidence`/`min_decision_confidence`**（而 `docs/02:1269/1290/1292` 要求必须有）。
- 分布：red 开场 mean 0.490（4/7 < 0.5）、blue 0.546（2/7 < 0.5）；`min(open,resp)` 后 **5/7 轮至少一边 < 0.5**。
- 同一轮 blue 自报 `rubric_score = 0.675（B 级）`却 `confidence = 0.45` —— 两套自评分互相矛盾，说明 confidence 字段没被“操作化”。
- **敏感性（关键）**：阈值 0.5→0.47 新增通过 **0 轮**；→0.45 新增 **+1 轮**；放宽 `min_rr`/`sl_min`/`sl_max`/`max_risk`/`max_lev`/`evidence` 全部 **+0 轮**。
  → 结论：**闸门只命中 6/14 侧，但放宽它救不了链路——因为绝大多数轮次根本走不到闸门。**

**其余 gate 问题**：`LOW_EVIDENCE`、`RR_TOO_LOW`、`STOP_*`、`RISK_OVER_CAP`、`LEVERAGE_OVER_CAP` 在 14 个侧评分里**一次都没命中**（实测 rr≥1.2314、stop≥0.295%、risk≤1.0、lev≤5、evidence≥0.623）。`rubric_score` 有 6/14 侧取默认值 0.5（分析只给单向候选时）。

## 4. 处置方案

### P0-0 重启 Host（前置动作，5 分钟）

> 不重启，下面所有源码改动都不会生效，P1.10 也永远不生效。
> 重启后先做一次“只读回归”：跑一轮，断言 `blocked_reason != OTHER`、`limits.truncated` 是否变化。

### P0-1 拆掉“截断–超时墙”（收益最高）

两种选一种，**不可只改一边**：

- **方案 A（推荐）**：`constants.js:83-94` 开场 4800→**4000**、回应 5850→**4600**；同时删掉 user payload 的 `output_schema_json`（改 20 行字段/枚举/长度清单），输入从 3.4k→约 2.2k token，TTFT 与总时延同步下降。
- **方案 B**：开场/回应 32s→**45s**，但必须同时把链截止提到 ≥240s（见 P0-2）。
- 另：截断重试时**同时放大 timeout**（`chain.js:327-329`），否则升级后的 cap 永远吃不到。
- 加回归 fixture：`role_max_tokens ≤ timeout × 130tok/s × 0.9`。

### P0-2 重定链预算，并改成显式 fail-fast

- `constants.js:146` `CHAIN_DEADLINE_MS 180_000 → 240_000`（178s + 1 次 32s 重试 ≈ 210s 才装得下）。
- `chain.js:326` 删掉 `min(...)` 收缩，改 `if (remaining < roleTimeout + 2000) throw CHAIN_DEADLINE`（对齐 `docs/02:3271`）。
- 给重试单独预算（如 45s），超预算直接降级。
- **注意联动**：240s 会越过 `order_gate_ttl_s=180` 与服务端证据 180s 门限 → 必须同时处理 P0-6 或让 Host 在开链前重新取快照。

### P0-3 补调度器（**灰度，不要一步全量**）

- `runOneRound({trigger:'auto', slotId=floor(now/10min)})`；用 `ctx.effect` 注册 timer；single-flight；服务端唯一索引天然去重；重叠记 `OVERLAP_SKIPPED`；**catch-up 最多补 1 轮**；kill switch；无轮 >15min 告警。
- **灰度前必须先把 AI 失败率从 50% 降下来**——否则 auto 只会把 token 消耗和失败率一起放大。
- 诊断/测试统一走 `WORKBENCH_LLM_MODE=session_fixture`（已支持，无条件短路下单），**不要再动 `control_state`**。

### P0-3b 开链前硬门（直接省掉 37% 无效耗时）

在调 LLM 之前先判：`control_state != normal` → 直接 `CONTROL_LOCKED`；`account/equity` 全空 → 直接 `ACCOUNT_UNAVAILABLE`。当前 `localVerdict` 在开链前就算出来了（`integration.js:1466-1470`），却要等跑完 6–8 次调用才在链尾判死——这 5 轮白烧了 **788.3s**。
另加 stale-cycle janitor（RUNNING >5min 自动标 `ABORTED_BY_RESTART`），防止 04:40 那个 RUNNING 299s 的孤儿 cycle 再堵门。

### P0-4 修证据供数

- prompt 预算 6000→≥12000，或按角色投影；保证 analysis 看到 15m K 线 + 1d + 1h/4h 指标。
- 实现 `EVIDENCE_SLICE_TOKENS`（decision/risk/execution 三档目前是死代码）。
- `clock offset>1000ms` 做校正或明确降级；`oi_usd` 按 Demo 口径缩放或从 gate 排除。

### P0-5 解耦“问风控”与“定数量”

- 若 `decision.action=TRADE` 且有 SL/TP，即使 `executable=false`，Host 也合成上界 qty（`equity×maxRiskPct/100 ÷ |mark−SL|`）照常调 P1，让服务端裁决（只降不升，更安全）。
- 只有 `blocked_reason ∈ {SIZE_BELOW_MIN, SPREAD_TOO_WIDE}` 才尊重阻塞。
- 同时修 `prompts.js:49`（用 `equity.exchange` 而非布尔 `available`）、补 `total_position_margin`/`max_withdraw_amount`、`semantics.js` 加归一化断言（account/equity 全空 → 强制 `ACCOUNT_UNAVAILABLE`）。

### P0-6 排掉服务端三个地雷

1. **R11**：`filters.py:178-181` 改为按**目标杠杆档**取 mmr（或按 notional 匹配档位），不要 `max()`；`rules.py:340-346` 恢复文档约定的 1% 兜底并记 `risk_mmr_assumed` 审计事件。**先在维护窗口打印一次 `broker.mmr_for('BTCUSDT')` 确认现值**。
2. **R14**：把证据门限与链预算解耦（链 240s 则证据 300s），或 P1 时重新取 15s 内的快照。
3. **RR 口径**：`scorecard.js:39` 改用 evidence 的 mark 计算 rr/stop，与 `risk/models.py:126-127` 对齐。

### P0-7 置信度：先补契约，再谈阈值

- `chain.js:278-286` 的 `constraints` 补 `min_confidence`、`min_decision_confidence`、`tie_epsilon`。
- `scorecard.js:71/134` 把 0.5 收进 `DEFAULT_CAPS` + `capsFromEnvelope`（可治理、可审计），统一全链路口径。
