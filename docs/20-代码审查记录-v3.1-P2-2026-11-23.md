## 3. 发现的问题

### H1（高，已修复）孤儿 trigger cycle 会让触发引擎永久停摆

- **路径 A**：`dispatchRuleTrigger` 在 `createCycle` 之后抛非预期异常（不是它内部消化的 P1/P2 错误）时，engine 的 catch 只回写 rejected + 释放租约，**没有终结已创建的 cycle**。
- **路径 B**：Host 进程在派发中途崩溃，cycle 停在 RUNNING。下次派发 `createCycle(purpose='trigger')` 得到同 purpose 的 `E_CYCLE_RUNNING`，而 engine 按设计「绝不终结别人的 cycle」→ 每 tick 只跳过 → **后续所有用户策略派发永久失效**（服务端没有僵尸 RUNNING cycle 的自动收敛，research 路径也不会碰到 trigger purpose）。
- **修复**（`host/trigger-engine.js`）：
  1. `dispatch` 记录自己创建的 cycle；异常路径先 `finalizeOwnCycle(..., 'TRIGGER_DISPATCH_FAILED')` 再回写 rejected。
  2. `handleDispatchBusy` 在 stage=CYCLE + `E_CYCLE_RUNNING` 且 `details.running_purpose === 'trigger'` 时终结该孤儿（`reason=HOST_ORPHAN_TRIGGER_CYCLE`）。安全性：cycle 创建前已经拿到租约，别的 Host 不可能正在派发，所以此时还能看到的同 purpose RUNNING cycle 只能是孤儿；research/manual 一律不碰。
  3. `status()` 增加 `orphanCycleCleanupCount`，README 记录该行为。
- **测试**：新增「孤儿 trigger cycle 被终结且下个 tick 恢复派发」「research/manual cycle 永不终结」「派发异常终结自己创建的 cycle」；更新既有的「异常仍释放租约」用例（现在顺序里含 finalizeCycle，并断言 reason）。

### L1（低）`rule_eval_state` 不回收旧版本行

规则键含 `<version>`，每次重新挂载都会新建一行；只增不删。规模是「策略数 × 版本数 × 标的数」，量级极小，暂不处理；如要清理可在 attribution 或运维脚本里按 last_eval_ms 过期删除。

### L2（低）`clamp_interval_ms(0)` 返回 5000 而不是默认 15000

Host 总是显式传 `markIntervalMs`，因此没有实际影响；只是 `body.scan_interval_ms=0` 的语义与「缺省 15s」不一致。留作已知边界。

### I1（信息）研判轮与触发轮争用执行租约

研判轮仍在链前拿租约（约 30–150s），期间触发的规则会 lease_busy 跳过并在下一 tick 重试（`retryMaxAgeMs` 内）。这是 P2 的已知取舍：把 acquireLease 后移到 P1 前会把冲突推到跑完整条链之后才失败。P3 研判不再持租约后自然消失。

### I2（信息）`plan.qty=1000000` 的归档副作用

服务端把它当 requested，于是每笔策略单都会记 R05/R06/R07 downsize、`verdict='reduced'`（界面显示「降仓」）。功能安全（approved_qty 取 min，没有任何规则按 requested 拒绝），`record.sizing` 与 README 已写明来源。

### L3（已核实不是问题）扫描不再做熔断巡检

`/api/rules/scan` 刻意不调 `check_and_trip_circuits`（每 15s 算归因太重）。核实：`execution/service.py` 的心跳（`_heartbeat_once`，monitor 每 30s）与下单后、对账后都会调用它，熔断状态仍会被判定，`strategies.enabled=0` 后扫描自然排除。

- 在「设置 → 插件 → ocr-review」卡片选 provider/model（key 由宿主按 `api_key_cmd` 动态读取，不落盘）；
- 或命令行：`ocr config set provider <p>` / `ocr config set providers.<p>.api_key "$KEY"` / `ocr config set providers.<p>.model <m>`，然后 `ocr llm test` 应为 200。
- 有 ChatGPT 订阅的话也可以 `ocr auth login --provider chatgpt`，然后用 `ocr config model` 选模型。

### 第二轮仍用 delegate 模式，覆盖到 `c3ad4bc`

范围与第一轮相同（30 个可审文件），额外重点看：`host/integration.js` 的删除段与新增派发路径、`execution/service.py` 的 451 守卫、`test/host-integration.test.mjs` 的断言变更、以及 `c3ad4bc` 的孤儿清理修复本身。

**结论：没有新的 blocker / high。** 几点记录：

- **触发路径不计算客户端 `preSubmitGate`**（旧 rule_direct 会算）。判断为可接受、不需修：触发轮的证据是秒级生成的，客户端时间闸门本来是为 100s 的 AI 链准备的；服务端 R14 的新鲜度校验与 P2 的 `_pre_submit_refresh` 仍然生效。若以后 `trigger_confirm` 变成慢调用（>30s），需要把时间闸门补回。
- **D-1 改写了「有持仓时手动跑一轮」的既有用例**：旧断言是「mounted + 有持仓 → 链照跑（≥1 次 LLM）」，新断言是「0 次 LLM + POSITION_OPEN + 不建 cycle + 不调 P1」。这是文档 16 §5.1 的预期行为变更，测试名也同步改了，不是掩盖回归。
- **旧 rule_direct 内联段（386 行删除）与 `dispatchRuleTrigger` 一一对应**：审批令牌、租约、`E_DEMO_CREDENTIALS_MISSING` 的 degraded 标记、cycle finalize 都在新函数里；没有静默丢掉的闸门。
- **租约/cycle 忙时回写 `rejected`** 会让服务端记一次「派发过」（冷却 1 个周期 + 需要重新武装），引擎再用 `pendingRetry` 在窗口内重试。语义上偏保守（抢不到租约也算派发过），但不会造成重复下单；记录为已知取舍。
- `rule_eval_state` 老版本行不回收（第一轮 L1）依旧存在，量级极小。
