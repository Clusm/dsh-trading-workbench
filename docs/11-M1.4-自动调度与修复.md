- **预算**：24 小时内自动轮次上限 96 轮（≈16 小时满负荷）。
- **可关**：`WORKBENCH_AUTO_SCHEDULE=off`，或运行时 `POST /trading-workbench/api/schedule?action=disable`。

## 5. 取舍与风险

1. **自动调度默认开启**。这是需求 §12 的字面要求，也是你这次的明确指令。若不希望无人值守，设 `WORKBENCH_AUTO_SCHEDULE=off` 即可，其余修复仍然有效。

4. **首次真实 P1 仍需人工确认一次**。R11 的实际档位值取决于 Demo 交易所返回的 `leverageBracket`，建议首轮后核对 `/api/risk/envelope` 与 `ai_calls` 里 `context.mmr`。

| risk role 调用 | 次数 |
|---|---:|

| max_tokens（1600） | 14 |

26 轮 `RISK_UNAVAILABLE` 里，**26/26 都是 decision 已经给出 `action=TRADE`**——交易被一个"读得太慢"的角色吃掉。根因：risk/decision 都是 `effort=max`，要在 130 tok/s 解码之外再付推理延迟；`1600 tok @14s`（需 ≥114 tok/s）本身就贴着物理极限。

**修复**：risk `1600@14s → 2400@40s`；decision `4500@30s → 4000@45s`；链截止 `250s → 340s`；服务端 R14 证据门禁 `300s → 400s`；客户端与 Host 的 run timeout `290s → 400s`。Host 墙钟 235s + 一次完整重试，仍余 105s。

### 8.2 `E_CYCLE_DUPLICATE_SLOT` 被记成"失败轮"

同一 10 分钟槽位内出现两次 tick（重复 timer / 重载），服务端按 `slot_id` 唯一索引正确拒绝，但 Host 把它写成 `outcome=failed` 的轮次，污染统计。

**修复**：
- `integration.run()` 把 `E_CYCLE_DUPLICATE_SLOT` 收口为 `status=skipped / reasonCode=OVERLAP_SKIPPED`，**不调用任何 LLM**，也不抛错；
- 调度器增加同槽位内存去重（`lastRunSlot`），`start()` 先清旧 timer，避免重载后双 timer。
- 回归：`host-integration` 新增"重复槽位是干净跳过"用例；`scheduler` 用例改为跨槽位推进。

### 8.5 卡死一轮会把整个自动化冻住（本次最危险的发现）

`host-rounds.json` 里出现一条 **`status=running` 停留 23 分钟**的记录（15:31:16 轮）。原因链：

- `integration.run()` 里 `this.runTimeoutMs`（默认 400s）**从未被使用**——没有整轮看门狗；
- 若 provider 的流一直不关闭，`chain` 的 for-await 永不返回，`run()` 永不 settle；
- `this.inFlight` 一直是那个 roundId → 调度器每次 tick 都 `ROUND_IN_FLIGHT` 跳过；
- `schedule.busy` 也一直是 true（调度器自己的 busy 靠 `await run()` 返回才复位）。

结果是**静默死亡**：UI 显示"运行中"，实际再也不会跑下一轮。

**修复（三层）**：

1. `integration.run()` 增加整轮**看门狗**：`runTimeoutMs` 到点 → `abandonRun()` 把该轮落库为 `failed / HOST_RUN_TIMEOUT`、清掉 `inFlight`；hung promise 若日后返回，只按正常路径再收口一次，不覆盖新轮。
2. `finally` 改成 `if (this.inFlight === roundId) this.inFlight = null`，避免旧轮清掉新轮的 in-flight。
3. 调度器再加一道 `Promise.race` 守卫（`runGuardMs`，默认 runTimeout+60s），保证 `busy` 必定复位；并在 tick 前调用 `recoverStaleInFlight()` 回收超龄 in-flight。

另加**启动修复**：`stateSync()` 首次调用时把历史里遗留的 `status=running` 记录（上一个 Host 进程留下的）统一改成 `failed / HOST_STALE_RUN`，避免 UI 永远显示"运行中"。

## 9. M1.4d：第一笔真实成交，以及它为什么立刻被平掉

### 9.1 发生了什么（16:10–16:13Z）

自动轮 `cyc-20261110T161044Z` 首次完整走通：

| 阶段 | 结果 |
|---|---|
| analysis / R1 / R2 / decision | 全部成功，decision=TRADE **blue SHORT** conf 0.57 |
| risk | 首调截断 → 重试成功，DOWNSIZE 0.6 |
| execution | 首调截断 → 重试成功，qty 0.042、lev 3、SL 73825 / TP 71500 |
| **P1** | **approved**（R11 已不再误杀 —— 服务重启生效） |
| **P2** | **SELL 0.042 成交 @ 73223.2** |
| 保护单 | **失败**：`STOP_MARKET` 被拒 `-4061 Order's position side does not match user's setting` |
| 收尾 | 触发 `protection_incomplete` → **紧急平仓** BUY 0.042 @ 73233.2 |

净结果：`positions=0`，realized PnL −0.42，手续费合计 2.46 —— **开了仓又立刻被自己平掉**。

### 9.2 根因：one-way 账户错误地发送 positionSide

对比同一轮发给交易所的原始报文：

```jsonc
// ENTRY（成功）
{"side":"SELL","type":"MARKET","quantity":"0.0420","reduceOnly":"false"}     // 无 positionSide

// PROTECTION（-4061）
{"side":"BUY","type":"STOP_MARKET","triggerPrice":"73825.0",
 "closePosition":"true","positionSide":"SHORT"}                              // 多了 positionSide
```

`order_outbox` 里两条保护请求都带 `positionSide`，而入场单没有 —— 说明该 Demo 账户是 **one-way（BOTH）模式**。Binance 在 one-way 模式下不接受 `positionSide`，返回 `-4061`。

`broker.open_market()` 本来就按 `mode == "HEDGE"` 决定是否发送 `positionSide`，但 `ProtectionManager.place()` 只要拿到 `position_side` 就无条件加上。这是**模式判断没有贯穿到保护单**的缺陷。

### 9.3 连带故障：两条 SUBMITTING 把整个服务变成 not ready

保护单被拒后，`place()` 没有把 outbox 行收口，两条记录永远停在 `SUBMITTING`。而：

- `outbox.can_open_new()` 要求 `submitting == 0`；
- `/api/ready` 因此返回 `service_ready=false`，`reasons=["ORDER_OUTBOX_SUBMITTING"]`；
- Host 的 `serviceSnapshot()` 直接抛 `E_SERVICE_NOT_READY`；
- **之后每一轮在开链前就失败** —— 这就是"最新未执行"的直接原因。

### 9.4 修复

| 文件 | 改动 |
|---|---|
| `execution/protection.py` | `place()/ensure()` 增加 `position_mode`；**只有 HEDGE 才发送 `positionSide`**；提交失败按 `definitely_rejected` 分别 `outbox.reject()` / `mark_unknown()`，不再留 SUBMITTING |
| `execution/broker.py` | 两处 `protection.ensure(...)` 传入 `position_mode`（`mode` / `snapshot.position_mode`）；`reconcile()` 新增 `_resolve_stale_submitting()` |
| `execution/outbox.py` | 新增 `stale_submitting(older_than_s=120)`：超龄 SUBMITTING 行 |
| `tests_execution/test_protection_side.py` | 新增 6 项：one-way/BOTH/HEDGE/None 四种模式 + 拒绝收口 + 传输错误收口 |

### 9.5 处理结果

- 服务已重启（PID 14532，boot 40），`/api/ready` 恢复：`ready=true`、`new_entry_allowed=true`、`blockers=[]`、`outbox.submitting=0`。
- 手动 reconcile 把两条历史 SUBMITTING 收口为 `REJECTED`（`stale SUBMITTING; exchange has no such order`），并写入 `stale_submitting` 计数。
- 回归：Python 141 + 27 + 16 + 69 = **253 项全绿**。

### 9.6 仍未生效（Host 侧）

Host 仍是 13:09:50 的旧进程，因此以下仍待一次重启：risk/execution 预算（45s/3000、35s/3200）、链 340s、看门狗、重复槽位去重、stale running 修复、决策链 UI 透明化。
### 9.7 追加发现：clientOrderId 全天碰撞，第二轮“成交”其实是回放

保护单修好后，17:13 的自动轮再次 `outcome=trade`、P1 approved、P2 `ok=true`，但：

- `orders` / `fills` 表**没有新增行**；
- P2 返回的 `client_order_id` 仍是 **`wb-cyc20261-BTC-O-0`**（与 16:13 那笔完全相同）；
- `positions` 仍为 0。

根因在 `derive_client_order_id()`：

```python
cycle_raw = re.sub(r"[^A-Za-z0-9]", "", cycle_id)[:8]   # cyc-20261110T... → "cyc20261"
```

`cycle_id` 的前 8 个字符对**2026-11 的每一天**都是固定的，于是同一天所有轮次派生出同一个
clientOrderId。第二轮 P2 命中 `outbox.prepare` 的重复分支，走
`idempotent_replay` 直接返回上一笔的 `FILLED` 状态 —— 界面显示“成交”，实际**没有发出任何订单**。

**修复**：取 `cycle_id` 的**末尾 18 个字符**（时间戳 + 随机后缀）：

```python
cycle_compact = re.sub(r"[^A-Za-z0-9]", "", cycle_id)
cycle = cycle_compact[-18:] if cycle_compact else f"m{uuid.uuid4().hex[:7]}"
```

总长度仍 ≤32 字符（限 36）。新增 `tests_execution/test_client_order_id.py` 5 项回归：
同日不同轮必须不同、同 cycle 必须确定、形状/长度、短 id、空 id 回退。

> 这条 bug 解释了更早的现象：为什么 16:13 之前 30 多轮 P1 都没通过（R11），
> 而通过之后“看起来每轮都能成交”，却始终只有一笔真实订单。
### 9.8 修复后的第一次完整轮（17:26Z）：仍被 PRICE_MOVED 挡住

服务重启（boot 41）后的第一轮跑了 263s，链路走到 execution，但执行角色返回
`EXECUTION_BLOCKED:PRICE_MOVED`（无新订单）。

- `PRICE_MOVED` 是 `execution_entry/1` schema 里的**模型自判枚举**，没有确定性校验；
- 链耗时 263s 时，执行角色手里的 `reference_price` 还停留在链首证据价，模型据此判断"价格已漂移"而拒单；
- 缩短链耗时（Host 侧 risk/execution 预算修复）会显著降低该概率；进一步的做法是在调用 execution 前重新取一次实时价（当前 `reference_price` 固定为证据价）。

**结论**：Host 重启后先观察该原因是否消失；若仍出现，再给 execution 注入新鲜参考价，而不是放宽 `max_slippage_bps`。
