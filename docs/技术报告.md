## 2. LangGraph 决策图

### 2.1 节点

| 节点 | 入参 | 出参 | LLM? | 备注 |
|---|---|---|---|---|
| `market` | top_n, analyze_top | `MarketBrief` | 是（flash） | 缓存 TTL 3600s |
| `macro` | tavily key | `MacroBrief` | 是（flash） | 缓存 TTL 3600s |
| `onchain` | etherscan key, cache dir | `OnchainBrief` | 是（flash） | 缓存 TTL 3600s |
| `signal_scanner` | scan_pool, kline_limit | `tickets` | 否（确定性） | 拉 K 线 + 调 strategy_lab signal_fn |
| `strategy` | tickets + 三简报 | `StrategyRefs` | 否 | 展示本次触发的 ticket |
| `strategy_trader` | tickets + portfolio + prices | `ChannelDecision(channel=strategy)` | 是 | 名义金额按风险预算自适应 |
| `ai_trader` | 三简报 + strategy_refs + portfolio + risk_envelope + feedback | `ChannelDecision(channel=ai)` | 是（主模型） | 强制 `submit_decision` 工具；裸 JSON 也会被 `check_decision` 兜底 |
| `merge` | 两通道 ChannelDecision | `TradeDecision` | 否 | 同 symbol AI 单被丢，生成 `decision_conflicts` |
| `risk` | decision + prices + channel_status | `RiskVerdict` | 否 | 复用 `ActionSpace.check_intent` |
| `execution` | decision + verdict + prices | `receipts` | 否 | 委托 broker.execute |

### 2.2 状态字段（`AgentState`）

完整字段见 [src/core/graph.py](file:///c:/Users/Tao/Desktop/%E5%B8%81%E5%AE%89/multi-agent-trader/src/core/graph.py#L26-L44)，重点：

- `run_id` / `decision_id`：每轮唯一，幂等 `clientOrderId = mta-<decision_id>-<idx>` 由此派生。
- `tickets`：本轮 `SignalScanner` 新触发的 ticket dict 列表。
- `strategy_decision` / `ai_decision`：两个通道各自的 `ChannelDecision`。
- `decision`：`merge` 节点把两通道合并成最终 `TradeDecision`，合并后同一 symbol 的 AI 单会被丢，记 `decision_conflicts`。
- `risk_verdict` / `execution` / `execution_prices`：风控输出与执行回执。
- `error` / `signal_error` / `strategy_error` / `ai_error`：节点级异常隔离标记。

### 2.3 异常隔离

- 任一情报 Agent 抛错：本轮该简报为 mock，决策继续。
- `signal_scanner` 抛错：策略通道 `no_trade`，AI 通道不受影响。
- `strategy_trader` 抛错：策略通道 `no_trade` + `strategy_error`，AI 通道不受影响。
- `ai_trader` 抛错：AI 通道 `no_trade` + `ai_error`，策略通道已完成。
- `merge` 之前任一节点失败：仍会写库、记账，但 `decision` 默认为 `no_trade`。

## 3. 双虚拟账本与通道资金（ChannelManager）

### 3.1 资金口径

```text
session_equity = exchange_equity − baseline            # 由 CapitalManager 计算
total_equity   = strategy_book.equity + ai_book.equity  # 通道账面
strategy_book  = total × 0.60   (settings.channels.strategy_weight)
ai_book        = total × 0.40   (settings.channels.ai_weight)
```

### 3.2 UTC 每日重算

`ChannelManager._rebalance_if_needed` 在 `sync()` 中判断 `state["date"]` 与 `utc_today()`：

1. 若不同日：先 `log_channel_daily_stats` 落昨日统计。
2. 调 `broker.rebalance_books()` 重平衡到 60:40；调账属"资金划转"，记 `daily_rebalances`。
3. 更新 `strategy_day_start_equity` / `ai_day_start_equity`，写入 `state`。

### 3.3 通道保证金上限

```python
cap = channel_equity × channel_max_margin_usage        # 默认 0.80
allow_new = margin_used(channel) <= cap
```

- 通道超限 ≤ 5%：只 `allow_new = False`；
- 通道超限 > 5%：自动 `broker.close_source(channel)`，记 `channel_margin_breach` (critical)；
- 一个通道触限不影响另一通道。

### 3.4 AI 通道当日 -30% 熔断

```text
ai_loss_ratio = -ai["day_return"] = -(equity − day_start_equity) / day_start_equity
if ai_loss_ratio >= ai_daily_loss_stop(0.30) and not ai_halted:
    state["ai_halted"] = True
    log_risk_event(severity=critical, action="AI通道当日 close_only")
```

次 UTC 00:00 `rebalance` 后自动解除。

### 3.5 关键修复（F1–F4，2026-09-01）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| F1 | demo 模式重置后 `session_equity` 仍显示 5000U | `manual_reset` 把 `baseline` 强制设 0 | paper 保持 0；demo/testnet 取 `交易所余额 - initial_equity` |
| F2 | 通道资金/保证金上限不随会话权益变化 | `_channel_day_start()` 优先返回陈旧存储值 | 会话权益可用时实时计算 `session_equity × weight` |
| F3 | 重置后通道仍叠加历史平仓盈亏 | `daily_trade_stats` 按 UTC 日全量统计 | 新增 `pnl_reset_at`，重置后只统计该时刻之后的订单 |
| F4 | 重置后页面仍显示旧值 | `/api/channels` 返回陈旧 `_latest` | `service.refresh_after_reset()` 实时 sync 并刷新缓存 |

## 4. 资金与会话权益（CapitalManager）

### 4.1 三种 baseline 模式

| 模式 | baseline | `session_equity` |
|---|---|---|
| `paper` | 0 | 账本现金（= 500U 起） |
| `demo` | 交易所余额 − 200 | 真实账户波动 - 200 |
| `testnet` | 交易所余额 − 200 | 真实账户波动 - 200 |

> **关键不变量**：无论交易所绝对余额是多少，风控、通道、AI 看到的是以 500U 为起点的会话权益；与币安账户容器解耦。

### 4.2 破产重置

`sync()` 流程：

```text
1. exchange_equity = _exchange_equity()         # 三次重试
2. session_eq = exchange_equity - baseline
3. if session_eq > 0 and total_margin > session_eq × max_margin_usage(0.95):
       broker.close_all()
       log margin_cap_breach critical
4. if session_eq <= 1.0 and reset_on_bankruptcy:
       broker.close_all()
       if paper: broker.reset_capital(200)
       new_baseline = 0 if paper else exchange_eq - 200
       save baseline
       log capital_reset critical
```

### 4.3 权益接口不可用

`_exchange_equity` 连续失败时返回 `_last_exchange_equity`，并设 `_equity_stale = True`；`sync()` 走"告警 + 跳过破产检查 + 阻断新开仓"分支，记 `equity_unavailable` 警告，绝不当成 0/爆仓。

## 5. LLM 层

### 5.1 双轨

- `src/llm/openai_compatible_client.py`：OpenAI 兼容客户端，当前默认走 SenseNova `https://token.sensenova.cn/v1`，并遵守 `MTA_NO_PROXY` 网络策略。
- `src/llm/mock_client.py`：无 key 时返回固定/可配置响应，**不会让开发阻塞**。

`factory.build_llm_for_agent(settings, agent_name)` 按 `agents.yaml` + `settings.yaml.llm` 拼装；
所有实际 LLM 节点使用 `deepseek-v4-flash`，其中 `ai_trader` 使用 xhigh 推理档。

### 5.2 工具调用（Tool Call）

主 Agent 注册三个行情工具 + 一个提交工具 + 一个回查库：

| 工具 | 计入预算 | 用途 |
|---|---|---|
| `query_symbol_detail` | ✓ | 任意 USDT 永续，1m/5m/15m/1h/4h/1d K 线 + ATR + 量能 + 资金费率 + OI |
| `query_symbol_cards` | ✓ | 批量查询多个 symbol |
| `query_top_symbols` | ✓ | 按 24h 成交额查活跃合约 |
| `query_review_library` | ✗ | 查本地复盘库，不计入预算 |
| `submit_decision` | — | 唯一能落地的提交动作；裸 JSON 也会被 `check_decision` 兜底校验 |

`query_budget = 8` 是 token 闸门——orchestrator 占全系统 prompt token 的 95%，且工具结果在 messages 里逐轮累积只增不减。

### 5.3 严格纠错

```python
MAX_STRICT_SUBMITS = 2  # submit_decision 校验失败后允许自我修正次数
```

`submit_decision` 通过 Pydantic Validator 失败 → 错误以 tool result 回传 → 模型可改后重试；超过 2 次降级 `no_trade`，避免烧 token 死循环。`H3` 修复后，**裸 JSON 走宽松解析成功后也要经过 `check_decision` 与 `check_position_reviews`**，发现 issues 直接降级 `no_trade` 并记 `decision_downgraded` warn。

## 6. 确定性闸门：ActionSpace

### 6.1 三处复用同一谓词

```text
1. 动态 schema 生成（编译期剪掉模型无权执行的动作）
2. submit_decision 的 Validator 回环（错误以 tool result 回传）
3. risk.py 运行时闸门（执行前再复核，因为状态可能在 schema 之后变化）
```

`H4` 之前的 bug：模型 `submit_decision` 通过后，`risk` 节点用 `intent.leverage` 之类的字段再判一次，但两边谓词漂移，导致 token 暴涨且本轮颗粒无收。`ActionSpace` 把所有规则集中到 `core/action_space.py`，三处共用，**改规则只改这里**。

### 6.2 关键规则

- `ALWAYS_ALLOWED = ("close", "reduce", "adjust")`：存量动作任何时候都不能被剪，避免"只能开不能平"的死局。
- `allow_new` 仅控制 `open`：
  - 通道 `ai_halted` → 不可 open
  - `control_state ∈ {pause, close_only, emergency}` → 不可 open
  - 通道 margin_used > cap → 不可 open
- `max_leverage_for(intent)`：AI 通道常规 20x、强信心 25x（必须同时 `confidence ≥ 0.75` 且 `stop_loss > 0`）。
- `remaining_slots = max(0, max_open_positions − held_symbols)`。

## 7. 风控 Risk Agent

### 7.1 风险档位（学习冒险档）

来源 [config/risk_learning.yaml](file:///c:/Users/Tao/Desktop/%E5%B8%81%E5%AE%89/multi-agent-trader/config/risk_learning.yaml)：

| 项 | 常规档 | 强信心档 | AI 通道 |
|---|---|---|---|
| max_leverage | 20x | 50x | 20x |
| max_margin_usage | 0.80 | 0.95 | 0.80 |
| max_position_notional | 100,000U | 200,000U | 100,000U |
| max_open_positions | 8 | 8 | 8 |
| max_risk_per_trade | 2% | 2% | 2% |
| daily_loss_stop | 15% | — | 30% (AI 自定义) |
| max_drawdown_from_peak | 30% | — | 30% |
| allow_bare_position | true | — | false（强制 SL/TP） |
| strong_confidence_threshold | — | 0.75 | 0.75 |

### 7.2 永不关闭的硬规则

```yaml
always_enforced:
  reduce_only_for_closing: true    # 所有 close/reduce 必须 reduceOnly
  duplicate_order_block: true      # 同方向重复单拦截
  stale_data_block: true           # 行情过期阻断
  reconcile_before_reopen: true    # 重启先对账
```

- **所有开仓必须同时设置初始 SL/TP**（`require_initial_sl_tp: true`）；用实际参考入场价校验方向：
  - LONG：`SL < entry_ref < TP`
  - SHORT：`TP < entry_ref < SL`
- `entry_ref` 优先 `limit_price`（限价单），市价单取最新价。
- 实盘执行层若挂不上止盈/止损，必须重试；仍失败则立即平掉该仓位（`M1` 待办：纸面加仓路径只能收紧不能放宽）。

### 7.3 AI 通道额外规则

- `margin_mode=ISOLATED`（默认）。
- 单笔风险 ≤ AI 权益 × 2%。
- 连续 3 笔亏损 或 当日 -30% → 当日只平仓。

### 7.4 冲突规则

- 同一 symbol，策略仓与 AI 仓**互斥**。
- 策略优先：AI 想开冲突仓位 → 拒绝（`merge` 节点处理）；策略信号想开冲突仓位 → 跳过并记 `skipped_ai_conflict`。

## 8. 信号扫描：SignalScanner

### 8.1 关键约束

- 只扫描**已完成 K 线**（`close_time <= now`），不把正在形成的 bar 当信号，避免未来函数。
- 同一根 bar 只发射一次信号（持久化去重 `data/signal_scanner_state.json`）。
- 信号 → ticket 全部写审计库 `signal_events` / `signal_tickets`。
- **不复制 strategy_lab 源码**，通过 `settings.signal_scanner.strategy_lab_src` 动态 `importlib`，保证策略研究与本系统解耦。

### 8.2 Ticket 字段

```json
{
  "ticket_id":   "t-<card_id>-<symbol>-<tf>-<bar_open_ms>",
  "signal_id":   "sig-<card_id>-<symbol>-<tf>-<bar_open_ms>",
  "strategy_id": "F_OLD_MACD_RSI_8H",
  "symbol":      "ETHUSDT",
  "side":        "SHORT",
  "timeframe":   "8h",
  "signal_time": "2025-08-31T08:00:00Z",
  "signal_price": 3350.0,
  "entry_zone_low":  3310.0,
  "entry_zone_high": 3390.0,
  "expires_at":      "2025-08-31T12:00:00Z",
  "stop_loss_pct":   0.07,
  "take_profit_pct": 0.09,
  "time_stop_hours": 96,
  "entry_mode_hint": "ai_minute"
}
```

### 8.3 策略 AI 权限边界

策略 AI **可以**：

- 决定是否执行这张 ticket；
- 名义金额在 `strategy_min_notional_usdt(20)` ~ `strategy_max_notional_usdt(120)` 之间按风险预算自适应；
- 杠杆 1x~20x 动态选择；
- 市价立即进场 / 挂限价 / 条件单；
- 分一批或两批进场；
- 主动放弃 ticket。

策略 AI **不能**：

- 改品种、方向、周期；
- 改卡片规定的 SL/TP 比例与 time stop；
- 改 entry_zone 范围（由 ATR 计算）；
- ticket 过期后继续追单。

### 8.4 影子基准（执行质量计量）

每张 ticket 同时记录：

1. **实际单**：AI 选择的分钟级进场点。
2. **影子基准**：同一信号按"下一根 K 线开盘"模拟成交，不占资金。

统计字段：`entry_delay_minutes` / `entry_deviation_pct` / `actual_return` / `baseline_return` / `entry_edge`。

自动升降级（计划中，见 P3）：

- 连续 20 张优于基准 → 保持分钟级自主权限；
- 连续 20 张劣于基准 → 降级为 `next_open`；
- 结果不稳定 → 只允许在基准价 ±0.3 ATR 内微调。

## 9. 执行层

### 9.1 Broker 工厂

`exchange/factory.create_broker(settings, db)` 读 `EXECUTION_MODE`：

| mode | Base URL | Key 源 | 行为 |
|---|---|---|---|
| `paper` | — | — | `PaperBroker` 落 `data/paper_portfolio.json` |
| `demo` | `https://demo-fapi.binance.com` | `BINANCE_DEMO_API_KEY/SECRET` | 主网真实行情 + 虚拟资金 |
| `testnet` | `https://testnet.binancefuture.com` | `BINANCE_TESTNET_API_KEY/SECRET` | 模拟行情（备选） |
| `live` | `https://fapi.binance.com` | `BINANCE_LIVE_API_KEY/SECRET` | 真实资金（默认禁用） |

`EXECUTION_MODE` 缺失对应 key → 自动回退 `paper` 并记 `broker_fallback_paper` 警告。

### 9.2 PaperBroker（本地双账本）

来源 [src/agents/execution.py](file:///c:/Users/Tao/Desktop/%E5%B8%81%E5%AE%89/multi-agent-trader/src/agents/execution.py)：

- 双账本结构：`state["books"]["strategy"]` 与 `state["books"]["ai"]`，各有 `cash / initial_equity / day_start_equity / positions / pending_orders`。
- 权益口径（逐仓）：
  - `book.equity = cash + Σposition.margin + Σposition.upnl`
  - LONG: `upnl = qty × (price − entry)`
  - SHORT: `upnl = qty × (entry − price)`
- 限价单队列：进入 `pending_orders`，用后续 1m K 线高低点按时间顺序判断成交，**不允许未来函数**。
- 旧状态迁移：旧 orchestrator 仓位自动归 AI 通道后重平衡。

## 13. 关键技术取舍

### 13.1 选 LangGraph 而不是裸 asyncio / Celery

每个情报 Agent 是图节点，并行后聚合到 merge；确定性闸门（schema / risk / execution）必须串行；这种"局部并行 + 整体串行"的拓扑用 LangGraph 表达最自然，且能直接拿到 `state` 做调试与回放。

### 13.2 选 SenseNova / OpenAI 兼容接口而不是 LangChain LLM 抽象

LangChain 的 LLM 抽象对多 provider 已经过度工程；OpenAI 兼容协议 + `httpx` 直接拼装，token 计数可控、延迟可见、出错可重试。`mock_client` 在没有 key 时也能跑通主流程。

### 13.3 选 SQLite 而不是 Postgres

单进程单写者，审计数据按日回放足够；SQLite 备份容易（一个文件）。等需要跨机时再迁。

### 13.4 选 Demo Trading 而不是测试网 / 沙盒

- 测试网：行情是模拟的，无法验证策略在真实波动下的表现。
- Demo Trading：主网真实行情 + 虚拟资金，是最接近实盘但不需要冒险金的沙盒。
- 主流 MCP 工具（Agent-Native）要求 confirm-before-execute 且未支持测试网，与"主 Agent 自主决策"目标冲突，**不接入**。

### 13.5 双交易通道的工程成本与收益

- 成本：双账本 / 双统计 / 双熔断 / 互斥 / 来源台账，代码量增加约 30%。
- 收益：
  - 策略通道（确定性）能稳定提供"是不是这套策略值得保留"的统计；
  - AI 通道（自主）能验证"AI 自主决策在风险预算内能不能跑赢策略"；
  - 两通道在同一账户上互斥运行，**用一张交易所账户同时做策略验证 + AI 验证**，是单人项目的最优解。
  - 等资金足够再考虑 Binance 子账户做物理分账。

### 13.6 选本地 FastAPI 而不是 React

- 单人学习项目，不值得引入前端构建链。
- FastAPI + Jinja2 + 原生 JS 完全够用，接口稳定后想换 React 可整体替换。
- 控制接口（`/api/control`）设计成纯 REST，前后端解耦。
