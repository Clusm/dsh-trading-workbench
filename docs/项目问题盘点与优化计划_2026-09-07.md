## 1. 结论与边界

项目已有明确的确定性风控、普通订单 Outbox、实例锁、原子状态写入、保护单镜像、审计数据库、在线备份和离线冒烟测试。当前最需要优化的是故障发生后的安全退化和恢复闭环，其次是可复现测试与模块边界。建议先完成 P0/P1，再投入新策略或扩大 AI 情报能力。

本次进行了源码审查、静态检查、三个隔离冒烟脚本和临时目录中的状态损坏复现。未启动交易服务、调用交易所或 LLM、修改风险配置、读取凭据内容或查询运行数据库。因此以下问题不等同于正在发生的线上事故，也不能据此评价策略收益。

优先级：P0 为安全控制可能失效，进入实盘前必须解决；P1 为执行可靠性、恢复和部署边界问题；P2 为维护效率与性能改进。工期是单名熟悉项目的开发者的有效工作日估算，不是承诺。

## 2. 问题清单

### F01 · P0 · 控制文件损坏后恢复为允许开仓【已复现】

- 证据：`src/core/control.py:18` 构造函数默认 `normal`，解析失败直接忽略；文件存在但 state 非法也保留默认值。
- 触发：原本为 pause/emergency 的文件损坏或不可读，随后重启。
- 复现：临时文件写入 `{broken`，构造 ControlState，得到 `state=normal`、`allow_new_positions=True`。这证明控制闸门放行，不代表其他闸门一定允许实际成交。
- 影响：人工停机意图丢失。原子替换降低半写概率，但无法处理手工破坏、磁盘错误或错误恢复。
- 整改：区分首次启动缺失与已有状态损坏；损坏进入 close_only 或显式 recovery_required，保留坏文件，生成 critical incident。状态写入成功后再提交内存值，明确写失败的保守行为。
- 验收：截断 JSON、非法枚举、权限错误、replace 失败及重启均不能自动恢复开仓；有效 emergency 能正常保持；保护与减仓仍可用。

### F02 · P0 · 风险状态损坏会重建水位并丢失熔断【已复现/源码确认】

- 证据：`src/core/risk_guard.py:40` 读取失败返回空字典；sync 按当前权益重建峰值。`src/core/channels.py:41` 失败后默认 `ai_halted=False`。
- 复现：损坏风险文件，在 enforce 模式以 350 权益同步，得到 `allow_new=True`、`peak_equity=350`、`daily_loss_ratio=0`。历史水位与锁存信息无法从该文件恢复。
- 影响：此前更高水位、日亏损或 AI 熔断可能丢失；是否实际开仓仍取决于其他闸门。
- 整改：状态增加版本、环境和会话标识；损坏禁止新开仓；使用已验证快照及审计记录重建，不能直接把当前权益视作新起点。将风险锁存与资金锚点的持久化逐步统一到事务边界。
- 验收：在已熔断状态破坏文件并重启，仍禁止新仓；不能证明历史状态时进入待恢复；跨会话与跨环境不串用。

### F03 · P1 · 保护单未覆盖普通订单的持久化幂等协议【源码确认】

- 证据：`src/exchange/binance_futures.py:966` 的 `_place_algo_protection` 直接 POST algoOrder，成功后才写审计。本地生成 cid，但当前请求参数未携带该 cid；与 `:356` 普通订单 prepare→POST→确认链不同。
- 触发：交易所已接受保护单，但响应丢失，或进程在接收响应后、审计前退出。
- 影响：本地不能依赖持久化提交 ID 确认结果；现有保护镜像和重扫能缓解，但无法替代提交阶段的恢复证据。重复或暂缺保护的具体概率本次未测量。
- 整改：为 Algo 命令建立独立/扩展 Outbox；实现前核验当前交易所官方接口支持的客户端标识和查询语义；提交前持久化；不确定时查询并阻断重复创建。覆盖创建、替换、取消的中间状态。
- 验收：模拟响应丢失、重启、延迟可见及取消失败；不确定提交不盲目重发；最终保护覆盖正确，并保留完整审计。

### F04 · P1 · 缺少环境密钥仍自动转入 paper【源码确认，现有设计】

- 证据：`src/exchange/factory.py` 的 create_broker 对未知模式拒绝启动，但 demo/testnet/live 缺少凭据时返回 PaperBroker。
- 影响：配置错误被包装成可运行系统；操作者期望管理远端仓位时，当前进程实际操作独立纸面账户。已有风险事件和模式显示，但尚不能消除误判。
- 整改：默认对所选非 paper 环境缺凭据拒绝进入交易运行态；若需要兼容降级，增加明确开关并显示 requested_mode/effective_mode/degraded_reason；不得仅凭 paper 初始化成功宣布预期环境已就绪。
- 验收：逐一测试缺 key、缺 secret、非法模式、显式 paper；预期与实际模式不一致时 readiness 失败。

### F05 · P1 · UNKNOWN 的安全阻断缺少有界处置流程【源码确认】

- 证据：`src/exchange/order_outbox.py:52` 阻断本环境所有新开仓；`:183` 查询失败仅更新 last_error，没有单条 next_retry_at、次数、分级升级或人工证据结案入口。
- 触发：prepare 后尚未发送即崩溃，或提交结果长期无法查证。
- 影响：安全阻断本身正确，但可能无限停留并反复查询。不能通过超时直接当作不存在，更不能删除记录解锁。
- 整改：记录未知原因、首次发生时间、查询历史、退避和告警升级；明确交易所未找到与查询失败；设计基于充分证据的人工结案流程，并与运行手册对接。
- 验收：持续未知时不新增订单；重试有预算；减仓仍允许；人工结案有依据、有操作者记录、可追溯。

### F06 · P1 · 健康与就绪状态缺少快照时效约束【源码确认】

- 证据：`src/dashboard/app.py:1567` health 的 ok 只组合 safety.ready、broker error 和 DB 可读；虽然输出循环 age/error，却不纳入 ok。`:1696` ready 也未检查快循环/账户/保护核验的最大年龄。
- 影响：循环停滞而旧快照仍为正常时，外部监控可能看到健康或就绪；本次未复现运行中停滞。
- 整改：区分进程存活、交易健康、允许开仓；为关键快照增加 observed_at、source、age、stale；提取统一的就绪判定供 UI 和执行层使用，避免只改显示。
- 验收：假时钟推进至过期后健康/就绪正确变化；正常 LLM 慢调用不误伤独立快循环；展示具体阻断原因；影子情报异常不应错误阻断交易。

### F07 · P1 · 审计模式不执行账户日亏损/回撤拦截【配置确认，策略选择】

- 证据：`config/settings.yaml:15` 为 `risk_guard_mode: audit_only`；`src/core/risk_guard.py` 在该模式下即使 would_allow_new=False，仍返回 allow_new=True。权益不可用仍会阻断。
- 影响：不能把“已计算账户风险”解释成“已强制阻断”。这不是擅自修改既有策略的理由；其他单笔、通道和保护约束仍存在。
- 整改：控制台明确展示审计/执行状态、实际阻断与模拟阻断；环境准入策略显式声明是否允许 audit_only。若未来启用 enforce，单独评估与验收，不在维护重构中顺手改变。
- 验收：阈值触发时两种模式的 UI、审计和执行结果一致；发布检查能识别模式；现有锁定风险参数不漂移。

### F08 · P1 · 控制台安全依赖仅本机可达【源码确认，条件风险】

- 证据：`scripts/run_web.py` 默认 127.0.0.1，但允许任意 --host；`src/dashboard/app.py:1288` 生成写 token，`:1301` 打印到控制台，页面也下发 token。读取页面没有登录鉴权。
- 影响：现有 token 可防跨站伪造，但不是用户身份认证；一旦监听局域网/公网或被无鉴权代理转发，能够访问页面的人也能获取写 token。未检查当前端口暴露情况，不认定已遭攻击。
- 整改：默认强制 loopback；远程访问必须配置认证与受信代理策略；移除 token 日志；增加 Host/Origin 校验和安全审计。
- 验收：未认证远程请求无法读取敏感页面或调用控制接口；本机正常操作及原有 CSRF 测试保持通过。

### F09 · P1 · 恢复备份未覆盖全部关键状态的一致性【源码确认】

- 证据：`src/core/db_backup.py:81` 使用 SQLite backup API，正确覆盖 WAL；但 capital/channel/control/risk/source ledger 等 JSON 位于数据库之外。现有恢复手册主要描述数据库恢复。
- 影响：只恢复旧 DB、保留较新的 JSON，或反过来，可能形成不同会话与不同时间的状态组合。整机/磁盘故障时，同盘备份也不能提供独立恢复来源。
- 整改：短期制定包含版本、环境、会话锚点和文件哈希的恢复清单；在安全停写点获取一致集合，或记录可验证的重建步骤；中期将关键账本统一到事务存储。保存独立位置副本并做隔离恢复演练。
- 验收：从独立备份恢复后能核对权益锚点、锁存、订单意图及交易所现状；UNKNOWN 保留；不同版本组合被拒绝。RPO/RTO 先定义再实测，建议初始目标 RPO≤1小时、RTO≤30分钟，需按数据量确认。

### F10 · P2 · 质量门禁与可复现构建不完整【已确认】

- 历史证据：`scripts/check_quality.py` 曾只对 Git 已跟踪 Python 执行 Ruff、编译及风险锁检查，不运行行为测试；requirements 曾为宽范围，且策略运行时依赖仓库外路径。
- 影响：静态检查通过不代表执行协议正确；新增未跟踪脚本不在门禁范围；新机器依赖和外部策略版本不确定。外部 CI 是否另有配置本次未核验。
- 整改：建立显式离线回归清单、默认禁网和临时目录夹具；在线 probe 单独运行；锁定可重建依赖和策略包版本；CI 包含 Windows 环境；逐步迁移到统一测试入口。
- 验收：干净环境一次安装并通过核心回归；错误新增文件能被检查；默认回归不读本机凭据、不操作真实 data、不发网络请求。覆盖率集中于状态机关键分支，不把总覆盖率当作唯一目标。

### F11 · P2 · 巨型模块与静默降级增加定位成本【已确认】

- 证据：当前 app.py 2044 行、binance_futures.py 1853 行、database.py 1526 行、orchestrator.py 899 行；`src/core/service.py:240` 快照刷新异常直接 pass，旧展示值缺少本次刷新失败信号。
- 影响：UI、账户投影、订单协议和恢复逻辑的修改影响范围大。行数是维护信号，不证明存在性能故障；目前没有负载基准，不能声称数据库已成为瓶颈。
- 整改：先提取健康判定、状态投影等纯逻辑，再按普通订单/Algo/对账分离 Broker 职责，最后拆审计仓储与迁移。异常保留最后有效值，同时标 degraded、error_code、last_success_at。性能先测 DB 锁等待、快循环耗时与 API P95。
- 验收：每次只迁移一个职责，兼容现有 API；回归结果一致；故障注入时展示旧值必须同时展示过期标记；性能改动有前后对照。

### F12 · P2 · 源码与运行产物边界不完整【已确认】

- 证据：git status 存在未跟踪 data/ 和多个诊断/修复脚本；`.gitignore` 未覆盖 data/backups、若干 HTML 探针和运行文件。上层目录并列大量会话提取中间产物。
- 影响：提交噪声、误纳入账户数据的概率上升、维护脚本入口难辨。没有证据表明备份已被提交或泄露；`git ls-files data` 本次为空。
- 整改：定义 runtime、fixtures、诊断与维护脚本边界；完善忽略规则，保留明确允许的测试夹具；对修复脚本统一增加 dry-run、运行环境摘要、互斥和修改后核验；历史提取材料建立归档索引。
- 验收：正常运行不污染源码状态；模拟备份/凭据文件不会被常规提交纳入；维护脚本默认只预览，实际更改有记录；不自动删除既有文件。

| 场景 | 必须观察到的结果 |

| 磁盘写入失败 | 控制与风险状态不产生未定义的内存/磁盘分歧 |
| 默认回归 | 零网络、临时文件、无真实服务与凭据依赖 |

### 7.2 对本项目有价值的策略机制

| A | 低波动/震荡均值回归 | 现有结构、供需和 RSI 背离策略可在合适市场状态下提高选择性 | 仅在 `range/calm` 状态且有订单流确认时生成候选；趋势状态禁用该候选 | shadow |
| A | 成交量与微观结构确认 | 降低只凭 K 线形态开仓及未完成 K 线误读 | 引入闭合 K 线、价差、盘口深度、主动买卖、资金费率、OI、清算数据的证据门 | 数据质量先 enforce，方向评价先 shadow |

| A | 回放、走步和成本归因 | 外部“回测存在”不等于对本项目有效 | 基于本项目历史快照原生实现 USD-M 回放，纳入费用、资金费率、滑点和深度 | 离线 |
| B | 流动性扫单反转 | 对假突破后的快速回归可能有价值 | 仅作为研究候选，需要成交量/订单流/闭合 K 线共同确认 | experiment_only |
| B | 资金费率/OI 背离 | 辅助识别拥挤方向与挤仓风险 | 只作为上下文特征，不单独触发交易 | shadow，执行权重 0 |
| B | 突破回踩确认 | 比首次突破追价更适合当前低频决策链 | 形成现有 Keltner/结构策略的实验变体 | experiment_only |

本项目已有 9 张策略卡，覆盖 MACD+RSI、PO3、市场结构与 OTE、逆向情绪、供需区、成交量与 RSI 背离及 Keltner 突破。CloddsBot 中的动量、均值回归和价格/成交量阈值与这些策略高度重叠，不再新增同名策略卡。升级重点是修复候选生成、证据质量、市场状态适配和退出管理，而不是用更多相似策略扩大扫描数量。

### 7.3 明确不采用的策略

以下能力不进入开发范围：Polymarket 二元合约动量、到期衰减、penny clipper、预测市场做市、现货与预测市场价差、跨交易所套利、Solana dip-buy/DCA/阶梯策略、复制交易、多市场路由。原因是交易品种、成交语义、到期机制、链上执行或资金模型与币安 USD-M 永续合约不一致。

CloddsBot 的 Kelly 仓位算法和低波动放大系数也不采用。前者需要已校准的真实胜率与优势估计，当前 AI `confidence` 不能替代；后者可能改变现有风险档。外部风险引擎中按近期交易 PnL 推断波动状态、按同向头寸数量近似相关性的做法仅作反例，不直接移植。

## 8. G–K 阶段共同设计约束

1. **交易边界不变**：只处理币安 USD-M 永续合约；不增加现货、期权、预测市场、链上或其他交易所执行器。
2. **风险档不变**：不得修改 `config/risk_learning.yaml`、风险锁哈希、杠杆上限、单笔风险、持仓数量、白名单、资金基线和现有止损要求。新增决策质量规则放入独立 `decision_policy`，不能伪装成风险参数调整。
3. **情报权限不变**：聪明钱、链上和市场情报仍为 `shadow/context`，执行权重保持 0；任何晋级必须另立评估和审批，不随 G–K 自动启用。
4. **AI 推理档不降级**：保留 agent 的 max 推理设置，但输入证据和输出契约必须结构化；模型不可用时禁止新开仓，已有仓位的交易所保护、对账和确定性管理继续运行。
5. **先影子、后强制**：除数据过期、数据缺失、未闭合 K 线误用等客观错误可直接阻止新开仓外，方向、追价、相关性、连亏等新规则必须先 shadow，形成机会成本与漏拦统计后再单项 promote。
6. **退出能力优先**：任何新闸门不得阻止平仓、减仓、止损维护、保护单修复和人工 emergency 操作。
7. **可回放、可解释、可回退**：每项检查必须有稳定原因码、输入快照和版本；关闭新策略层即可回到原决策链，不回滚交易所状态，不删除 UNKNOWN。

## 9. G–K 详细开发计划

### G · P0 · 市场数据与 AI 决策证据契约（3–5 个开发日）

目标：先消除未完成 K 线、陈旧数据和提示词偏置，再让每个开仓决定具备可机器验证的趋势、入场、止损、目标和证据链。

逐项任务：

- **G01 提示词中立化**：删除“每轮积极寻找机会、不要轻易 no_trade”一类交易频率偏置；明确 `no_trade` 是正常且无需补偿的结果；禁止模型因上一轮无交易而降低门槛。
- **G02 闭合 K 线口径**：指标默认只使用最后一根已闭合 K 线；当前形成中的 K 线只以 `live_bar` 单独提供，不能参与 EMA、ATR、成交量比和背离确认。

- **G04 结构化决策契约**：开仓输出必须包含 `strategy_id`、方向、市场状态、支持证据、反证、触发价、结构无效点、止损、目标、风险收益比、追价距离、数据时点和信心来源；自然语言解释不得替代字段。
- **G05 决策质量评估器**：独立于现有风险档实现 `trend_alignment`、`rr_quality`、`entry_chase`、`evidence_conflict` 和 `closed_bar_confirmation`；先记录 shadow 结果，禁止把 AI confidence 当作豁免条件。
- **G06 策略适配标签**：现有 9 张策略卡增加适用市场状态、必需证据和禁用条件；不改原始风险值，不新增重复动量/均值回归卡。

建议实现边界：`src/data/market_query.py`、`src/data/binance_public.py`、`src/agents/models.py`、`src/agents/orchestrator.py`，新增 `src/core/decision_policy.py` 与 `config/decision_policy.yaml`。配置只保存决策质量模式和原因码，不复制风险档字段。

### H · P0/P1 · 组合方向、相关性与连亏状态（4–6 个开发日）

目标：识别多个高 beta 山寨币在同一方向上的重复下注，以及短时间连续同类失败；先减少决策盲区，不通过降低仓位或修改风险档实现。

逐项任务：

- **H01 风险因子归类**：基于滚动收益相关性和 BTC beta 动态生成因子簇，静态币种组只作为缺数据时的保守标签；结果带版本、样本窗口和置信度。
- **H02 组合方向视图**：聚合同方向名义敞口、止损最坏损失、BTC/ETH beta 敞口和同因子候选数量；避免只按“持仓个数”判断集中度。
- **H03 连亏分类账**：按 `strategy_id + regime + direction + factor_cluster` 记录已实现结果、连续失败、最近失效原因和冷却到期；重启后可恢复且不跨环境串用。
- **H04 冷却策略**：初始只生成 shadow 建议；达到阈值后要求新的独立证据，不能用同一 K 线指标重复计数。是否升级为阻断必须通过 J 阶段评估和单独提交。
- **H05 震荡/方向失配识别**：短窗口内同策略双向连续止损时标记 `choppy_or_model_mismatch`，暂停该策略候选而不是全局停止交易。

测试用例：

- LINK、SUI、ARB、AVAX 在相近窗口同向开多时被归入共同高 beta 风险视图；不同方向的对冲暴露不被简单相加为同向风险。
- 相关性样本不足、稳定币异常、价格缺口和新上币时进入低置信状态，不伪造精确相关性。
- 相同策略/市场状态/方向的连续失败命中冷却；不同策略或有独立证据的候选可被区分。
- 状态跨进程重启保持，demo/testnet/live 与不同 session 不串账；日期边界和时钟回拨有覆盖。
- 所有冷却和组合检查均不阻止减仓、止损、保护修复；现有单笔风险与杠杆计算结果逐字段不变。

验收门槛：

- 每笔候选均产生可审计的因子簇、方向敞口和连亏状态；缺数据时不得静默标记“低风险”。
- 9 月连续逆势多单回放能够显示聚集风险和同类失败序列，且无需修改任何风险档字段。
- shadow 期至少覆盖 200 个方向候选且不少于 7 个自然日；晋级前必须同时报告拦截命中、误拦机会成本和未覆盖损失，不以单一收益指标决策。

### I · P0 · 独立 Position Guardian 与模型故障退化（4–6 个开发日）

目标：把“是否新开仓”和“已有仓位是否仍满足交易论点”拆开；即使 LLM、DNS 或供应商链路故障，仓位仍有确定性的保护和复核路径。

逐项任务：

- **I01 结构化持仓论点**：开仓时持久化方向、入场依据、结构无效点、比较操作符、确认周期、最晚复核时间和允许的数据源，不从后续自由文本猜测。
- **I02 Guardian 状态机**：实现 `ACTIVE → REVIEW_DUE → INVALIDATED/EXPIRED → CLOSE_INTENT → CLOSED/UNKNOWN`；与普通订单/Algo Outbox 复用幂等和恢复协议。
- **I03 模型故障策略**：LLM 不可用时立即禁止新开仓；已有仓位继续执行交易所止损/止盈、快循环对账和保护修复。只有机器可验证的无效点或已批准的时间规则可触发确定性退出，其余情况发 critical 告警而不编造 AI 决策。
- **I04 论点漂移检测**：后续 AI 不得无证据改变原止损、无效点或策略标识；任何放宽必须走明确的修改意图、审计和现有风险检查。
- **I05 人工接管**：展示每个仓位的 Guardian 状态、最后成功评估时间和阻断原因；人工平/减仓保持现有授权和审计链。

测试用例：

- 注入 DNS 失败、超时、429、空响应、非法 JSON 和连续 67 次模型失败；验证新开仓停用，但止损、保护对账和人工退出不受影响。
- 闭合 K 线越过结构无效点后只生成一次平仓意图；响应丢失和重启不重复提交，UNKNOWN 按既有协议收敛。
- 仅影线触碰但确认规则要求收盘时不得误平；时区、周期边界和缺 K 线进入待复核而非擅自判定。
- 模型建议放宽止损或延长过期时间时，未经允许不得覆盖原论点。
- 交易所已有仓位、本地记录缺失和部分成交场景通过对账进入显式恢复状态。

验收门槛：

- 模型故障注入期间新开仓为 0，已有保护覆盖率保持 100%，快循环无阻塞。
- 每个确定性退出都有持久化触发证据；同一失效事件最多产生一个有效交易所命令。
- Guardian 不能修改风险档、不能创建新增仓，只能维持保护、减仓或退出。

### J · P1 · USD-M 原生回放、走步评估与策略晋级（5–8 个开发日）

目标：用本项目自己的数据、费用和成交语义评价 G–I，而不是引用外部项目的策略数量或回测结果。

逐项任务：

- **J01 事件回放格式**：定义不可变夹具，包含闭合 K 线、实时形成 K 线、资金费率、OI、订单簿摘要、账户/仓位、模型输入输出、策略票据和执行结果。
- **J02 成交与成本模型**：覆盖 taker/maker 费用、资金费率、最小数量/价格精度、盘口深度、滑点、部分成交和信号到下单延迟；不承诺历史盘口缺失时的虚假精度。
- **J03 事故回放集**：固化 9 月 7 日以来连续亏损和策略扫描异常的去敏快照，保证可复现“知道趋势却逆势开多”“未完成 K 线误读”“模型链路中断”等路径。
- **J04 走步与样本外评估**：按时间切分训练/校准/样本外窗口，禁止用事故结果反向硬编码阈值；每个策略变体单独版本化。
- **J05 稳健性评估**：使用 bootstrap/Monte Carlo 评估成交顺序、滑点和缺失数据敏感性；只辅助判断，不把模拟分位数包装为收益保证。
- **J06 晋级报告**：比较基线与候选的触发频率、避免损失、机会成本、净收益、Profit Factor、最大回撤、覆盖率、平均持有时间、边际衰减和数据可用率。

测试用例：

- 同一夹具、同一配置和版本重复回放结果完全一致；事件乱序被拒绝或稳定排序并记录。
- 手续费、资金费率、滑点分别启停时净 PnL 变化方向正确；部分成交和精度舍入与 Broker 规则一致。
- 未来数据泄漏检测：任何指标不得读取决策时点后的 K 线、OI 或成交结果。
- 阈值在样本内改善但样本外恶化时不得晋级；缺盘口历史时报告 `coverage_gap`，不得自动补零。
- 回放过程零网络、零真实账户操作、零凭据读取，输出不写真实状态目录。

验收门槛：

- 事故回放集在干净环境可一键运行，结果含配置哈希、代码版本、数据覆盖和成本假设。
- 候选规则至少经历 200 个方向候选、30 笔闭合 Demo 交易和 7 个自然日观察；样本不足只能标记“继续观察”，不能宣称有效。
- 晋级必须在样本外同时满足：最大回撤不高于基线、净 Profit Factor 不低于基线、已知事故模式覆盖提升，且机会成本处于预先声明范围。具体数值阈值在首次基线报告后冻结，不能根据候选结果临时调低。
- 任何规则从 shadow 切换 enforce 都使用独立提交和独立配置开关；不得批量晋级。

### K · P1 · 统一决策管线、可视化与运维闭环（3–5 个开发日）

目标：把 G–J 的结果组合为稳定、可维护、可观察的单一路径，消除“某处检查了但实际执行链未调用”的假安全。

正式顺序：

`运行/账户健康 → Position Guardian 优先任务 → 数据新鲜度与闭合 K 线 → 结构化证据 → 策略适配 → 方向/追价/RR → 因子集中与连亏 → 现有 RiskGuard → Outbox → Binance USD-M`

逐项任务：

- **K01 单一入口**：所有新开仓必须经过同一 `DecisionPipeline`；禁止 agent、策略扫描器或 Web API 绕过。平仓/减仓走明确的退出分支。
- **K02 命名检查结果**：统一 `PASS/WARN/BLOCK/NOT_EVALUATED`，附 `check_id/version/mode/reason/evidence_at`；区分 `off/shadow/enforce`。
- **K03 控制台展示**：市场情报、链上情报、策略候选、AI 决策和最终执行按层显示；明确标注“仅参考/影子/强制”，展示被过滤原因而不只显示“无信号”。
- **K04 指标与告警**：统计扫描成功率、各原因码分布、模型可用率、数据年龄、Guardian 复核延迟、保护覆盖、shadow 机会成本及最终成交转化率。
- **K05 运维文档**：更新 README、架构图、配置说明、策略卡规范、故障处理、Demo 晋级、回退和数据恢复手册；核心模块补充中文“为什么”注释，避免逐行翻译式注释。
- **K06 兼容清理**：在测试覆盖后删除确认无引用的重复入口和陈旧适配层；任何运行数据、历史审计和用户诊断脚本不得自动删除。

测试用例：

- 从策略扫描到 Broker 提交的集成测试证明每个开仓只能经过一次管线，旁路调用被拒绝并记录。
- 任一检查抛异常时按其安全级别得到确定性结果；不能因异常默认 PASS，也不能影响允许的退出路径。
- shadow 与 enforce 对同一候选给出相同判断，仅执行效果不同；切换配置不改变现有风险档哈希。
- 控制台准确显示“未扫描、无候选、被过滤、模型失败、风险拒绝、已提交”六类状态，避免把扫描错误误认为策略没有触发。
- 重启、并发扫描、重复事件、模型延迟、交易所超时和磁盘写失败均进入既有幂等/恢复协议。

验收门槛：

- 代码搜索和集成测试均证明不存在可达的新开仓旁路；决策审计可从最终订单反查全部检查和原始证据版本。
- Dashboard 与数据库统计一致，任一“无交易”都能归属于明确阶段和原因码。
- 全量离线回归、质量检查、故障注入和 7 天 Demo 观察通过；保护覆盖、UNKNOWN 收敛和快循环性能不得低于当前基线。
- 发布前再次核对风险档哈希、USD-M 白名单和情报执行权重，三者必须与升级前完全一致。

## 11. G–K 提交顺序与每次门禁

每个提交保持可独立回退，禁止把风险档变更、策略晋级和结构重构混在一起。建议顺序如下：

1. **`docs: record Clodds review and G-K delivery plan`**：只提交研究结论、范围、用例和验收门槛；运行 Markdown 链接/格式检查与 `git diff --check`。
2. **`fix(data): use closed candles and enforce freshness metadata`**：完成 G02/G03；运行指标单测、时间边界、数据陈旧和真实状态隔离回归。
3. **`feat(ai): add neutral prompt and decision evidence contract`**：完成 G01/G04；运行模型合法/非法响应、no_trade 和旧数据兼容测试。
4. **`feat(policy): evaluate trend rr chase and strategy regime in shadow`**：完成 G05/G06；只开 shadow，附 9 月事故回放结果，不改变执行。
5. **`feat(portfolio): add factor exposure and loss-state shadow ledger`**：完成 H01–H05；运行重启、跨环境、相关性缺样本和退出不受阻测试。
6. **`feat(guardian): add deterministic position thesis supervision`**：完成 I01–I05；运行模型断链、无效点、幂等退出、UNKNOWN 和保护覆盖测试。
7. **`feat(replay): add USD-M event replay and cost model`**：完成 J01–J03；提交去敏夹具、未来函数检测和确定性结果。
8. **`test(strategy): add walk-forward robustness and promotion report`**：完成 J04–J06；只生成评估报告，不自动修改运行配置。
9. **`feat(pipeline): unify checks and expose decision trace`**：完成 K01–K04；运行旁路、并发、故障注入、Dashboard/DB 一致性和性能回归。
10. **`docs(ops): update architecture strategy and recovery runbooks`**：完成 K05/K06 中无风险的文档与清理；运行全量离线回归和源码边界检查。
11. **`policy: promote <single-check-id> after demo acceptance`**：仅当 J 阶段门槛全部满足时，一次只晋级一个检查；提交必须附基线、样本外结果、误拦分析、回退开关和风险档哈希复核。未达到门槛时不存在这类提交。

每次代码提交共同门禁：`scripts/check_quality.py`、相关单元/冒烟测试、默认禁网、临时 `project_root`、真实 `data/` 哈希不变、无凭据读取、风险档哈希不变。涉及 Broker/Guardian/管线的提交还必须运行订单 Outbox、保护单、UNKNOWN、服务生命周期和 Web 隔离回归。任何失败先修复或回退该提交，不把失败留给后续提交掩盖。
