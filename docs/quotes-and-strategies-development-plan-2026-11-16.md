# 持仓行情更新与策略挂载 · 开发计划

- 日期：2026-11-16。
- 状态：首版代码与离线验证已完成；尚未部署，Q03 与 Demo 实际交易验收待完成。详见 [连续实施记录](quotes-and-strategies-implementation-2026-11-16.md)。
- 原则：简单、可靠、专业；复用 Client → Host → Service → SQLite/交易所架构。
- 输入：[行情调查](position-quotes-investigation-2026-11-16.md)、[策略提案](strategy-mounting-proposal.md)、[07 优化方案](live-mode/07-方案优化评审.md)。
- 本计划是上述两个需求的执行清单，不重新启动 07 中其他全部改造。

## 1. 范围与产品默认决策

| 项 | 本期决定 |
|---|---|
| 行情 | 先准确呈现过期状态，再实现独立轻量标记价刷新；优先 REST，不先上 WebSocket |
| 策略输入 | 自然语言、Markdown、纯文本；不执行上传代码，不首发 PDF/OCR |
| AI 补全 | AI 解释、指出矛盾并提建议；交易意图缺项由用户补全或确认 |
| 挂载 | 确认后的不可变策略版本；已挂载不等于已启用 |
| 命名 | 用户可在添加时或挂载后改名；名称不作为执行身份 |
| 调度 | 用户授权策略后，AI 可在已授权集合中选择；无需每轮确认，不能自行授权新策略 |
| 并发 | 沿用账户现有限制，首版每轮最多一个新开仓策略；不增加跨策略并发仓位 |
| 规则能力 | 首批支持已有数据/指标可表达的规则；判断型规则仅在结构化输出与校验可验证时开放 |
| 自动修改 | 不自动改策略、提额、切环境、自动启用草稿；修改需形成新版本并确认 |

以上是第一版的实施假设，可在开工前修订，不需要再为普通代码组织与实现细节反复确认。未回答的上传代码等扩展能力不进入本期。

## 4. 行情需求：Q01–Q03

### Q01 · 旧数据必须看得出来（P0）

**代码落点**：`client.js` 的持仓/保护/异常提示与刷新 effect；`host/integration.js` 快照投影。

- 区分服务在线、行情可用和账户数据可用；保留最后成功数据及时间，失联标“历史快照”。
- 数据年龄随时钟增长，不能只在新响应到达时更新。价格、盈亏、保护状态分别保留其时间来源。
- 独立行情定时器不依赖整个 stateData，账户刷新不清零行情计时。
- 显式监听页面可见性：隐藏时停止页面高频轮询，恢复可见立即刷新；后台保护和执行继续由 Service 管理。
- 页面卸载取消请求；单通道只保留一个在途请求，响应时间长时不叠加新请求，失败用有上限的退避。

**验收**：模拟断线、503、隐藏/恢复、AI 运行中的 3 秒状态轮询；旧值不变成零，行情 timer 不被饿死，不堆积请求。

### Q02 · 独立轻量标记价（P1）

**代码落点**：`service/workbench_service/market/service.py` 和对应 API，`host/service-client.js`、`host/integration.js`、`client.js`。

- 新增轻量用途的标记价接口或兼容可选参数，保留现有含深度的 prices 契约；该通道不查询深度、订单、成交、权益曲线或复盘。
- 页面传入全部持仓标的，去重并限制数量；服务端验证标的，Host 只读代理并经过统一 DSH 访问检查。
- 可见页面目标周期 2 秒。Service 按环境/标的共享短缓存、合并同时到达的请求；多个页面不成倍放大上游访问。
- 遵守上游限流/重试提示；断线保留数据并标 stale，不对失败请求做高频强制刷新。
- 建议响应字段：`symbol, mark, source, as_of_ms, received_at_ms, stale`。复用已有同义字段，不再造重复时间字段。
- 页面以同环境、同标的且更新的行情更新行内标记价；拒绝乱序响应。账户切换、持仓消失后清理订阅与旧响应。
- 持仓数量、方向、入场价、官方盈亏仍来自账户快照。首版不重算账本盈亏；标记价变快而盈亏较慢时给盈亏独立时间提示。
- 新行情不能把账户过期状态“洗绿”；没有有效持仓事实时不凭新价格推断仓位仍然存在。

**验收**：多标的、乱序、缓存命中、多个页面、账户/环境切换、限流与断线；已有行情与交易校验功能不退化。

### Q03 · 实际延时验收与部署

- 上游正常条件下，可见页面标记价数据年龄目标 p95 ≤3 秒；同时记录响应耗时、价格变更呈现延时和请求量。连续观测至少 30 分钟，样本与异常段可追溯。
- 无行情源时间戳时标注只能验证接收/呈现延时，不宣称测得真实行情年龄。
- 对比修改前后请求权重和错误率，检查完整 /state 未被改为高频拉取。
- 若 REST 无法满足目标，先定位瓶颈再决定是否增量引入一个 Service 公共行情 WS；不在本轮顺便重建实时平台。

## 5. 策略需求：S01–S04

### S01 · 策略版本与授权存储

**代码落点**：Service 新增轻量 `strategies` 模块与 API；复用现有数据库迁移、鉴权、审计设施。

建议最小模型（表名可按现有命名规范调整）：

| 对象 | 关键数据与约束 |
|---|---|
| strategy | 固定 ID、显示名称、当前已确认版本、启用状态、授权 generation、创建/更新时间 |
| strategy_version | strategy_id/version、原文、规范规则、来源标记、内容摘要、用户确认；确认后不可修改 |
| strategy_draft | 原文、问题和回答、AI 建议、草稿 revision、校验状态；允许合并到版本表实现，避免多表形式主义 |
| 执行归因 | round/intent/order/position 的 strategy_id/version 与信号标识；优先利用已有元数据 |

- 规则生命周期和运行授权分开保存：新草稿不影响正在执行的旧版本；确认新版本后下一轮采用。
- 改名不改 ID/version，不重建策略；引用过的版本不硬删。首版不提供删除持仓所属策略的入口。
- 冲突保存使用 revision；挂载确认使用内容摘要和幂等 request ID，重复提交不生成两个版本。
- 启用/停用写审计；停用增加授权 generation，旧开仓意图立即失效。
- 迁移前用 SQLite 一致性备份，先测升级与重复启动；回退代码不得覆盖新成交数据库。

**验收**：保存、重命名、确认幂等、版本不可变、并发保存冲突、重启恢复、旧版本仍可追溯。

### S02 · AI 理解、提问、确认与挂载 UI

**代码落点**：Host 新增策略理解模块，复用现有 LLM、schema、预算和错误处理；`client.js` 设置/自动化增加策略区域。

- 输入采用粘贴或 UTF-8 文本文件，建议首版上限 64KB/20,000 字符，前后端一致校验；不抓取任意 URL，不运行脚本。
- AI 输出：理解摘要、结构化规则、缺项、矛盾、待答问题、建议及其来源。每次最多展示 3–5 个关键问题。
- 固定字段：适用标的、周期、入场、退出、止损/失效条件、持仓约束、所需数据、是否依赖 AI 判断。不能用空值或含糊文本通过执行校验。
- 提供受限条件结构与允许的指标/运算列表，不做通用 DSL/解释器；第一批支持能力在 P00 核对后列明，超出能力返回明确的待完善原因。
- 规则型条件由代码算；判断型输出必须有限定枚举/数值及证据时间，不能直接转成任意执行指令。
- AI 超时保留草稿和已答问题，允许重试。迟到的旧分析不能覆盖用户新修订；按草稿 revision 校验。
- 展示用户原意与 AI 建议的区别；确认后后台校验并显示“已挂载 · 未启用”。用户可以改名，再单独启用。
- 页面只增加策略列表和一个编辑/澄清详情，复用现有抽屉；不新增独立工作台。

**验收**：完整策略、缺失止损、矛盾条件、未支持指标、恶意提示词、超限文本、超时重试、旧分析迟到、重复点击挂载；同时验证键盘操作与空/加载/失败态。

### S03 · 一个策略接通 Demo 执行闭环

**代码落点**：`host/ai/chain.js`、`host/integration.js`；Service 计划/批准、执行、保护与持仓管理入口。

- 首先只允许一个已启用策略；开始轮次冻结策略版本与授权 generation。明确选择原生 AI 模式或挂载策略模式，无启用策略时不偷偷回退成自由 AI 交易。
- AI 理解后的策略仍进入现有确定性风控、租约、Outbox 和订单回查；不得另建下单接口。
- P1/P2 都核验策略是否允许该开仓意图；停用使旧 generation 的新开仓失效，已发出请求仍继续回查。
- 同一信号去重：包含 strategy_id/version、symbol、side 与触发周期/事件标识。保存执行意图，不能靠页面按钮防重。
- 成交后保存策略归属；已有仓位继续执行开仓版本的退出和保护规则，即使该策略已停用新开仓。停用与平仓明确分开。
- 拒绝其他策略随意接管；既有外部仓位保持原归属处理，不通过命名/启用策略自动认领。

**验收**：一条受支持规则在 Demo 完成入场—保护—退出；覆盖重复信号、部分成交/回查、停用在途轮次、编辑策略时已有仓位、Host/Service 重启恢复。不能仅凭 AI 返回“应买入”作为完成证据。

### S04 · 已授权集合中的 AI 选择

依赖 S03 完成，不并行开发复杂的组合引擎。

- 确定性预筛：仅已启用、数据齐全、适用标的与周期符合、未被去重/冷却的版本。
- 输入模型的是有限候选摘要与当前证据，不让它每轮重读全部长文。首版建议最多启用 5 个；成本与延时量测后再调整。
- 输出选择的 strategy_id/version 或不交易，并给一个主要理由；可使用用户明确的优先级解决平局。
- Service 再验证选择属于授权集合，不能仅信任模型返回的策略 ID。
- 账户预算和仓位上限共享，每轮最多一个新开仓意图；已有仓位管理优先，不能新策略把旧仓位反手。
- UI 展示本轮选用、跳过理由和结果；不把“被选择次数多”显示成策略质量评分，不自动淘汰亏损策略或改规则。

**验收**：两个候选冲突、无合适策略、返回未授权 ID、选择后被停用、选择期间用户改规则、已有仓位、行情过期；确保不越权和不重复执行。

## 6. 开发接口与兼容约束

- 浏览器只访问 Host，Host 路由统一经过 DSH 准入，Service 保留鉴权和业务授权。
- 策略 API 围绕列表/读取、草稿保存、AI 理解、提交回答、确认挂载、改名、启用/停用；具体路由在 P00 统一，避免先做两套名字。
- 交易实体新增字段兼容旧记录：旧轮次显示“原生 AI/未归因”，不补造策略身份；不能因升级重新执行旧信号。
- 每轮记录实际策略版本、模型路由、配置版本、证据时间、选择/阻断原因和订单标识。
- 行情缓存与策略调度均按当前账户/环境上下文隔离。行情刷新只影响展示，不触发策略重新下单。

## 7. 排期与交付

按一个执行开发流估算约 **8–12 个工作日**，是工程量预估，非承诺日期；外部连接恢复时间不包含在内。

| 顺序 | 切片 | 预估 | 交付物 |
|---|---|---|---|
| 1 | P00 + Q01 | 0.5–1 天 | 实际基线、契约、旧数据提示及刷新生命周期修复 |
| 2 | Q02 + Q03 | 1–2 天 | 轻量批量价格、页面更新、延时/请求量证据 |
| 3 | S01 | 1–1.5 天 | 策略/版本/授权存储、迁移及 API |
| 4 | S02 | 2–3 天 | 理解、澄清、确认、命名、挂载完整界面 |
| 5 | S03 | 2–3 天 | 单策略 Demo 开平仓/保护/恢复闭环 |
| 6 | S04 + 发布收尾 | 1–1.5 天 | 授权集合内选择、回归、实际加载验证 |

范围控制：第一版不做上传代码沙箱、策略市场、自动回测/调参、组合优化、多策略净额管理或新通知平台。WS 仅在 REST 实测不足时另评估。

## 8. 验证、发布与恢复

- 行情测试复用 `client/render-smoke.mjs`、`test/host-state.test.mjs`、Service 市场测试；补有意义的定时器/乱序/失联与轻量请求验证。
- 策略测试围绕存储状态机、澄清版本、执行授权、重复信号与持仓归属，分别放现有 Node/Python 测试入口，不为本需求建测试框架。
- 每个切片先跑相关测试，再跑受影响的整体检查；记录真实命令、计数与退出码，不强退、不跳过失败冒充通过。
- 行情和策略分开发布，避免一项阻塞另一项。发布记录 Git SHA、包版本、实际加载身份与迁移版本。
- 行情退回旧通道时保留“旧快照”提示；不能恢复成误报实时。策略故障可停用新开仓，保留已有仓位的保护/退出管理。
- 最终初步稳定观察至少 24 小时：无重复订单、无未提示的保护缺失、无身份串用、无静默停机，核对账户与订单事实；观察通过不等于盈利证明。

开发过程中只维护本计划的任务状态和一份连续实施记录，不为每个补丁再生成一套评审文档。
