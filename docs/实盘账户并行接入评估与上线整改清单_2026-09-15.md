## 1. 第一问：demo 与实盘能否并行运行

### 1.1 结论

**不能。** 系统当前是严格的**单租户**设计：一个进程、一个 `EXECUTION_MODE`、一个 Broker、一套未分区的运行状态。`live` 是可供切换的**互斥模式**，不是可与 demo 共存的分区。

需要注意：**数据层已经做了环境分区，运行层没有。** 这是好消息也是坏消息——好消息是改造不需要动 schema；坏消息是阻断点全在运行时，且都不在数据层。

### 1.2 三条硬阻断（附代码位置）

**阻断一：进程级单实例锁 —— 第二个进程会被直接拒绝启动**

```python
# src/core/service.py:85-86
self._instance_lock = InstanceLock(settings.project_root / "data" / "trading_service.lock")
self._instance_lock.acquire()
```

`InstanceLock.acquire()`（`src/core/instance_lock.py:84`）在锁被存活 PID 持有时抛
`RuntimeError("交易服务已在运行（PID=...）")`。注释已明确这是**资金安全约束而非便利功能**：两个进程会各自持有旧内存状态、在不同时间覆写基线与通道台账、并可能重复提交订单。这是设计意图，不是缺陷。

**阻断二：模式是全局单值环境变量 —— 一个进程只能产出一个 Broker**

```python
# src/exchange/factory.py:39
raw_mode = os.getenv(cfg.get("mode_env", "EXECUTION_MODE"), "").strip().lower()
```

`create_broker()` 每次调用只返回**一个** Broker，模式来源是单个 `EXECUTION_MODE`。
`config/settings.yaml:86-102` 的 `base_url_map` / `api_key_env_map` / `api_secret_env_map` 三张表是 `mode → 值` 的**单射**，没有「当前活跃模式集合」的概念。
`service.py:119` 只创建一次，随后注入图、Guardian、Outbox 全链路；`service.py:139-143` 把
`release_id`/`environment`/`account_ref` 作为**单值**写入 DB 上下文（`database.py:1062`）。

**阻断三：运行状态文件全部共享且未按环境命名**

`service.py` 中以下路径均为 `settings.project_root / "data" / ...` 硬编码，两个账户若共用一个进程（或共用一个 data 目录）会互相覆写：

| 状态 | 位置 | 后果 |
|---|---|---|
| 单实例锁 | `service.py:85` `data/trading_service.lock` | 第二进程无法启动 |
| 限流/418 冷却 | `service.py:97` `data/public_rate_limit_state.json` | 见 §1.4 的关键陷阱 |
| K 线缓存 | `service.py:98` `data/cache/klines` | 进程内模块级单例 |
| 资金基线 | `service.py:166` `data/capital_state.json` | 两账户权益口径混写 |
| 账户风险水位 | `service.py:181` `data/account_risk_state.json` | 日亏损/回撤水位混写 |
| 市场扫描池 | `service.py:188` `data/market_universe_state.json` | 轮转游标互相踩 |
| 通道台账 | `service.py:204` `data/channel_state.json` | 60/40 分配与通道熔断混写 |
| **全局控制状态** | `service.py:218` `data/control_state.json` | **最危险**：`close_only`/`emergency` 是全局的。实盘触发熔断会把 demo 一起停掉，反之亦然 |
| 发布清单 | `service.py:148` `data/release_manifest.json` | 单 `release_id`，无法按环境出候选批次 |
| 信号去重 | `service.py:327` `data/signal_scanner_state.json` | 触发去重跨账户互斥 |

托管层同样单例：`config/windows_service.json` 只有一组 `service_name: "MultiAgentTrader"` / `port: 8000` / `log_path`；`scripts/run_web.py:79-80` 默认 `127.0.0.1:8000`，且 `windows_service.py` 校验 `log_path` 必须位于项目内 `data/` 之下，天然排斥「同根目录、双实例」。

### 1.3 已具备的基础（改造之所以可行）

**数据层已经按环境和我户分区**，不需要动 schema：

| 表 | 约束 | 意义 |
|---|---|---|
| `order_outbox` | PK `(environment, business_key)`（`database.py:615`） | 幂等键已含环境 |
| `exchange_order_mirror` | PK `(environment, exchange_order_id)`（`:518`） | 订单镜像已分环境 |
| `protection_order_mirror` | PK `(environment, algo_id)`（`:642`） | 保护单镜像已分环境 |
| `position_lifecycles` | PK `(environment, account_ref, symbol, position_side)`（`:904`） | 持仓生命周期已分账户 |
| `execution_fills` | UNIQUE `(environment, account_ref, trade_id)`（`:867`） | 成交幂等已分账户 |
| `release_observations` | UNIQUE `(release_id, environment, account_ref, observed_minute)`（`:1035`） | 观察证据已分环境 |

更关键的是账户标识机制：

```python
# src/exchange/trade_reconciliation.py:66-69
def account_reference(api_key: str, environment: str) -> str:
    digest = hashlib.sha256(str(api_key).encode("utf-8")).hexdigest()[:16]
    return f"{str(environment or 'unknown').lower()}:{digest}"
```

**不同 API Key 自动映射到不同 `account_ref`**（`env:sha256(key)[:16]`），且不含凭据原文。这意味着换成实盘 Key 后，审计、成交归因、持仓生命周期、发布候选批次会自动按新账户隔离，**无需任何 schema 变更**。这是整件事最重要的现成能力。

同时 `live` 作为互斥模式已经打通：`factory.py:23` `VALID_MODES` 含 `live`；`factory.py:53-76` 按 mode 取密钥与域名；`factory.py:83-87` 缺密钥时**拒绝启动**而非静默回退；看板 `dashboard/app.py:2111-2125` 在切 live 前校验密钥存在。

### 1.4 三条路径对比

| | 方案 A：单进程串行切换 | 方案 B：双进程双账本（推荐） | 方案 C：单进程双租户 |
|---|---|---|---|
| 做法 | 保持一个进程，`EXECUTION_MODE` 在 demo↔live 间切换，一次只跑一个账户 | 同一份代码起两个进程，各自独立 data 根 / 锁 / DB / 端口 | 一个进程内持有两个 Broker，按租户分区全部状态与决策图 |
| 代码改动 | 0 | 中，约 1–2 人日 | 大，周级 |
| 触及资金主链路 | 否 | 否 | **是** |
| 对 demo 观察窗口的影响 | **每次切模式重启都会打断** | 无影响，两窗口独立 | 无影响 |
| 主要风险 | 切换重启期间仅靠交易所侧算法保护单托底；`control_state` 仍全局 | 同出口 IP 限流预算双花 → 418（见下） | 与当前 NO-GO 冻结范围冲突，且把两个账户的失败域耦合 |

**方案 B 的关键陷阱（务必不要做反）**

`configure_rate_limit_state()`（`service.py:97`）是**进程内模块级单例**，指向 `data/public_rate_limit_state.json`，该文件本身有跨进程文件锁。
如果给两个 profile 各配一份限流状态文件，两个进程会在**同一个出口 IP** 上各自记账，双花 Binance 的 `REQUEST_WEIGHT 2400/min` 与 `futures/data` 5 分钟额度，**几乎必然触发 418**——而这正是项目历史故障形态。

正确做法：**两个 profile 的限流/冷却状态文件必须指向同一个共享路径**，其余状态全部隔离。这是 B 方案唯一"不能隔离"的一项。

反向地说，隔离 `control_state.json`、`capital_state.json`、`channel_state.json` 是**必须**的：否则实盘熔断会连带停掉 demo。

### 1.5 若选方案 B：改造点清单

**P0（不做则无法并行）**

1. **单实例锁按 profile 命名** — `service.py:85` → `data/trading_service.<profile>.lock`。
2. **运行状态根目录按 profile 解析** — 引入 profile → data_root 映射，替换 `service.py` 中 10 处 `project_root / "data" / ...` 硬编码（§1.2 表格全部条目）。
3. **数据库按 profile 隔离** — `settings.yaml:paths.db_file` 每 profile 一份；`AuditDatabase` 的单值 `environment` 由各自进程设置，无需改 schema。
4. **限流状态共享（不可隔离）** — 两 profile 指向同一 `public_rate_limit_state.json`（§1.4）。
5. **端口与托管隔离** — 新增第二份 `config/windows_service*.json`（不同 `service_name` + `port`），或扩展 `windows_service.py` 支持多实例；`log_path` 校验需允许 profile 子目录。
6. **启动前先完成生产库迁移** — 见 §3.1，两 profile 若各自独立的库，各自都会自动迁移一次。

**P1**

7. `control_state` 隔离后，看板需明确标注"当前控制的是哪个账户"，避免误判。
8. **LLM 配额跨进程无协调** — `request_coordinator` 按 `base_url + 凭据` 共享，但只在本进程内生效。两进程共用同一 SENSENOVA Key 会突破 `max_concurrency: 1` 的设定，需要跨进程协调或接受降级。
9. **看板形态** — 一个控制台只连一个进程；需明确"两个控制台"或另做多账户聚合页。
10. `release_manifest` 每 profile 各一份，正好满足 L07「按环境 + 版本出候选批次」的要求。

**P2**

11. 日志、备份、告警各跑一套（`DatabaseBackupManager` 独立）。
12. `MTA_EGRESS_ID` — 两 profile 若共用出口，应在同一 `egress_id` 下合并限流证据。

### 3.5 同一脚本违反项目自己的 WAL 快照规则


```
窗口 since = 2026-09-15T15:12:01.824+00:00
窗口 until = 2026-09-15T16:05:18.926+00:00
观测条数   = 55
首行累计 418 = 11        末行累计 418 = 11        窗口内新增 418 = 0
门禁报出     = 65
```

**错因一：作用域错误。** `responses_by_status` 是限流器**自进程启动以来**的累计计数器，不是窗口内计数。原实现取 `max`，会把窗口开始前就已发生的限流算进当前候选。

**错因二：累加位置错误。** 原实现（`src/core/release_evidence.py:355-368`）：

```python
for row in observations:                 # 55 行
    limited_418 = max(limited_418, int(statuses.get("418", 0) or 0))   # = 11
    if rate.get("last_status") in {418, "418", ...}:
        limited_418 += 1                 # ← 写在循环体内，每行各加一次
```

`last_status` 是 sticky 值，一旦变成 418 就不会自动复原，因此 55 行各加 1：`11 + 55 = 66`。

**真实情况**：那 11 次 418 全部发生在 **15:01:27**，比窗口起点**早 11 分钟**（`last_limited_at = 1789484487.1246703`）。窗口内新增为 **0**。

**为什么这是上线阻断而不是小瑕疵**：只要会话内出现过一次 418，该门禁就恒为 FAIL，7 天观察窗口永远无法收口——GO 在结构上不可能达成。同时它让发布报告长期带着一个假 FAIL，掩盖了其余真实缺口。

**修复方式**（提交 `dcf22f7`）：按「累计计数器首尾差值」取窗口内新增数，并用绝对时间戳 `last_limited_at` 交叉校验，只采纳落在窗口起点之后的事件；进程重启导致计数器归零时用时间戳兜底补计一次。窗口外的最近一次限流时间以 `pre_window_limited_at` 保留在门禁明细中供排查，**不再参与判定**。

**这是语义收敛到门禁自己声明的 reason（"观察窗口内无 418/429"），不是放宽**：窗口内实际发生限流仍然判 FAIL。已用 7 项新断言锁住该口径，含反向用例。原 fixture 的 `responses_by_status` 为空，所以这条路径此前零覆盖。

> ⚠️ 附带事实：15:01:27 那次 418 是**真实发生的限流事件**，只是发生在窗口之前。它当前没有对应的 `risk_incidents` 记录。建议运营侧确认是否需要补记——门禁不再因为它 FAIL，但"发生过一次 418"这个事实本身应当留痕。

## 6. 建议执行顺序

关键是：**观察窗口一旦开启，就不能再改任何代码或配置**，否则会被判为新候选批次、窗口归零。

因此所有代码整改必须**在开窗口之前**完成。而方案 A 的每次切模式重启都会打断窗口——**若打算并行，必须在开窗口前就把方案 B 做完**。这两件事的时序是绑定的。

```
第 0 步  C-01 轮换并收紧实盘 Key（今天就能做）
          ↓
第 1 步  F-01 备份生产库 → 受控启动新代码 → 迁移 14→16 → 生成 manifest
          ↓
第 2 步  F-07 / F-08 审核未跟踪脚本、修 WAL 快照、门禁覆盖工作区
          F-03 13 个游离 smoke 归队
          ↓
第 3 步  【决策点】并行方案 A / B
          —— 若选 B，在此完成 §1.5 的 6 个 P0 改造点
          ↓
第 4 步  F-02 SCM 安装与受控启停；R-02 故障注入矩阵
          ↓
第 5 步  F-04 数据正确性（K 线对照 + 9 卡差分）
          ↓
第 6 步  ★ 冻结代码，开启 7 天观察窗口 ★
          F-05 网络门槛 / R-03 样本门槛 / F-06 AI 窗口并行积累
          ↓
第 7 步  report_release_readiness.py --strict → GO / NO-GO
          ↓
第 8 步  【单独决策】切换 EXECUTION_MODE=live
```
