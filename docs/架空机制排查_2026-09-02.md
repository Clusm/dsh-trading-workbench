## 二、残留的同类「架空」现象

### 1.【P1·建议尽快修】max_open_positions 只约束单轮批次，不约束总持仓数

- **现象**：risk.py:42-44 只检查 `len(decision.intents) > max_open_positions`（一次决策最多带几笔 intent），**从不统计当前已开仓位数**。提示词第 3 条"仓位数量不得超过 max_open_positions"对模型是纯软约束。
- **架空方式**：LLM 每轮只开 1 仓即可无限累积；strategy 通道开的仓位也完全不计入额度。分散度/集中度设计实际失效。
- **现有兜底**：只剩保证金帽（80% session equity + 通道 cap）——管得住总敞口，管不住仓位个数与相关性集中。
- **修法**：`evaluate_risk` 已接收 `portfolio` 参数（当前只用于通道额度），补一段：统计 portfolio 当前 open 仓位数（含 strategy 源），open intent 逐一校验「现有 N + 本批已通过的新增 ≤ max_open_positions」。

### 2.【P2】保护单同步存在双线程竞态

- **现象**：快循环 `sync_protections` 持 `_protection_lock`；但慢循环执行节点开仓/调参时直接调 `_place_protection`/`_adjust` → `_resync_protection`，**不持该锁**。两线程可同时操作同一 symbol 的 Algo 单（撤旧挂新交错）。
- **后果**：窗口小且能自愈（下一轮 `stop_total != 1` 触发清理重建），但会产生瞬时重复挂单、多余 critical 告警和流水噪声。
- **修法**：`_resync_protection` 内部加一把 broker 级 `RLock` 串行化（对整个保护单操作段加锁，而非各调用方自己加）。

### 3.【P2】review_lessons.json 只写不读

- **现象**：`lessons.build_review_library` 每次被查询都重写 JSON 快照（lessons.py:106-111），但代码消费路径只有 DB 查询——文件纯给人看，没有任何代码读回它。
- **后果**：本身无害，但它未被 `.gitignore` 排除，每次运行都污染 git status（就是反复出现的那个"运行时漂移文件"）。
- **修法**：加入 `.gitignore`；如需给人看，改为仅在复盘页渲染时按需生成。

## 三、方法论备注

本次核查的判据是：「某机制在提示词/配置/文档里宣称存在，但服务端没有对应强制点，且存在一条绕过路径」。此前两起已修复案例（全量平铺架空查询链路、SL/TP 硬编码 None 架空执行反馈）都属于此类；本轮新发现的 #1 是同构问题——**提示词里的行为约束若无风控强制点，就不能算机制**。
