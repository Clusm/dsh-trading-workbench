## 2. 根因逐条分析

### P0-1 · 策略信号通道 100% 失效（69 次）

**现象**：每轮 `signal_scanner_error: ModuleNotFoundError: No module named 'signals'`，`output_summary` 恒为 `{"tickets": [], "error": ...}`。

**定位**：`src/signal_engine/scanner.py:129-137`

```python
if not str(self.strategy_lab_src or "").strip() or not self.strategy_lab_src.exists():
    raise RuntimeError("strategy_lab 未配置或路径不存在，策略信号扫描跳过")   # ← 本该在这里退出
src = str(self.strategy_lab_src.resolve())
...
self._registry = importlib.import_module("signals").REGISTRY   # ← 实际撞在这里
```

**根因**：`config/settings.yaml:86` 配置为 `strategy_lab_src: ""`。
第 116 行 `self.strategy_lab_src = Path(strategy_lab_src)` 把 `""` 归一化为 `Path(".")`，于是：

| 表达式 | 实际值 | 守卫是否拦截 |
|---|---|---|
| `str(Path(""))` | `"."` | 非空 → 不拦截 |
| `Path(".").exists()` | `True` | 存在 → 不拦截 |

**空配置守卫被 `Path()` 的归一化行为绕过**，代码继续往下硬撞 `import signals`。

**证据**（实机复现）：
```
Path("") = WindowsPath('.') str='.' exists=True
guard would skip? False
```

**影响**：
- 策略通道（strategy_lab 选币/择时）**自启动以来零产出**，69 轮全空
- 当前所有交易决策**全部由 AI 通道单独产出**，双通道设计退化为单通道
- 每轮白扫一遍，日志噪声淹没真实告警

### P0-2 · Algo 撤单"成功"被误判为失败（38 次）★ 已实机复现

**现象**：`futures_adjust_error: XXX: 取消Algo单失败 RuntimeError Binance 200: success`

**定位**：`src/exchange/binance_futures.py:124-125`

```python
data = r.json()
if isinstance(data, dict) and data.get("code") and data.get("code") != 200:
    raise RuntimeError(f"Binance {data.get('code')}: {data.get('msg')}")
```

**根因**：币安 Algo 接口（`POST/DELETE /fapi/v1/algoOrder`）返回的 `code` 是**字符串 `"200"`**，而普通下单接口返回的是**整数**。代码用 `!= 200`（int）比较，`"200" != 200` 恒为 `True` → **每一次成功的撤单都被当成失败抛异常**。

**实机证据**（本次排查直接调用 DELETE 并打印原始响应）：
```
HTTP 200 body: {"algoId":1000000190786880,"clientAlgoId":"1c7dkgykxM1x2L7PaeAVUR","code":"200","msg":"success"}
code 值 = '200'   类型 = str
现有判据 `code and code != 200` -> True  => 会被误判为失败并抛 RuntimeError
撤单后 ARBUSDT algoId=1000000190786880 仍在交易所: False   （撤单实际成功）
```

**后果链**（这是本条最严重的部分）：

1. `_cancel_symbol_algos()` 抛异常 → `except` 分支直接 `continue`，**不执行 `db.cancel_order_by_exchange_id()`**
2. 本地 `orders` 表中对应保护单**永远停留在 `NEW`**，无法收口
   → 实测：**`orders` 表 56 条永 NEW 的幽灵单**（CANCELED 74 / NEW 56 / FILLED 41）
3. `futures_adjust_error` 每轮重复写入 38 条噪声
4. 上一版为此专门写了 `scripts/cleanup_ghost_orders.py` + `cleanup_orphan_algo_orders.py` 清理 —— **治标不治本，清理完还会再长**

### P0-3 · 决策链每轮执行两遍（adjust 意图重复下单）

**现象**：每一条 `futures_adjust` 都成对出现，两条内容完全相同、相隔约 1.5 秒：

```
06:58:44 info futures_adjust | ARBUSDT 已自动调整止损/止盈：SL=0.131, TP=0.1385
06:58:45 info futures_adjust | ARBUSDT 已自动调整止损/止盈：SL=0.131, TP=0.1385
```

**定位**：`src/core/graph.py:500-506` 图拓扑

```
signal_scanner ──┬─→ strategy_trader ─────────────┐
                 └─→ strategy → ai_trader ────────┴→ merge → risk → execution
```

`merge` 有两个上游分支，LangGraph 在**每个上游完成时各触发一次** `merge`。两次触发都向下游传播，于是 `risk` 和 `execution` 每轮各跑两遍。

**证据**：
- `agent_runs` 计数：本轮启动以来 `signal_scanner` **69** 次，而 `ai_trader` / `risk_agent` / `execution_agent` 各 **134** 次 ≈ 2 × 69
- 两次 execution 的 `input_summary` 中 `client_order_id` **完全相同**：
  ```
  06:58:44.103  IN: {..."client_order_id":"mta-9ddd263afac9451ea1465b65-0",...}
  06:58:45.565  IN: {..."client_order_id":"mta-9ddd263afac9451ea1465b65-0",...}
  ```

**为什么没有重复开仓**：`execute()`（`binance_futures.py:483-493`）有 `duplicate_skipped` 守卫，按 `client_order_id` 查 `orders` 表去重 —— **但 `open` 意图会落库带该 cid 的 order 行，`adjust` 意图不会**（`_place_algo_protection` 内部生成全新的 `mta-sl-<uuid>`）。

**所以**：
| 意图类型 | 去重是否生效 | 结果 |
|---|---|---|
| `open` | ✅ 生效 | 未重复开仓（万幸） |
| `adjust` | ❌ **失效** | 每轮撤旧挂新两遍 |

**风险评级**：这是**最危险的一条**。当前只重复"撤旧挂新"保护单，看起来无害；但同一个缺陷对 `open` 意图的防护完全依赖"落库时机"——一旦 `_open()` 落库路径有任何延迟或失败，**重复开仓会直接发生**。实盘放量后这是资金事故级隐患。

### P0-4 · 权益基线兜底错误 → 风控量纲失真

**现象**：
```
snapshot_rejected | 权益快照异常已丢弃：本次 equity=5016.71，上一条 520.67，跳变 864% 超过 60% 阈值
snapshot_rejected | 本次 equity=-4493.59，上一条 501.74，跳变 996%
equity_unavailable | 币安账户权益接口暂时不可用，本轮跳过破产检查和保证金全平检查。最近有效权益=0.00
```

**定位 A**：`src/core/capital.py:58-68`（基线初始化）
```python
baseline = 0.0            # ← 接口不可用时的兜底
...
baseline = exchange_eq - self.initial_equity
...
self._save(baseline)      # ← 把 0.0 落盘了
```
进程在账户接口 502 期间启动（本轮启动后第一个小时 62 次 ProxyError 502）→ `baseline = 0.0` 被持久化 → 接口恢复后 `session_equity = 交易所总权益 5016 - 0 = 5016`，而正确值应为 `5016 - 4516 ≈ 500`。**量纲放大 10 倍**。

**定位 B**：`src/core/capital.py:144`（保护被绕过）
```python
# session_equity() 有 <=0 的兜底保护：
def session_equity(self):
    eq = self._exchange_equity()
    if eq <= 0:
        return round(self.initial_equity, 2)     # ← 有保护
    return round(eq - self.baseline, 2)

# 但 sync() 直接算，绕过了保护：
session_eq = round(exchange_eq - self.baseline, 2)   # ← L144，无保护 → -4493.59
```

**定位 C**：`src/core/capital.py:139-143`（风控被跳过）
```python
details=f"...本轮跳过破产检查和保证金全平检查。最近有效权益={exchange_eq:.2f}",
action_taken="skip capital checks; block new opens"
```
**6 轮**在接口不可用期间，破产检查与保证金全平检查被完全跳过。

**影响**：会话权益是所有资金约束（通道保证金上限、破产熔断、仓位规模）的**唯一基准**。基准失真 10 倍 = **所有风控额度同步失真**。当前未出事是因为 `block new opens` 同时生效；一旦该保护被移除就会放大。

### P1-5 · 网络层：代理 502 + 签名失效 + 客户端并发竞态（62 次）

| 子类型 | 次数 | 根因 |
|---|---:|---|
| `ProxyError 502 Bad Gateway` | 59 | 出口代理不稳定（集中在启动后 00:08–01:34） |
| `Binance -1022: Signature not valid` | 2 | 疑似代理改写请求 / 客户端被并发关闭导致半包 |
| `Cannot send a request, as the client has been closed` | 1 | **并发竞态** |

**并发竞态定位**：`src/exchange/binance_futures.py:129-136`
```python
if "10054" in msg or isinstance(e, (httpx.ConnectError, httpx.ConnectTimeout)):
    self._client.close()                                  # ← 线程 A 关闭
    self._client = httpx.Client(timeout=self._client_timeout)   # ← 重新赋值
```
`self._client` **无任何锁保护**。快循环（30s）与慢循环（10-15min）跨线程共用同一个 broker：线程 A 正在发请求时，线程 B 触发 10054 恢复逻辑关闭并替换 client → 线程 A 拿到已关闭的 client → `client has been closed`，或请求体被截断 → 服务端签名校验失败 `-1022`。

**附带缺陷**：`binance_futures.py:77-92` 注释承诺"校准失败（离线）时退回 0 并**放宽 recvWindow** 兼容小漂移"，但**代码里 `recvWindow` 恒为 5000，从未放宽**。注释与实现不一致。

**环境澄清（重要）**：本次排查过程中发现两个代理进程并存：

| 端口 | 进程 | 可用性 |
|---|---|---|
| `10808` | `sing-box.exe` | ✅ 可连通币安 |
| `54312` | `sandbox-cli.exe` | ❌ 502，不能转发币安 |

`.env` 配置的是 `10808`（正确）。主服务入口 `scripts/run_web.py:29` 与 `scripts/run_web_service.py:26` 都强制接管了代理（`apply_proxy_env()` / 硬编码），**主链路是安全的**。但这暴露两个隐患：
- `run_web_service.py` 硬编码 `10808`，与 `.env` 存在**配置漂移**风险（换机/换端口时两处需同步改）
- 诊断类脚本（含我这次写的探针）若未调用 `apply_proxy_env()`，会静默走坏代理 → 误判为"系统故障"

### P0-6 · 孤儿 Algo 保护单：结构性盲区（实时存在 6 个）

**现象**：`sync_protections()` 只遍历 `self.positions()` 的 symbol。仓位在交易所被外部平掉（或由成交流水补记）后，**该 symbol 的残留 Algo 单永远不会被扫到**。

**实机核对结果**（本次排查直连交易所）：

```
持仓 4 个: ARBUSDT / DOGEUSDT / ETHUSDT / SUIUSDT
Algo 单 14 个，覆盖 10 个 symbol

=== 孤儿保护单：有 Algo 单但已无持仓 ===
  XRPUSDT    TAKE_PROFIT_MARKET  trigger=1.375   qty=500.0     ← 仓位 05:29 已平，残留 ~2h
  UNIUSDT    STOP_MARKET         trigger=6.48    qty=10.0      ← 09-02 18:13 已平，残留 ~13h
  ZECUSDT    TAKE_PROFIT_MARKET  trigger=880.0   qty=0.12      ← 09-01 11:41 已平，残留 ~1.9 天
  ENAUSDT    TAKE_PROFIT_MARKET  trigger=0.1455  qty=850.0     ← 库中无成交记录
  MAGMAUSDT  TAKE_PROFIT_MARKET  trigger=0.31    qty=230.0     ← 库中无成交记录
  ZKPUSDT    TAKE_PROFIT_MARKET  trigger=0.0625  qty=1700.0    ← 库中无成交记录

=== 持仓保护完整性 ===  （4/4 全部 SL+TP 齐全，无裸仓）
```

**风险评估**：这些单均带 `reduceOnly=true`，无持仓时不会成交 → **当前无直接资金损失**。但：
1. 长期占用 Algo 单额度，随运行时间**单调累积**（已积累到 6 个 symbol）
2. 一旦对应 symbol 重新开仓，`_resync_protection_impl` 会读到**过期价格的旧单**（如 ZEC 880、ZKP 0.0625），误判"保护已存在"而跳过重挂 → **新仓位可能带着错误的止损位存活**
3. `futures_protection_fallback`（critical）正是同类问题的告警形态

**注**：`scripts/cleanup_orphan_algo_orders.py` 已存在但是**一次性手工脚本**，未纳入常态调度。

### P2-8 · Broker 频繁重建（19 次）

`create_broker()` 每次都执行 `_load_exchange_info()`（全量交易规则）+ `_calibrate_time()`。19 次重建 = 19 次全量拉取，无健康度复用/退避机制。

## 5. 复盘：本轮暴露的系统性模式

8 个根因里有 5 个（P0-1 / P0-2 / P0-3b / P0-4a / P0-6）属于同一类缺陷模式：

> **降级路径与正常路径的语义/量纲不一致，且降级路径缺少等价的守卫。**

| 根因 | 正常路径 | 降级路径 | 断裂点 |
|---|---|---|---|
| P0-1 | 路径存在 → import | 路径为空 → 应提前退出 | `Path("")` 归一化为 `.`，守卫失效 |
| P0-2 | 普通下单 `code`=int | Algo 接口 `code`=str | 类型假设不一致，成功被判失败 |
| P0-3b | open 落库带 cid → 可去重 | adjust 落库不带 cid → 不可去重 | 幂等机制覆盖不全 |
| P0-4a | 接口可用 → 算真实基线 | 接口不可用 → `baseline=0.0` 落盘 | 兜底值量纲错误且被持久化 |
| P0-6 | 有持仓 → 扫得到 | 已平仓 → 扫不到 | 扫描集合随状态收缩，盲区单调扩大 |

**建议的通用防线**：为所有降级路径建立"降级契约"三件套 —— ①统一的量纲/类型约定；②降级时写 `critical` 事件而非 `warn`；③降级状态必须可被后续轮次自动纠正（不得落盘持久化错误的兜底值）。
