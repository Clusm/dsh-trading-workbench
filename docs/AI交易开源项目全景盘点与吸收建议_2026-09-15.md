# AI 交易开源项目全景盘点与吸收建议

本文面向仅交易币安 USD-M 永续合约的 `multi-agent-trader`。调研范围覆盖成熟交易引擎、
数字货币机器人、AI/LLM Agent、机器学习与强化学习框架、量化研究工具、交易所 SDK 和
市场数据基础设施。信息核验截止 2026 年 9 月 15 日，优先采用项目官方仓库、官方文档与
原始论文；“可利用”指吸收架构、测试方法或独立研究工具，不等于复制代码或采用外部收益
结论。

> **2026-09-15源码复核勘误**：本文是外部项目研究资料，其中原始实施建议并非全部准确。
> 最后一轮开发与上线门槛以[《上线前最后一轮优化工作计划》](上线前最后一轮优化工作计划_2026-09-15.md)
> 为准。该计划基于本地`25825b3`核对了实际实现，区分已有能力、确定缺陷和后续研究项。

## 1. 执行摘要

最重要的结论不是更换现有系统，而是把成熟项目已经证明有效的工程纪律补到现有链路中：

1. **交易执行必须与 AI 解耦。** NOFX 将原则概括为“模型提议、运行时裁决”：模型给出
   方向与论点，代码独立限制标的、仓位、杠杆、频率并部署交易所侧保护。[^1] 这与本项目
   的 `DecisionPipeline → RiskGuard → Outbox → Binance` 方向一致，应继续强化而不是让
   LLM 获得 Broker 工具直连权。
2. **实盘安全的核心是状态一致性。** NautilusTrader 把启动恢复、交易所对账、外部订单、
   不确定命令结果和持续对账列为 live 与 backtest 的关键差异。[^2] 本项目已有 Account/
   Order/Protection Mirror 和 UNKNOWN 协议，下一步应补齐统一交易域事件、启动栅栏和
   可证明的连续对账不变量。
3. **策略研究必须先证伪，再优化。** Freqtrade 提供前视偏差与递归指标偏差检查；Jesse
   用随机入场分布做规则显著性检验，再做完整回测和 Monte Carlo。[^3][^4][^5] 这比继续
   扩充策略数量更有价值，尤其适合处理“扫描少”“连续逆势做多”和“历史表现是否只是
   巧合”这类问题。
4. **模型输出必须有新颖性、时效和分布外状态。** FreqAI 会标识模型过期、输入异常和
   与训练空间的距离，并让陈旧模型停止产生可交易预测。[^6][^7] 本项目的 LLM 证据时效
   已较完整，但还应增加“本轮输入是否异常/超出已验证分布”的独立状态。
5. **研究与实盘必须使用同一个决策契约，但不能共用权限。** FinRL-X 使用单一目标权重
   契约贯穿研究、风险叠加和执行；Hummingbot 将 Controller 的意图与 Executor 的持仓
   生命周期分离。[^8][^9] 对本项目而言，更合适的契约不是目标权重，而是现有结构化
   `Intent + ActionSpace + PipelineAuthorization`，但必须真正成为唯一入口和唯一标的来源。
6. **LLM 多 Agent 更适合产生可审计观点，不适合直接成为风控。** TradingAgents 的多角色
   讨论、结构化输出、检查点恢复和持久决策日志值得借鉴，但官方明确定位为研究框架，
   交易结果受模型和数据等非确定因素影响。[^10] 风险、精度、幂等、保护和账户状态必须
   留在确定性代码层。
7. **当前项目不应在上线前引入新框架依赖或重写执行层。** 最短安全路径是修复 20 币种
   运行时白名单、建立生产网络出口验收、治理 LLM 429，再继续累计 30 笔可归因 Demo
   闭合交易。大型框架迁移会增加新的账户语义、状态迁移和许可证风险，不能解决眼前阻断。

NautilusTrader 的 live 文档明确指出，网络失败可能让命令结果处于未知状态，且交易所外部
活动与内部持久化会破坏模拟环境中的简单假设；启动时应先恢复缓存和交易所状态，再启动
策略，运行中继续核对在途订单、挂单和仓位。[^2][^11] 这与本项目已经实现的 Outbox 和
Mirror 高度同构。可利用的下一步不是替换 Broker，而是将现有多个镜像的状态变化统一为
稳定域事件，并建立“对账未完成时新开仓必为 0”的系统不变量。

Hummingbot V2 的 Controller 读取 MarketDataProvider 后只产生 ExecutorAction；Executor
负责下单、刷新、撤单和结束，PositionExecutor 用止盈、止损、时间限制和追踪止损管理
完整仓位生命周期。[^9][^12] 本项目的 AI/策略通道相当于 Controller，Outbox 与 Guardian
相当于 Executor 的一部分。可以增加稳定 `position_lifecycle_id`，把开仓、保护、复核、
退出和 outcome 串为一个有限生命周期，但不应照搬 Hummingbot 的默认杠杆或障碍参数。

### 2.2 AI、机器学习与强化学习

| [FinRobot](https://github.com/AI4Finance-Foundation/FinRobot) | 多 Agent 金融分析、LLMOps/DataOps、调度 | Agent 注册、能力路由、任务经理、模型按任务选择 | 偏股票基本面和报告生成，不是生产 OMS[^32] |

| [FinRL/FinRL-Crypto](https://github.com/AI4Finance-Foundation/FinRL) | PPO/SAC/TD3 等 DRL 与 Gym 环境 | 状态/动作/奖励基准和算法对照 | 官方已将原 FinRL 定位为教育与研究，生产方向转向 FinRL-X[^13] |
| [Qlib](https://github.com/microsoft/qlib) | 数据、训练、预测、组合、执行的量化工作流 | 数据处理器、实验记录、模型与策略解耦、嵌套 Executor | 原生数据和范例偏股票；接入成本较高[^29] |
| [FreqAI](https://github.com/freqtrade/freqtrade/blob/develop/docs/freqai.md) | 每交易对自适应监督学习/RL | 后台重训、模型 ID/恢复、过期拒绝、异常样本拒绝、训练和推理元数据 | 连续学习仍被官方标注为实验性并有过拟合风险[^7] |

TensorTrade 官方实验给出了一个重要反例：BTC/USD PPO 在零手续费下盈利，但加入 0.1%
手续费后转亏，主要问题是过度交易。[^14] 这说明任何 AI 策略的奖励必须基于**净收益**，
同时惩罚换手、滑点、资金费和尾部回撤；只优化方向准确率、毛收益或单次成功率会系统性
产生错误激励。当前项目已在 USD-M Replay 纳入费用和滑点，下一步可增加“候选产生但因
成本后优势不足而跳过”的独立归因，而不是直接引入 PPO。

FreqAI 的 `do_predict`/Dissimilarity Index 思路尤其适合本项目：如果输入距离训练样本过远、
被异常检测器识别或模型已经过期，就不应把预测当作正常信号。[^6] 对 LLM 决策可等价实现
一个确定性的 `evidence_novelty` 检查：异常波动、历史极端 funding/OI、盘口缺失、价格断层
或当前 regime 不在策略验证集合时，状态为 `OUT_OF_DISTRIBUTION`，默认只允许 no-trade/
存量管理。它是决策质量检查，不改变风险档。

| [CloddsBot](https://github.com/alsk1992/CloddsBot) | 多市场 Agent、统一风险引擎、交易审计、语义记忆、鲸鱼追踪和工具/技能注册 | 118+ 策略横跨预测市场、Solana、现货和多交易所合约；大多数不适配单一 Binance USD-M 边界 | **吸收工具编排与审计，不吸收策略数量和风险参数** |

| [AutoHedge](https://github.com/The-Swarm-Corporation/AutoHedge) | Director→Quant→Risk→Execution 的结构化流水线、JSON 输出和日志 | “enterprise-grade”是项目自述；当前主要支持 Solana，缺少本项目所需 USD-M 证据 | **概念参考，成熟度不足** |
| [FinAgent](https://github.com/effective-p/FinAgent) | 市场情报、低层/高层反思、记忆检索分离 | 面向股票/新闻/图像的研究回测，不具备本项目实盘基础设施 | **可研究记忆，不接执行** |

NOFX 的硬边界与本项目最接近：模型可以自由形成观点，但标的、名义仓位、杠杆、同币种
唯一仓位、重入冷却、每周期/每小时开仓数都由模型不可修改的代码强制；连续模型失败后
阻止新开仓，已有仓位仍有交易所侧保护。[^1] 本项目已有其中多数能力，但当前“配置锁定
20 币种、运行时 AI 池却可能扩展”的问题说明边界尚未做到端到端。应把 `core_symbols`
写入签名授权材料并由 Broker 再验证，而不只是验证配置哈希。

Vibe-Trading 值得关注的是把 paper/live 作为 Broker 连接属性和结构性运行时校验，而不是
让 Agent 可修改的普通配置开关；其近期版本还加入了 mandate、订单守卫、审计账本、即时
停止、依赖哈希锁和生成策略 AST 沙箱。[^16][^17] 同时其公开问题也展示了自动生成代码的
典型风险：生成模板与沙箱规则可能互相矛盾，或者子进程继承生产密钥和网络权限。[^18][^19]
因此本项目如未来引入 AI 自动策略开发，只能在无 Broker 凭据、无生产网络、独立数据副本
的研究进程中运行，产物经过人工审查和固定回放后才能进入 shadow。

CloddsBot 官方把 118+ 策略、121 个技能、多交易所合约、预测市场、链上交易、鲸鱼追踪和
语义记忆汇集在同一终端。[^36] 这证明“Agent 工具注册表 + 延迟加载 + 审计账本”的产品形态
可行，但也说明策略/技能计数不能等同于独立 alpha：其中大量能力是平台连接、运维工具、
市场适配或相似模板。此前对固定源码版本的本地复核已经识别出动量、均值回归、套利、
价格/成交量阈值、做市和 DCA 等主要算法族；与现有策略卡重叠的只做证据增强或 Challenger，
Polymarket、Solana、跨所套利和无限 DCA 类能力继续排除。

### 2.4 研究、数据与连接基础设施

| 项目 | 用途 | 对本项目的判断 |
|---|---|---|
| [vectorbt](https://github.com/polakowo/vectorbt) | 向量化批量策略/参数研究、组合统计和可视化 | 可作为离线快速筛选工具；最终结论仍须进入 USD-M 事件回放验证 |
| [CCXT](https://github.com/ccxt/ccxt) | 多交易所统一接口、精度/限额、内建漏桶限速 | 限速与精度处理值得做差分测试；不应在上线前替换专用 Binance Broker |
| [OpenBB](https://github.com/OpenBB-finance/OpenBB) | 多数据源统一 Python/REST/MCP 接口 | 宏观/研究 sidecar 可参考 provider registry；加密执行链不需要引入 |
| [Binance Python Modular SDK](https://github.com/binance/binance-connector-python) | 官方 USD-M REST、WebSocket API 和 Stream 客户端 | 用作协议/响应差分测试和升级预警，不直接替换已加固 Transport[^34] |
| [Binance Public Data](https://github.com/binance/binance-public-data) | 日/月级 USD-M klines、aggTrades、trades 与校验文件 | 应作为可复现历史数据基线，减少回测时实时 REST 压力[^35] |

CCXT 使用按端点 cost 调整的漏桶或滚动窗口限速，并明确同一交易所实例应复用内建限速器；
但它也指出交易所还存在端点、账户和突发限制，单一 `rateLimit` 不能完整表达。[^20] Binance
官方说明 429 后必须退避，持续违规会触发基于 IP 的 418，封禁可逐步延长，`Retry-After`
给出等待时间。[^21] 因此本项目当前的统一网关、请求权重、跨进程预算和持久冷却方向正确，
但**共享代理出口信誉**不是软件重试可以解决的问题；生产应使用稳定独立出口，并把生产
只读 API 的持续成功率纳入 live readiness。

Binance 官方还建议在高波动时优先用用户数据 WebSocket 获取订单和仓位状态，单连接会在
24 小时到期并需要处理 ping/pong 与重连。[^22] 当前系统已采用私有流加 REST 对账，后续应
加入“计划性 24 小时轮换”和重连前后序列缺口指标，而不是依赖异常断线后才恢复。

vectorbt 适合用矩阵化方式快速探索大量参数组合，Jesse 适合检验单个规则是否优于随机，
现有 USD-M Replay 适合验证币安成交语义。三者可形成漏斗：

`大规模假设筛选 → 规则显著性/偏差检测 → USD-M 事件回放 → Demo shadow → 单规则审批`

不能将 vectorbt 或任何 K 线级引擎的漂亮结果直接作为实盘晋级证据，因为 K 线无法确定
盘中价格顺序、价差、深度和队列位置。NautilusTrader 同样明确建议，依赖精确成交的策略
必须从 bar 验证升级到 quote/trade/depth 数据。[^23]

### 2.5 历史项目与退役风险

| 项目 | 历史价值 | 当前判断 |
|---|---|---|
| [Gekko](https://github.com/askmike/gekko) | 早期加密 TA、回测、交易所插件和 Broker 抽象 | 仓库于 2020 年归档且维护者明确停止维护；仅作架构史料[^37] |
| [Zenbot](https://github.com/DeviaVir/zenbot) | CLI、paper trading、策略/交易所插件与模拟器 | 仓库于 2022 年归档并警告不再积极维护；不能进入依赖链[^38] |
| [Catalyst](https://github.com/scrtlabs/catalyst) | 流式回测、滑点/成本/延迟和 backtest/live 接口一致 | 自 2018 年末停止积极维护，仓库于 2022 年归档；只保留事件流思想[^39] |
| [backtrader](https://github.com/mementum/backtrader) | 丰富订单模拟、佣金、滑点、future-like cash adjustment 和指标生态 | 通用回测参考，不具备本项目的 Binance USD-M 与 AI 运行时语义；不新增生产依赖[^40] |

这组项目给出的教训是：历史知名度、Star 数和策略数量都不能替代维护活性、安全更新、
交易所语义覆盖与可复现实验。候选依赖进入生产前应增加四项准入检查：最近维护状态、
许可证、已知安全问题、目标交易所协议覆盖；任一项不满足，只能作为阅读材料或隔离工具。

## 3. 可迁移经验与当前系统映射

| 外部成熟经验 | 当前已有基础 | 仍存在的差距 | 推荐动作 |
|---|---|---|---|
| 模型提议、硬代码裁决 | DecisionPipeline、RiskGuard、运行时签名、Outbox | 交易标的存在多数据源，20 币配置未形成最终执行不变量 | `core_symbols` 单一来源，并进入授权签名与 Broker 二次校验 |
| 启动前恢复与持续对账 | Account/Order/Protection Mirror、UNKNOWN | 多镜像缺少统一域事件和总状态栅栏 | 建立 `ReconciliationBarrier` 与统一 health reason code |
| Controller/Executor 分离 | 双通道 Intent、Guardian、Outbox | 仓位生命周期跨表追踪，部分状态靠关联查询 | 增加稳定 lifecycle_id 与状态迁移日志 |
| 三重障碍持仓管理 | 开仓 SL/TP、Guardian invalidation | 时间障碍尚未作为统一、可评估的策略字段 | 先新增 shadow `max_holding/expiry`，不改风险档和真实退出 |
| 前视/递归偏差检查 | 闭合 K 线、未来数据 fail-closed 回放 | 尚无对所有策略卡的自动差分扫描 | 新增 `strategy_bias_check` 离线门禁 |
| 入场规则显著性测试 | 200 候选、30 闭合、走步/bootstrap | 候选数量不等于规则有边际预测力 | 每张策略卡按 symbol/regime/horizon 对随机基线检验 |
| 模型过期与 OOD 拒绝 | evidence_at、age/completeness | 有数据新鲜度，无“输入超出验证分布”状态 | 加 `evidence_novelty`，先 shadow 后独立审批 |
| 正反研究员/反证 | 支持证据、反证、evidence_conflict | 多 Agent 重复调用可能放大 429 与相关错误 | 单模型结构化双栏论证优先，不盲目增加 Agent 数 |
| 模型检查点和恢复 | Agent recorder、审计 DB | LLM 429 后整轮重算，调用可用率偏低 | 决策阶段 checkpoint、请求 single-flight、总预算和断路器 |
| 研究/部署同一契约 | USD-M Replay、Intent/Pipeline | 研究工具产物尚无统一导入清单 | 定义 versioned candidate manifest，不允许研究代码直接导入生产 |

| Agent 工具最小权限 | 行情 Function Calling、Broker 无直接工具 | 未来自动策略开发可能继承 `.env` | 研究 worker 无生产密钥、默认断网、只读数据卷、产物签名 |

## 4. 对当前上线工作的直接建议

### 4.1 上线前必须完成

#### A. 运行时白名单不变量

目标不是再增加一层提示词，而是让以下集合在运行时严格相等：

`配置锁 core_symbols = MarketData 订阅 = Scanner 范围 = AI ActionSpace = RiskGuard 支持范围 = Broker 开仓范围`

实施要点：

- 删除 AI 独立硬编码币种池；异常币种只能在 20 币集合内重排，不能追加集合外标的。
- Broker 开仓校验同时验证 symbol 属于锁定集合和授权签名；交易所全量 filters 只用于精度，
  不能定义业务支持范围。
- `/api/ready` 显示上述六个集合的哈希和差异；任一差异即不允许新开仓。
- 加一条端到端测试：对集合外 `BCHUSDT/TONUSDT/APTUSDT` 的 Agent、Scanner、Web/API
  和 Broker 旁路请求全部拒绝，但集合内退出、保护和对账正常。

这直接借鉴 NOFX 的“模型不能覆盖硬限制”和 Vibe-Trading 的结构性 Broker 边界，不改变
风险档、杠杆或白名单内容。

#### B. 生产网络与 418 readiness

- 配置独立、稳定、地区合规的生产出口；共享代理不作为实盘依赖。
- readiness 必须分别显示 Demo 与生产 `fapi.binance.com` 的只读探针结果，不能用 Demo
  HTTP 200 证明 live 可达。
- 生产探针只调用低权重公开接口，遵守本地预算，不发送签名、不探测下单。
- 验收为至少 24 小时无 418/429、DNS 解析稳定、WebSocket 至少一次计划轮换成功；如果
  出口变化，观察窗口重新计时。
- 429/418 继续严格遵守 `Retry-After`，不得通过多进程、换 API key 或高频重启绕过。

#### C. LLM 调用准入控制

- 保持决策 Agent 最高推理档，不通过降推理换稳定性。
- 同一慢周期只允许一个 AI 决策在途；重复触发复用同一 Future/结果。
- 按“行情摘要→仓位评述→最终决策”保存 checkpoint，429 后只重试失败阶段。
- 对 429、超时、无效 JSON 分别设置有界退避；总时限到达后 fail-closed 为 no-trade，
  Guardian、保护单和对账继续。
- 独立记录 provider availability 的 1h/6h/24h 窗口，避免累计 70% 指标掩盖近期恢复。
- 上线门槛建议为连续 24 小时无 provider 429、每轮无并发重复调用、决策延迟 P95 小于
  慢循环间隔的 50%。

### 4.2 上线后第一个迭代

#### D. 策略证伪流水线

按照 Freqtrade、Jesse 和现有 J 阶段形成四道离线门禁：

1. `lookahead`: 删除某一未来区段后，历史信号和指标不得改变。
2. `recursive`: 使用不同 warm-up 长度，最后闭合 bar 指标差异不得超过预声明容差。
3. `random baseline`: 新入场规则与同市场、同频率随机入场比较；报告 p-value、样本数和
   观测均值，不把单一 p-value 当收益保证。
4. `USD-M replay`: 通过费用、资金费、滑点、部分成交和延迟模型后，才进入 Demo shadow。

Jesse 的公开 issue 也说明研究工具本身可能有统计实现缺陷，例如交易顺序 Monte Carlo
如果用绝对 PnL 重建权益，会产生不合理回撤。[^24] 因此本项目应独立实现小而可验证的
统计函数，固定合成样本和手算基线，不直接把第三方报告当真值。

#### E. 候选与策略卡的 Champion/Challenger

- 现有 9 张策略卡保持生产 Champion；任何外部思想都作为 versioned Challenger。
- Challenger 只能输出 shadow candidate，不能改风险参数、资金分配或真实订单。
- 每次变更固定数据窗口、成本假设、原因码、策略版本和代码 commit。
- 晋级同时看事故覆盖、机会成本、净 Profit Factor、最大回撤、数据覆盖和稳定性；继续
  保持当前 200 候选、30 闭合 Demo、7 天门槛，不能用批量生成模拟交易填充 30 笔。

#### F. LLM 记忆由“全文历史”改为分层证据

借鉴 FinMem，但不让模型自由改写事实：

- **短期层**：本轮行情、仓位、订单和数据质量，严格 TTL。
- **中期层**：同策略/方向/regime 最近结果与失效原因，来自结构化 outcome。
- **长期层**：已审批策略规则、事故教训和不可变风险边界，只读版本化。
- 检索必须返回 `source_id/evidence_at/version`；模型生成的总结不能覆盖原记录。
- 记忆只影响解释和候选排序，不能越过 ActionSpace、RiskGuard 或白名单。

### 4.3 中期研究路线

#### G. 独立 Alpha Lab

可以组合 Qlib/vectorbt/Jesse 的方法，并参考 RD-Agent 的自动研究工作流，但保持物理隔离：[^30]

- 独立 Python 环境、独立数据库和只读历史数据副本；不加载 `.env.local` 或 Binance 私钥。
- LLM/RD-Agent 只负责生成假设、因子表达式和测试计划；代码执行在无网沙箱。
- 输出唯一允许的产物是 `candidate_manifest.json`、源码 diff、回测报告和数据覆盖清单。
- 生产仓库由人工审查后重新实现，运行离线回归并从 shadow 开始。

#### H. 监督学习优先于 RL

在现有样本规模下，不建议直接部署 RL。更可行的第一步是训练一个只做过滤/排序的轻量
监督模型：输入现有结构化趋势、波动、funding/OI、盘口和策略标签，输出“候选后续净收益
为正的校准概率”。它不决定方向、不定杠杆、不直接下单。

启用前必须满足：

- 样本按时间走步，训练/校准/样本外完全隔离；
- 模型版本、特征顺序、Scaler、训练截止时间和输入分布摘要持久化；
- 预测过期或 OOD 时自动退回现有规则链；
- 与无模型基线比较净收益和机会成本；
- 初始 execution_weight 为 0，单独审批后才能用于候选排序。

RL 只在拥有更长的逐笔/盘口数据、可信成交模型和足够多独立市场阶段后再研究。TensorTrade
的成本实验和 FreqAI 对连续学习的谨慎提示都说明，能在模拟器中学到行为不等于能在真实
市场产生净优势。[^7][^14]

## 5. 明确不采用的做法

1. **不复制“上百策略”或用策略数量衡量能力。** 大量模板通常只是参数变体、市场适配器
   或工具；真正价值来自证据、适配状态和样本外验证。
2. **不采用 Martingale、无限 DCA 或低波动自动放大杠杆。** Passivbot 明确以逆势加仓和
   类 Martingale 为主要机制。[^25] 这与现有风险档和趋势策略目标冲突。
3. **不允许 LLM 直接调用 Broker。** Agent 只能产生结构化 Intent；精度、名义金额、
   reduce-only、保护、幂等和重试由代码控制。
4. **不让 Agent 在线修改自身风险、提示词或策略源码。** 自动进化只在隔离 Alpha Lab；
   生产只加载审核过且哈希固定的版本。
5. **不在上线前引入多交易所抽象。** CCXT/Hummingbot 的广泛连接能力对当前单一 Binance
   USD-M 边界没有即时收益，反而会模糊订单和仓位语义。
6. **不把情报准确率直接变成执行权重。** 当前 Web3/聪明钱 execution_weight 继续为 0；
   B/C 组只能通过既定 shadow 晋级流程。
7. **不把多 Agent 投票当独立证据。** 多个 Agent 若共享同一模型、提示和数据，其错误高度
   相关；“三票同意”不等于三份独立市场证据。
8. **不直接复制 GPL/AGPL/LGPL 项目代码。** 当前仓库没有根级 LICENSE。Freqtrade 是
   GPL-3.0，NOFX/OpenBB 是 AGPL-3.0，NautilusTrader 是 LGPL-3.0-only；直接组合或分发
   可能产生许可证义务。[^26][^27][^28][^33] 上线前只吸收思想并独立实现；任何代码级复用必须
   先确定本项目许可证和完成逐项法律审查。

## 6. 建议的实施优先级

| 优先级 | 工作包 | 预计投入 | 上线关系 | 完成判据 |
|---|---|---:|---|---|
| P0 | 20 币种运行时白名单单一来源 | 0.5–1 天 | **阻断实盘** | 六个集合哈希一致，集合外开仓全路径拒绝 |
| P0 | 独立生产出口与 live 只读 readiness | 外部条件 + 1 天 | **阻断实盘** | 连续 24h 无 418/429，DNS/WS 稳定 |
| P0 | LLM single-flight、阶段 checkpoint、窗口化 SLA | 1–2 天 | **阻断无人值守** | 连续 24h 无 429，失败安全收敛 |
| P1 | 偏差检测与规则显著性门禁 | 2–4 天 | 上线后策略质量 | 9 张卡全覆盖，合成反例/正例可复现 |
| P1 | 仓位 lifecycle_id 与统一 reconciliation barrier | 2–4 天 | 提高恢复能力 | 任一订单可反查完整状态迁移；重启无歧义 |
| P1 | 证据 OOD/novelty 影子检查 | 2–3 天 | 降低极端行情误判 | OOD 有原因码、零执行权重、机会成本报告 |
| P2 | 分层事实记忆 | 3–5 天 | 降低提示词漂移 | 所有检索可追溯，生成摘要不覆盖事实 |
| P2 | 隔离 Alpha Lab | 5–10 天 | 长期研发效率 | 无生产凭据/网络，候选通过 manifest 导入 |
| P3 | 监督模型 Challenger | 依样本决定 | 长期增强 | OOS、校准、OOD 和 shadow 门槛全部通过 |

这里的时间不包含既定 30 笔闭合 Demo 观察。软件开发可以并行，真实观察样本不能通过缩短
时间或伪造闭合记录替代。

## 7. 总体判断

当前项目已具备独立 RiskGuard、Outbox UNKNOWN、交易所保护单、三类镜像、持久 incident、
闭合 K 线检查、outcome记录、USD-M 回放和shadow评价等基础。其正确性仍需按复核计划验收，
本次没有足够同条件运行数据支持与其他项目作安全性排名，也没有整体迁移能立即改善上线
安全性的验证证据。

最值得吸收的组合是：

- **NautilusTrader**：状态机、启动/持续对账和 backtest/live 语义一致；
- **Freqtrade/FreqAI**：前视与递归偏差、模型过期和 OOD 拒绝；
- **Jesse**：新规则先与随机基线比较，再做 Monte Carlo 和样本外验证；
- **Hummingbot**：Controller/Executor 分离与每个仓位的有限生命周期；
- **NOFX/Vibe-Trading**：模型不可覆盖的硬边界、结构性 paper/live、mandate 与最小权限；
- **FinMem/TradingAgents**：分层记忆、正反证据和可恢复 Agent 图，但只用于研究与候选层；
- **Binance 官方 SDK/数据**：协议差分、历史数据校验和低 REST 的 WebSocket-first 运行。

上线前的正确选择仍然是小范围、可证明的修复，而不是增加新策略、新模型或新框架。先封死
20 币种边界、解决生产出口、稳定最高推理档的调用链，再以当前风险档继续 Demo 验收；
上线后再把统计证伪、OOD、分层记忆和 Alpha Lab 逐项加入 shadow。
