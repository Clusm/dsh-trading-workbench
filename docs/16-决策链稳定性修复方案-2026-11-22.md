## 2. 方案 A：执行角色改为确定性代码

### 2.1 为什么还要改
失败率已经不高了，但这个角色本来就没有需要模型判断的东西：

- `semantics.js:215-249` 已经锁死了标的、方向、止损和止盈（`SL drift` / `TP drift`），`entry_type` 也只能是 `MARKET`。
- 模型实际做的是“现价是否在入场区内、按风险算数量、写 preflight”，全是算术。
- 它给出的 `blocked_reason=PRICE_MOVED` 是当前 38 轮里 **20 轮不交易的直接原因**。这本该是确定性判断，现在由模型来做，结果无法复现，只能看它写的 `rationale`。
- 每轮额外花 10.5s（p50）到 30.2s（p90），还要占一次调用名额（`MAX_CALLS = 14`）。

### 2.2 改动
1. **新文件 `host/ai/execution-plan.js`**，导出：
   ```js
   buildEntryExecution({ cycleId, decision, risk, referencePrice, equity, exchange, caps, toleranceBps })
     -> execution_entry/1 对象（结构不变）
   ```
   - **可执行判断**：
     - 有 `entry.zone_low/zone_high` 时，现价必须在区间内。
     - 没有入场区时，现价必须在 `entry.price ± toleranceBps` 内（`ENTRY_TOLERANCE_BPS`，建议先设 15，可配置）。
     - 不满足时：`executable=false`、`blocked_reason='PRICE_MOVED'`，`order_plan` 和 `preflight` 置为 `null`，`rationale` 写清现价、区间和偏离 bp。
   - **数量**：`equity × min(plan.risk_pct, risk.max_risk_pct) × risk.size_multiplier ÷ |referencePrice − stop_loss|`，按 `exchange.step_size` 向下取整；低于 `min_qty` 报 `SIZE_BELOW_MIN`。
   - **杠杆**：`min(plan.leverage, risk.max_leverage, caps.maxLeverage)`。
   - **preflight**：由代码填 `reference_price / notional_usd / risk_usd / risk_pct / margin_required_usd / estimated_fee_usd / checks`。`checks` 至少 5 项，满足 schema 的 `minItems: 5`。
   - **权益缺失时直接拒绝**（`ACCOUNT_UNAVAILABLE`），**不使用默认值**。
2. **`chain.js:1271-1311`**：用 `buildEntryExecution(...)` 替换 `callRole('execution_entry', ...)`。
   - 结果仍然走 `validateOutput('execution_entry', ...)`，现有语义校验继续把关。
   - `calls` 里追加一条审计：`role: 'execution'`，`provider: 'deterministic'`，`latency_ms`、token 均为 0。这样界面阶段表和归档结构不变。
3. **`constants.js`**：
   - 新增 `EXECUTION_ENGINES = { DETERMINISTIC, LLM }`，默认 `DETERMINISTIC`，通过 `config.executionEngine` 可以切回模型，便于对照。
   - 引擎为 `DETERMINISTIC` 时，从 `VARIANT_ROLES.baseline / lean` 中去掉 `execution_entry`。
4. **规则直通路径（`integration.js:4466-4493`）改用同一个函数**。现在它在读不到权益时默认按 **5,000** 算仓位（`:4470-4471`），风险比例缺省按 1%、杠杆封顶 5×。改用 `buildEntryExecution` 后，权益缺失直接拒绝，两条路径的口径也统一了。

### 2.3 边界
- 现价仍是证据构建时的冻结价（`chain.js:1324-1339` 已注明），这次改动不解决盘口时效问题，真正的时效校验仍由 P2 提交前报价负责。
- 计划入场方式全是 `MARKET`（69/69），条件入场仍然会被判离区，这是另一项（条件单）要解决的，不在本次范围内。
- 执行闸门 `evaluateEntryPlan` 的 `observe / enforce` 逻辑不动。

## 3. 方案 B：决策角色不再逐字段抄写计划

### 3.1 问题
`semantics.js:46-61` 的 `copiedPlanWithRiskDown` 用 `deepEqual` 比对整份计划（只放行 `risk_pct` / `leverage` 下调）。模型抄写时改一个小数位、漏一个 `basis` 字段就判失败，在当前 40 次决策调用里占了 8 次。每次失败都要带修复提示重试一次（每次 10–25s），两次都失败的 2 轮直接以 `DECISION_INVALID` 结束。

### 3.2 小改（建议先做）
- **位置**：`chain.js:848`（`parseJsonText`）之后、`:858`（`validateOutput`）之前。
- **逻辑**：当 `roleKey === 'decision'` 且 `parsed.action === 'TRADE'`，并且 `selected_case` 指向的 R1 `plan_draft` 存在时：
  ```js
  const src = input.openings?.[parsed.selected_case]?.plan_draft
  if (src && parsed.plan) {
    parsed.plan = {
      ...structuredClone(src),
      risk_pct: Math.min(num(parsed.plan.risk_pct) ?? src.risk_pct, src.risk_pct),
      leverage: Math.min(Number.isInteger(parsed.plan.leverage) ? parsed.plan.leverage : src.leverage, src.leverage),
    }
    audit.plan_normalized = true
  }
  ```
- **效果**：复制校验必然通过，但“只能下调风险和杠杆”的规则一点没放松。审计里记录 `plan_normalized`，事后能区分哪些轮次被代码覆盖过。
- 约 10 行改动，加一条单测：模型抄错 `stop_loss.basis` 时，结果仍然可交易，且计划等于 R1 原件。

### 3.3 彻底改（可选，二期）
- 决策 schema 去掉完整的 `plan`，只保留 `selected_case`、`risk_pct_cap`、`leverage_cap`、`thesis`、`case_comparison` 等。计划由代码从 R1 复制。
- 提示词删除“必须原样复制计划”这一段，`PROMPT_VERSIONS.decision` 升到 `decision.v4.zh1`。当前决策输出 p90 约 5.1k token，预计能减少一截。
- 这一步涉及 schema、提示词、界面和归档读取，需要单独排期。

### 3.4 对照
已有的 `lean` 变体（`constants.js:192-199`，不调用分析和决策两个角色，由评分卡直接选边）可以和 baseline 并行跑一段时间，对比成交率和失败率。注意：评分卡给红队的分数恒为默认值（单独问题，见附录），对照前要先确认这一点不会让 `lean` 一律选蓝队。

## 5. 方案 D：已有持仓分支的两个缺口

### 5.1 手动“运行一轮”没有持仓预检
- 自动调度在 `scheduler.js:287` 调用 `preflight()`，有持仓时返回 `POSITION_OPEN` 并跳过。
- 手动触发 `integration.run()` 不经过这一步。`integration.js:4007-4011` 发现有持仓时只写了一句 `strategy_selection_reason = '账户已有持仓，优先执行持仓风险管理…'`，然后照样跑完整条开仓链，最后在 P1 以 `E_RISK_SYMBOL_POSITION` 失败（约 4–5 万 token、2 分钟）。
- **改法**：`run()` 开头，在 `trigger !== 'auto'` 时也调用 `preflight()`。返回 `POSITION_OPEN` 时，直接写一条 `outcome='no_trade'`、`reasonCode='POSITION_OPEN'` 的轮次记录并返回，不调用任何模型。界面上能看到这一轮为什么没跑。

### 5.2 持仓管理没有接上
- `execution_manage/1` 的 schema（`schemas.js`）、提示词、语义校验（`semantics.js:251-271`）和模型配置都已就绪，但 `chain.js` 里没有任何地方调用它。
- 所以有持仓时，系统对仓位不做任何 AI 管理（只有服务端监督进程的对账和可选的 `WORKBENCH_TIME_STOP_HOURS`）。这和 README 里“有持仓时只做减风险动作”的说法不符。
- **本次只改文档**：README 的“范围”段和界面上的相应文案，如实写明持仓管理尚未接入。持仓管理链单独立项，需要先设计输入（持仓 + 保护单 + 证据）、允许的动作（HOLD / REDUCE / CLOSE / REPAIR_PROTECTION）和 P1/P2 的减仓通道。
