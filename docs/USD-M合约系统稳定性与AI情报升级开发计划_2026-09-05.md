# USD-M 合约系统稳定性与 AI 情报升级开发计划

版本：1.0

日期：2026-09-05

适用项目：`multi-agent-trader`

## 1. 目标与不可变约束

本计划的目标是在不改变当前风险档的前提下，提高币安数字货币合约系统的状态一致性、故障恢复能力、可观测性和市场情报质量。

不可变约束：

1. 交易范围仅限 Binance USDⓈ-M 数字货币 USDT 永续合约。
2. 不交易现货、杠杆现货、Convert、币本位合约、期权、股票、ETF、贵金属或链上资产。
3. Web3 Skills、MCP、LLM 和外部情报源无权直接提交订单。
4. 所有订单只能经过现有确定性风控和唯一的 `BinanceFuturesBroker`。
5. 不修改当前风险档数值；稳定性改造不得隐式降低或提高杠杆、仓位、保证金、单笔风险、日损或回撤阈值。
6. 任何账户、订单、仓位或保护单状态未知时，允许减仓和平仓，禁止新开仓。
7. 每个阶段必须可独立关闭和回退，不允许一次性替换整条交易链路。

### 1.1 风险档基准

升级前后必须保持以下值不变：

| 项目 | 固定值 |
|---|---:|
| 常规最大杠杆 | 20x |
| 强信心最大杠杆 | 50x |
| 最大保证金使用率 | 80% |
| 强信心保证金使用率 | 95% |

| 单笔风险 | 2% |
| 单日亏损阈值 | 15% |

在 CI 和发布脚本中生成这些字段的规范化 SHA-256。任何非计划内变化都阻止发布。

## 2. 当前系统基线与可行性结论

### 2.1 已具备的能力

- 同步 `httpx` Binance USD-M Broker，支持 demo、testnet、live。
- 基于 `clientOrderId` 的重复提交保护和 POST 异常后 REST 对账。
- 开仓后止损、止盈保护；保护失败时紧急平仓。
- 30 秒快循环处理限价单、保护单和账户风险；慢决策已放入独立线程。
- SQLite WAL、5 秒 busy timeout、进程内 `RLock`。
- 资金基线、双通道台账、控制状态采用本地持久化。
- 价格 WebSocket 失败后自动回落到 REST。
- `/api/health`、单实例锁、启动保护核验已经在工作区开发中。

### 2.2 主要缺口

- 没有 USD-M 私有 User Data Stream，订单和仓位主要依赖 REST 轮询。
- 没有持久化的交易所事件收件箱和完整订单状态机。
- `orders` 表能记录结果，但不能可靠表达 `SUBMITTING`、`UNKNOWN`、部分成交及事件处理进度。
- WebSocket 仍使用旧的无路由地址；币安 2026-09-04 文档已要求按 `/public`、`/market`、`/private` 路由。
- 当前网络曾出现 `fstream.binance.com` 握手成功但不推送帧，私有流可用性必须先探测。
- 自动化验证主要位于 `scripts/smoke_*.py`，缺少统一测试入口、覆盖率和固定回放样本。
- SQLite 当前为单连接跨线程共享，虽有锁但事件流接入后写入频率上升，需要缩短事务并验证关闭竞态。
- 现有链上情报是直接网络采集，不具备独立进程、严格 Schema、来源版本和故障隔离。

### 2.3 技术路线结论

不整体改写为异步系统。保留现有同步 Broker 和 LangGraph 决策链，新增：

- 一个独立私有流线程；
- 一个内存有界队列；
- 一个单写入事件消费者；
- 一组 SQLite 增量表；
- 一个独立 Web3 情报侧车进程。

该方案对现有代码侵入小，能够按功能开关旁路运行，并兼容当前 Windows 启动环境。

## 3. 目标架构

```text
USD-M public/market WS ───────┐
USD-M private user stream ────┼──> Exchange Event Inbox ──> Account/Order Mirror
USD-M signed REST reconcile ──┘              │                    │
                                             │                    ├─> Dashboard/Health
                                             │                    └─> Execution context
Web3 read-only sidecar ──> Intel Events ──> Feature Store ──> Shadow Signal Fusion
                                                               │
Strategy + AI decisions ───────────────────────────────────────┘
                                                               ↓
                                              Existing deterministic risk rules
                                                               ↓
                                                Single BinanceFuturesBroker
                                                               ↓
                                                  Binance USD-M Futures only
```

状态来源优先级：

1. WebSocket 事件用于低延迟更新。
2. Signed REST 快照用于启动、重连和周期性最终一致性校验。
3. 本地数据库用于恢复处理进度，不能覆盖更新的交易所事实。

## 4. 关键数据模型与状态机

### 4.1 新增数据库表

#### `exchange_events`

保存私有流和 REST 对账产生的原始事实：

- `event_key`：唯一键；优先由事件类型、订单号、执行号和事件时间组成。
- `event_type`：`ORDER_TRADE_UPDATE`、`ACCOUNT_UPDATE`、`MARGIN_CALL` 等。
- `event_time_ms`、`transaction_time_ms`、`received_at`。
- `symbol`、`client_order_id`、`exchange_order_id`、`trade_id`。
- `source`：`user_stream` 或 `rest_reconcile`。
- `status`：`RECEIVED`、`APPLIED`、`IGNORED`、`ERROR`。
- `payload_json`、`error`、`processed_at`。

`event_key` 建唯一索引，重复帧必须幂等。

#### `order_outbox`

保存系统准备提交的订单命令：

- `command_id`、`client_order_id`、`decision_id`、`intent_id`。
- `symbol`、`action`、`request_json`。
- `state`、`attempt_count`、`last_error`。
- `created_at`、`submitted_at`、`resolved_at`、`updated_at`。

`client_order_id` 唯一。任何状态为 `SUBMITTING` 或 `UNKNOWN` 的订单，在按 `clientOrderId` 对账完成前不得重新提交。

#### `account_balances` 与 `account_positions`

保存账户镜像：

- 余额按 `asset` 唯一。
- 仓位按 `(symbol, position_side)` 唯一，兼容 Hedge Mode。
- 保存交易所事件时间、本地更新时间和快照版本。
- 只允许数字货币 USDT 永续白名单 symbol 入库到“可交易镜像”；其他资产只记录审计并标记 `out_of_scope`。

#### `intel_events` 与 `shadow_decisions`

分别保存标准化情报和 A/B/C 影子决策，禁止与真实订单表混用。

### 4.2 订单状态机

```text
PLANNED
  -> SUBMITTING
  -> ACKNOWLEDGED -> NEW -> PARTIALLY_FILLED -> FILLED
                  -> CANCELED / EXPIRED / REJECTED
  -> UNKNOWN -> REST query by clientOrderId -> ACKNOWLEDGED/终态
                                      └─────> NOT_FOUND_CONFIRMED
```

规则：

- 网络超时不是下单失败，而是 `UNKNOWN`。
- `UNKNOWN` 只允许查询，不允许再次 POST。
- `NOT_FOUND_CONFIRMED` 至少需要两次间隔查询，且第二次使用交易所服务器时间窗口。
- 订单状态只能按允许的状态迁移前进；迟到事件可补充成交信息，但不能把终态退回 `NEW`。
- 部分成交必须累计成交数量、成交额、手续费和已实现盈亏。
- 保护单和普通订单共享状态机，但通过 `purpose=ENTRY|EXIT|STOP|TAKE_PROFIT` 区分。

### 4.3 私有流状态机

```text
INIT -> CONNECTING -> RECONCILING -> LIVE
                    -> DEGRADED -> RECONNECTING -> RECONCILING
```

- 启动和每次重连后必须先拉取账户、仓位、普通挂单和 Algo 保护单快照。
- `RECONCILING` 完成前不开新仓。
- 私有流不可用时保留 REST 快循环；系统进入 `DEGRADED`，不让流故障阻断减仓和平仓。
- 是否允许在 `DEGRADED` 下新开仓由“最近一次成功 REST 对账＋无未决 UNKNOWN 订单＋保护覆盖完整”共同决定，不由 WebSocket 单一状态决定。

- `M7-08` 文本按不可信数据处理，过滤提示注入和任何“调用工具/提交订单”指令。
- `M7-09` Sidecar不可用时返回 `unknown`，不返回伪造的中性或零值。
- `M7-10` 保存来源版本、请求摘要、响应哈希和延迟，禁止日志泄露密钥。

验收：

- Sidecar进程即使被完全接管，也无法访问Broker对象或交易密钥。
- 非白名单资产和非USDT永续标的进入交易决策的测试通过率必须为0。
- Sidecar停止、超时或返回恶意文本时，主交易系统正常运行。

## 7. 测试矩阵

| 类别 | 必测场景 | 通过条件 |
|---|---|---|
| 单元 | 状态机、事件幂等、symbol映射、Schema | 确定性通过，核心覆盖≥90% |
| 数据库 | 重复迁移、WAL、锁等待、崩溃恢复 | 无丢失、无重复、可恢复 |
| HTTP | 超时、5xx、-1021、-1022、限流 | GET可退避，POST不盲重试 |
| User Stream | 断线、迟到、重复、乱序、过期 | 对账后镜像一致 |
| 订单 | POST超时、部分成交、重复响应 | 不重复下单，终态正确 |
| 保护单 | 缺失、重复、错误数量、触发成交 | 自动恢复或禁止新开仓 |
| 服务 | LLM卡死、快循环异常、线程退出 | 保护与对账不中断 |
| 状态文件 | 截断、空文件、模式不匹配 | fail closed且可恢复 |
| Web3 | 超时、恶意文本、错误映射 | 不影响主服务，不产生订单 |
| 端到端 | demo连续运行、重启、断网恢复 | 账户/订单/仓位最终一致 |

额外故障注入：

- POST已被交易所接受但本地收到超时。
- WebSocket在FILLED事件前断开。
- 数据库写入短暂被外部进程占锁。
- 系统时钟偏移超过5秒。
- 服务在写状态文件和写订单中间崩溃。
- 保护单触发发生在服务离线期间。
- Web3 Sidecar返回超大响应或提示注入文本。

## 8. 发布、观察和回退

环境顺序：离线回放 → demo → testnet（接口可用时）→ live。

每阶段采用四级开关：

1. `disabled`：代码存在但不运行。
2. `observe_only`：采集和比较，不影响读取路径。
3. `read_enabled`：业务读取新镜像，但Broker仍保留REST兜底。
4. `enabled`：正式使用，旧路径仍可通过开关恢复。

发布前：

- 备份数据库和关键状态文件。
- 记录风险档哈希、Git commit、执行模式和当前交易所快照。
- 有未决 `UNKNOWN` 订单时禁止发布。
- 有仓位时必须确认保护覆盖后再重启。

发布后观察：

- 5分钟：进程、健康、实例锁、私有流、保护单。
- 30分钟：事件积压、镜像差异、快慢循环。
- 24小时：Listen Key续期、重连、SQLite增长、告警质量。
- 72小时：订单/仓位最终一致性。

自动回退条件：

- 新模块导致重复订单或状态倒退。
- 镜像与REST连续两次无法解释的不一致。
- 保护覆盖不完整且自动修复失败。
- 事件队列持续积压或消费者线程退出。
- 风险档哈希变化。
- 交易范围出现非白名单或非加密合约。

回退动作只关闭新模块读取和情报权重，不删除数据库事件，不撤销交易所真实订单，不覆盖资金基线。

## 10. 完工定义

只有全部满足以下条件，项目才视为完成：

1. 风险档哈希和交易范围哈希与基线一致。
2. 服务只允许一个交易实例，重启可确定性恢复。
3. 订单提交、User Stream、REST和SQLite形成可审计的最终一致链路。
4. POST未知结果不会触发重复下单。
5. 所有当前持仓均有且只有一组有效SL/TP，异常能够被及时发现和恢复。
6. LLM或Web3故障不阻塞保护、减仓、平仓和账户对账。
7. 私有流断开后系统可降级，恢复时不会遗漏交易所侧成交。
8. Dashboard显示的权益、持仓、挂单和订单终态与交易所一致。
9. 非白名单、非USDT永续和非数字货币合约无法进入执行链路。
10. Web3情报默认影子运行，无法直接产生订单或改变风险档。
11. 所有核心故障注入、回放、demo长稳测试通过。
12. 提供运行手册、故障处置手册、数据库恢复手册和版本回退说明。

## 11. 推荐实际执行顺序

第一批只执行 M0、M1、M2，先把当前未提交的稳定性改动安全收口。

第二批执行 M3、M4，完成User Data Stream影子接入。

第三批执行 M5，逐层接管Dashboard、快循环和慢决策读取。

第四批并行执行 M6、M7，保持执行权重为0。

第五批执行 M8、M9，完成观察、评估、运维和文档闭环。

任何阶段未过发布门，不进入下一阶段，也不靠临时放宽校验继续推进。

## 12. 官方接口依据

- Binance USD-M REST User Data Stream：`POST/PUT/DELETE /fapi/v1/listenKey`，有效期60分钟。
- Binance USD-M WebSocket路由：`wss://fstream.binance.com/public`、`/market`、`/private`。
- 单连接有效期24小时；服务端ping/pong及连接消息频率需遵守官方约束。
- Binance官方建议在剧烈波动期间优先使用User Data Stream获取订单和仓位状态，同时保留REST恢复路径。

实施时以当日官方文档为准；接口适配器通过契约测试隔离文档变更。
