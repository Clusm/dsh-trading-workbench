## 3. 为什么限流状态必须共享（代码证据）

读了 `src/data/rate_limit.py`，三个额度的作用域**并不一致**：

| 额度 | 实现 | 作用域 | 共享后行为 |
|---|---|---|---|
| 418/429 冷却 | `rate_limit.py:578` `remaining = payload["cooldown_until"] - now`，在 `_state_file_lock` 临界区内读取 | **跨进程**（读共享文件） | ✅ 一个进程登记冷却，另一个进程立即拒绝发送 |
| `futures/data` 5 分钟 800 次 | `rate_limit.py:590` `_data_group_count(events, group) >= _DATA_REQUEST_BUDGET_5M`，`events` 来自共享 payload | **跨进程**（共享计数器） | ✅ 两进程共用同一个 800 池 |
| 分钟权重 600 | `rate_limit.py:37` `_LOCAL_WEIGHT_BUDGET_1M = max(60, int(os.getenv("MTA_BINANCE_WEIGHT_BUDGET_1M", "600")))`，模块级常量 | **进程内** | ⚠️ 两进程各 600 → 合计上限 1200 |

**结论与对策**：

1. **共享** `public_rate_limit_state.json` → 冷却与 5 分钟额度自动跨进程互斥，这是 B 方案能成立的前提。
2. **下调**每进程分钟权重预算 `600 → 300`，使两进程合计仍为 600，保持 `settings.yaml:180` 注释里"最多主动使用 25%"的原始设计意图。
   实现方式优先级：`MTA_BINANCE_WEIGHT_BUDGET_1M=300` 环境变量（`rate_limit.py:37` 已支持，零代码）> 在 profile 配置里改 `local_weight_budget_1m`。
   注意 `configure_rate_limit_budget()`（`service.py:88`）会在服务启动时用 `settings.yaml` 的值覆盖环境变量，所以**必须改配置侧，只设环境变量无效**。

**反例（务必避免）**：给每 profile 配独立限流文件 → demo 进程触发 418 登记冷却后，live 进程对此毫不知情，继续以 600/分钟打同一个被封 IP。这正是项目历史 418 事故的形态。

### 3.4 实际落地方式（与上文的差异）

实施时对第 3 条采用了**比"下调到 300"更正确的做法**：把分钟权重的判定基准从"进程内累计"改成"共享文件里的窗口累计"。

```python
# src/data/rate_limit.py:588-600（已实施）
minute_weight = sum(
    _safe_int(item.get("weight")) for item in events
    if _event_time(item) > now - 60
)
if (normalized_priority != "critical"
        and minute_weight + event["weight"] > _LOCAL_WEIGHT_BUDGET_1M):
    raise PublicMarketBudgetDeferred(
        f"Binance 跨进程分钟权重预算已用尽（{_LOCAL_WEIGHT_BUDGET_1M}），请求延后")
```

`events` 来自共享文件的 payload，在文件锁临界区内读取。因此**两个进程合计**被同一个
`_LOCAL_WEIGHT_BUDGET_1M = 600` 封顶，无需把每进程预算降为 300 —— 25% 的设计意图被完整保留，
且比"各降一半"更严格（后者在只有一个进程运行时会浪费一半额度）。

**结论：§3 第 2 条的对策已被更优实现取代，不必执行。** 三项额度现在全部跨进程原子。

其余落地细节：

- `Settings.runtime_path()`（`src/core/config_loader.py`）承担 profile 路径解析，并做了路径逃逸校验：
  解析结果必须落在 `data/` 内，且 live 目录不能被软链接指到别处。
- `Settings.rate_limit_state` 返回**未加 profile 前缀**的原路径 → 天然共享。
- `Settings.console_port`：demo 8000 / live 8001。
- `MTA_PROFILE` 除 `demo`/`live` 外一律 `ValueError`；`None` 表示旧调用方，保持原语义。
- live 允许覆盖 `channels` 分配（`config/settings.yaml` 的 `profiles.live.channels` 设为
  `strategy_weight: 0.0` / `ai_weight: 1.0`，即实盘只跑 AI 通道，策略通道不分配），
  但**风险档与杠杆仍来自共同的风险配置**，未被 profile 覆盖。

## 5. 冷启动与数据迁移（关键决策：零搬迁）

**推荐做法：demo 保持现有路径不变，live 使用新子目录。**

| profile | DB 路径 | 处理 |
|---|---|---|
| demo | `data/agent_trader.sqlite`（**原路径不动**） | 零搬迁 |
| live | `data/live/agent_trader.sqlite` | 首次启动自动建库 |

理由：

1. `data/agent_trader.sqlite` 是 35MB 的 WAL 模式生产库，且带 `-wal` / `-shm` 边车文件。
   把它搬进 `data/demo/` 需要一次 WAL 感知的搬迁，是纯粹引入的风险 —— 而收益只是目录整齐。
2. 项目在 `b93e745` 刚刚修过"WAL 主库单独复制导致快照不一致"的问题，L00 第 4 条也明确禁止。
   **不搬，就不会踩。**
3. demo 路径不变意味着**回滚成本为零**：删掉 `data/live/` 并回退代码即可。

**首次启动 live 的顺序**（与评估文档 §6 第 1 步一致）：

```
1. 备份 demo 库（WAL 感知，用 SQLite 在线 backup API，不用 shutil.copy）
2. 受控启动 demo profile  → 迁移 14→16（在现有库上）
3. 断言 current_schema_version() == 16
4. 启动 live profile     → 从 0 建库，迁移 1→16
5. 断言 live 库 current_schema_version() == 16 且 account_ref 为新账户
```

两个 profile 的 `environment` 分别是 `demo` / `live`，由 `service.py:139` 的 `set_release_context()` 写入，`account_reference()`（`trade_reconciliation.py:66`）会因 Key 不同自动生成不同 `account_ref`。**历史 demo 证据不会被污染。**

## 10. 与 7 天观察窗口的时序

**这是本次改造最关键的一条约束。**

评估文档 §6 已确立：观察窗口一旦开启，代码或配置变更会被判为新候选批次、窗口归零。
而方案 A（单进程串行切换）的每次切模式重启都会打断窗口。

因此：

```
必须在此处完成 →  【方案 B 全部改造 + §7 验证矩阵通过】
                        ↓
                  ★ 冻结代码，开启 7 天观察窗口 ★
```

**方案 B 不能边跑观察边改造。** 如果打算并行，就必须在开窗口之前做完；否则只能先走方案 A 开窗口、接受窗口被打断的代价。
