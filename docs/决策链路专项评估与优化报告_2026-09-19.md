## 1. 执行结论与证据边界

当前架构方向可继续使用：确定性策略与模型研究分离，模型提交意图，本地程序负责权限、风控、执行、保护和对账。无需为上线彻底重写，也不建议通过增加模型数量、推理档或开仓次数来替代可靠性整改。

但尚不能认定形成了可靠的无人值守决策闭环。最需要修正的不是“模型不够敢交易”，而是四项基础问题：证据中的数字与交易语义未充分验证；持仓管理责任和时效仍有缺口；成本与复盘标签不可靠；运行版本、模型路由和真实耗时的证据不足。

### 1.2 固定边界

只交易白名单内的数字货币 USD-M USDT 本位永续合约；宏观指标仅作为加密市场背景，不增加股票、黄金、外汇等交易能力。沿用当前风险档，不修改仓位、杠杆、止损或置信度阈值。实盘保持用户指定的关闭状态。SCM安装仍延期。

将现有 `shadow/audit_only` 改为强制执行，即使阈值不变，也会改变交易行为，必须按原方案单独审批、测试和发布，不能借“修Bug”直接开启。无人值守指可检测、限制、恢复故障并通知人员，不代表任何故障下都继续开仓或完全无需人工响应。

## 2. 整体逻辑链条：实际代码如何运行

### 2.1 调度与主图

源码：[service.py](../src/core/service.py)、[graph.py](../src/core/graph.py)。配置默认慢周期10分钟、快周期30秒、研究查询预算4次，三个背景简报共用3600秒缓存TTL。运行覆盖值需另取有效配置验证。

```text
Service 调度
├─ 快循环：挂单处理、保护单/账户对账等，不调用决策模型
├─ 慢决策线程：获取组合/资金/门禁上下文 → 执行下列主图
└─ 复盘worker：日终统计与可选模型总结

START → Guardian → market → macro → onchain → signal_scanner
                                              ├─ strategy_trader ───────┐
                                              └─ strategy → ai_trader ─┤
                                                                     ↓
                       双通道会合 → pipeline授权 → risk → execution → END
                                                                     ↓
                     订单回执/持久化意图 → 后续对账 → 成交/成本/Outcome
                                                                     ↓
                      日报 + 按需经验检索（尚非可靠的自动学习闭环）

独立只读情报侧车 → 市场情报展示 / A、B、C影子实验
                 不拥有Broker，execution_weight固定为0
```

图中 market、macro、onchain 在当前实现中串行，并非三个并行研究Agent。Guardian先评估，但其退出意图仍经过主图会合后执行；“先评估”不等于“独立即时退出”。服务已有独立快循环，不能把主图的延迟问题误写成所有保护都被模型阻塞。

### 2.2 各阶段的输入、输出与责任

| 阶段 | 输入与输出 | 已有约束 | 待完善部分 |
|---|---|---|---|
| 运行入口 | profile、资金、组合、控制状态、业务白名单 | 双环境设计、交易范围、就绪门禁 | 固化实际配置和模型路由指纹；拒绝模糊身份 |
| Guardian | 既有开仓证据、对应周期已收盘K线 → 持仓论点状态/退出意图 | 不用自然语言猜退出、不把网络失败等同平仓理由 | 当前影子模式；退出不能依赖完整慢图成功；历史仓证据不足单列 |
| market | 公共行情、持仓标的 → regime、快照、候选 | 确定性基础简报，摘要LLM可选 | 小时级缓存可能造成背景/候选落后于逐币现查 |
| macro/onchain | 公开背景数据 → 结构化简报和摘要 | 失败有errors、存在原始简报降级 | 数据抓取总时限、来源时间和缺失语义不统一 |
| signal_scanner | 策略卡、K线、持久化状态 → tickets | 真正触发检测，不是模型猜信号 | 分清未触发、跳过、异常、冲突、过期、成交 |
| strategy_trader | tickets、价格、通道资金 → 策略意图 | 实际为确定性执行，不调用配置中的策略模型 | 时间退出、管理责任、历史仓迁移 |
| ai_trader | 简报、组合、ActionSpace → 工具研究 → 决策/持仓表态 | 查询预算、最终提交、字段校验、本轮逐币查询来源验证 | 数字事实验证、跨周期一致性、持仓研究覆盖、原因分类 |
| merge | Guardian/策略/AI意图 → 一份决策 | Guardian优先，其次策略，丢弃冲突AI意图；会合屏障 | 多意图、重复调度、Hedge同币双向语义需专项验收 |
| pipeline/risk | 决策 → 逐级检查、批准/缩量/拒绝、签名 | AI来源强制归AI，本地风险规则不交模型修改 | 逐意图完整签名与管理授权；区分观察与强制规则 |
| execution | 签名意图、控制/就绪状态、交易所约束 → 回执 | 执行前重读门禁与暂停状态，开仓受阻时保留退出 | 部分成交、迟到回执、未知状态、保护覆盖的证据闭环 |
| review | 订单、Outcome、日志 → 日报/经验/校准 | 已有日终worker，不在调度线程做模型复盘 | 成本完备性、归因、校准方向、经验隔离存在明确缺陷 |

### 2.3 “强制最低研究”究竟保证什么

[orchestrator.py](../src/agents/orchestrator.py) 当前只有同时满足以下条件才强制先 `query_symbol_cards` 再至少一次 `query_symbol_detail`：允许新开仓、组合没有任何持仓、查询预算至少2次。

因此，有持仓时不强制新仓候选研究是当前设计，不等于工具损坏；即使空仓完成研究，也可以合理 `no_trade`。另一方面，任何新开仓仍要求该币本轮成功detail查询与匹配的数据时间戳，不能因持仓轮豁免最低研究就免除新开仓证据要求。

风险是：长期持有一个旧仓后，剩余空闲资金的候选研究可能持续缺失。解决办法是将“持仓管理”和“剩余额度候选研究”分成有优先级的预算，不要求每轮强行扩池或强行开仓。

### 2.4 必须区分的状态

`no_trade` 目前同时可能意味着没有优势、管理后继续持有、无法获取数据、模型限流、预算耗尽、字段验证失败、账户不允许开仓。只看最终一个标签，不能判断模型保守程度。

阈值也不能混用：此前采证中的0.65属于强置信度档条件，RR≥2属于该档配套要求；决策质量配置另有RR minimum=1.5且为shadow。它们不等于“全系统任何单都必须confidence≥0.65且RR≥2”。解释某笔批准/拒绝，必须列出实际命中的规则、模式和版本。本轮不将三种口径强行统一为新阈值。

建议原因码至少分为 `NO_EDGE`、`HOLD_EXISTING`、`RESEARCH_INCOMPLETE`、`DATA_UNAVAILABLE`、`MODEL_RATE_LIMITED`、`MODEL_DEADLINE`、`VALIDATION_REJECTED`、`READINESS_BLOCKED`、`CHANNEL_CONFLICT`；允许主原因与多个辅助原因共存。预期拒绝不计成模型错误，模型错误也不能算成有效“看空/观望”研究样本。

## 3. 模型要求与供应商路由评估

### 3.1 源码配置与实际能力是两回事

依据：[agents.yaml](../config/agents.yaml)、[settings.yaml](../config/settings.yaml)、[factory.py](../src/llm/factory.py)、[workbuddy_client.py](../src/llm/workbuddy_client.py)。以下是仓库配置，不证明本轮在线供应商接受所有参数。

| 角色/路由 | 仓库声明 | 实际调用方式与边界 |
|---|---|---|
| 主AI / SenseNova | `deepseek-v4-flash`，temperature 0.3，max_tokens 4000，effort `xhigh` | 主研究与submit；Agent模型配置优先于模型环境变量 |
| market/macro/onchain | 同模型，temperature 0.1，max_tokens 2000，effort `low` | 可选背景摘要；不是各自独立下单者 |
| review_agent | 同模型，temperature 0.2，max_tokens 4000，effort `low` | 对已生成统计做文字总结，不能纠正上游错误账本 |
| strategy_trader | 配置中有模型参数 | 主图实际 `model=None`，确定性函数；配置易误导维护者 |
| WorkBuddy显式路由 | `deepseek-v4.1-flash`，effort `max`，90秒 | 受限CLI StructuredOutput适配，仅ai_trader，不是原生function-call API |
| OpenCode显式备用 | `union-alpha`，90秒 | 仅主AI可选fallback；并非默认全链路备用；当前继承主模型effort等参数 |

主AI多轮研究总时限默认240秒；辅助摘要每次60秒；主API单请求配置180秒；正常路由重试配置3次，启用备用后主请求重试配置0。它们必须服从同一绝对剩余时限，不能把每一层超时相加当总预算。

本次访问[商汤文档入口](https://platform.sensenova.cn/docs)超时，因此没有重新确认其当前模型目录、effort枚举或额度。仓库注释中的“xhigh已测试”仅属历史项目记录，不应改写成供应商现行保证。`max`、`xhigh` 在不同供应商不可机械互换。

### 3.2 模型准入最低要求

1. **协议正确**：识别强制tool_choice；保留工具调用ID；多工具调用逐一响应；结构化输出可验证；截断、拒答、空响应有明确状态。
2. **证据使用**：只引用系统提供的原始数值和证据ID；能区分已收盘K线与live bar、主网市场与Demo账户；缺失不能自造。
3. **交易语义**：LONG/SHORT、entry/SL/TP、数量单位、持仓方向、reduce/close/adjust区分正确；不以“新闻利好”替代可执行价格条件。
4. **资源有界**：单请求、整轮、队列、工具、校验修正、fallback都受期限与调用次数限制；最后预留提交/校验时间。
5. **可审计**：记录请求角色、实际provider/model、effort、token、尝试次数、切换原因、原始响应状态和最终结构化决策。用户审计依据是证据与简要理由，不依赖模型内部思维链。
6. **权限隔离**：运行时模型不能持有交易密钥、读写项目、执行shell或修改风险配置；外部网页/新闻/经验只能当数据，不能升级成指令。
7. **成本与可用性**：用项目真实工具回放评估成功率和p95/p99耗时，不用聊天体验或编程榜单替代；免费/临时模型不得被假设有稳定SLA。

### 3.3 已识别的路由风险与修复设计

- **静默Mock**：factory在缺key或模型none时返回Mock。尚未证明它在所有启动门禁下均能执行真实订单，但必须增加端到端负例：Demo/live主决策缺key只能显式阻断新开仓，不能伪装真实AI成功；测试Mock仅允许显式离线模式。不能因此停掉既有保护与合法退出。
- **WorkBuddy早返回**：该分支在共享API协调器/fallback构建前返回。需要单独验证它的进程限额、超时清理与路由观测，不应宣称享有同一套API并发/fallback保护。环境变量控制并不天然仅限live，必须记录各profile实际选择。
- **上下文裁剪**：WorkBuddy按角色字符上限压缩上下文以适配CLI；有丢失反证、持仓和完整证据的风险。应按证据结构裁剪，保留关键数字、时间、仓位和约束；无法容纳时返回不足，不截断JSON后继续研究。
- **备用参数兼容**：备用当前继承主模型effort等参数。增加provider/model capability表，各自验证，不支持参数应明确报错或使用经批准的映射，不静默降低推理档。
- **配置优先级**：修改环境模型名称不一定覆盖agents.yaml。用配置解析测试与有效配置页面展示最终值、来源、哈希。
- **跨进程额度**：进程内并发1不等于Demo/live共享凭据总并发1；按凭据别名与provider域建立共享准入或统一网关，不暴露真实key。

如果保留高推理档，优先减去背景重复摘要、预计算指标、缓存稳定上下文、保留提交预算，而不是无限延长整轮。高推理主模型不可占用紧急退出职责。模型全失效时禁止新增风险，保护和可证明的管理动作继续工作。

## 4. Agent设计：保留什么、拆分什么

### 4.1 当前角色评价

当前多Agent主要是职责分层，不是多个独立分析师交叉投票。市场/宏观/链上摘要与主AI可能来自同一底层模型，不能用“多个Agent一致”证明信息独立。确定性策略并非AI研究结论的背书；Guardian与risk也不需要升级成LLM。

建议首批保持一个交易主模型，不增加每轮多模型辩论。把反证审查做成结构化字段和确定性验证；第二模型用于离线抽样复核或影子候选评估，其故障不阻塞交易安全路径。

### 4.2 目标职责与接口

| 组件 | 应输出 | 不能做 | 建议代码归属 |
|---|---|---|---|
| 数据采集/质量层 | 带来源、时点、质量的快照 | 把未知填成中性、猜订单结果 | data层；K02证据契约 |
| 确定性特征与候选层 | 各周期指标、候选排序、覆盖原因 | 自改白名单/风险档 | market_query、scanner |
| Research Agent | 支持/反对证据引用、候选比较 | 自报数值覆盖行情事实 | orchestrator适配；提取可测试纯函数 |
| 主决策Agent | open/hold/adjust/reduce/close建议与理由 | 签名、下单、调配置 | 现有ai_trader |
| Evidence Validator | 每条意图的事实/几何/时间验证 | 用LLM文字判断替代数字检查 | U03，K02 |
| Position Manager / Guardian | 有界、幂等管理意图和管理责任 | 依赖新仓研究完成才能退出 | U02，K04 |
| Risk / Authorization | 现有风险约束、签名与执行许可 | 根据近期盈亏自动放宽参数 | U02/U03/U15集成 |
| Execution / Reconciliation | 接受状态、真实成交、保护覆盖、成本 | 将请求成功当成交、盲目重下UNKNOWN | U04，Broker/outbox |
| Review / Evaluation | 分层事实、归因假设、可信度与样本覆盖 | 用不完整成本指导自动调仓 | U01与本文DL06 |

接口复用执行规格K01–K06，不建立第二套平行schema。为review新增的字段必须在U00登记版本和兼容规则，再分派实现。

### 4.3 模型工作流拟议调整

先在离线回放实现显式阶段机：`CONTEXT_READY → MANAGE_EXISTING → SCREEN → DETAIL → VERIFY → SUBMIT`。任意阶段失败均输出阶段、原因、缺失证据和是否仍可进行持仓管理。

持仓管理拥有优先预算；只对剩余可用额度研究新仓；不可用额度的轮次不伪造“已研究但无机会”。多币开仓每币必须有独立有效证据。支持/反证引用同一快照集；高周期趋势必须引用实际取得的该周期数据，不能用15m结论冒充4h。

背景情报移出必须成功的串行关键路径；独立刷新，带年龄入上下文。保护性管理的执行时效由独立调度验收，不依赖辅助摘要甚至主模型返回。这里是目标设计，不是当前已经实现的并行拓扑。

### 5.2 已确认的数据语义问题

1. `query_symbol_detail` 对funding/OI提供可用性元数据，但funding缺失时数值仍可能是0、mark缺失也可能是0。消费端必须先检查质量，不能把缺失解释成“费率中性/价格为零”。
2. 宏观搜索使用写死2026的查询词，返回未来一周线索却装入 `risk_events_24h`；并没有可靠的事件时间/已公布状态。不能据此精确断言“加息结束”或自动解除事件风险。
3. 链上 `whale_activity` 字段承载热门币、总市值、gas等内容，名称夸大了数据含义；当前普通链上Agent的Etherscan分支只查询gas，不证明已取得鲸鱼转账。
4. 普通链上模块使用Etherscan旧入口，侧车使用v2；本轮不据此认定服务已坏，但必须分别核对协议与替身测试，不让两套来源语义漂移。
5. 三类简报共用一小时TTL；工具detail虽较新，但无法自动消除旧候选、旧宏观摘要对注意力分配的影响。
6. 主图辅助LLM超时不覆盖之前所有串行HTTP抓取；宏观有多个独立15秒请求和25秒搜索。整图时限不能简单声称只有240秒。

### 5.3 证据数据契约

在现有K02上补充：`evidence_id / schema_version / environment / market_venue / account_profile / symbol / interval / bar_close_time / source_event_time / observed_at / fresh_until / source / quality / missing_fields / content_hash`。具体列与payload划分由U00决定，不能各Agent自行建表。

事实分层：交易所账户事实 > 已验证行情字段 > 程序计算特征 > 模型解释 > 搜索/外部文本线索。发生冲突保存双方证据并进入复核，不让摘要覆盖事实；主网行情与Demo账户标明不同venue，不能冒用时间戳合并成同一快照。

数据过期策略按用途定义：过期价格不得支持新开仓；过期背景仅降低研究完整性且明确标记；账户状态不可信时阻断新增风险，但不盲目平仓。基于必要数据的管理动作须使用其专属门禁，不能拿“开仓门禁失败”全面禁用保护。

TTL不是交易风险档，但阈值需要通过数据频率/延迟测量后冻结。可先用已有5秒取价缓存、30秒流式新鲜度、600秒侧车新鲜度作为测试边界，不能把一套TTL用于所有源。资金费按实际结算事件与覆盖区间核算，不默认所有合约永久每8小时结算。

## 7. 复盘总结与记忆反馈专项审查

### 7.1 当前反馈链不是自动学习系统

日终worker调用review生成统计报告，再可选让模型做300字总结；保存daily_reviews与scorecard。AI主链可自行调用query_review_library，但该工具独立从订单表构造亏损案例，并非读取昨日日报。置信度校准主要供报告使用；未发现一个经版本化验证的流程把它转换成下一轮安全、可撤销的策略改进。

因此不能把“有复盘页面”描述为“AI已经持续学习”。没有证据证明系统自动训练权重，也不应该允许日报文字直接修改风险档。

### 7.2 已复现的三个统计缺陷

| ID | 代码条件 | 纯内存输入 | 当前实际输出 | 正确目标 |
|---|---|---|---|---|
| RV01 | review._build_outcome_stats使用 `float(pnl or 0)`，并把>=0计赢 | 一条pnl=NULL的Outcome | wins=1、win_rate=1.0、total=0 | unknown=1；合格胜率/净盈亏为不可计算，不造0收益 |
| RV02 | 亏损且invalidation字符串非空就计论点失效 | pnl=-1，有失效条件文本、无触发证据 | invalidated_losses=1 | 是否触发=UNKNOWN；必须引用可验证事件 |
| RV03 | calibration用绝对误差标记overconfident | 3条confidence=.2、pnl=+1 | miscalibration=.8、overconfident=true | 至少区分低估与高估；3样本不足以可靠下结论 |

复现直接调用原统计函数与只返回测试行的FakeDB；未调用run_review_agent/build_review_library。只证明函数行为，不等于已修复或完整集成回归通过。

### 7.3 其他复盘缺口

- **成本源不统一**：日报订单口径raw.net_pnl/pnl与Outcome并行统计；保护触发、部分平仓、资金费晚到可能导致不同结果。必须说明各口径和覆盖率，禁止不加说明地都叫“净盈亏”。
- **因果过度推断**：经验库把≤15分钟亏损写成追价、≥60分钟写成没有及时止损；不同持有周期不能共用这类因果标签。设置了失效条件也不等于市场曾触发它。
- **配对错误风险**：经验库按symbol最近一次open配对close/reduce，不按position lifecycle、side、channel、真实成交分配数量；加仓、减仓、Hedge反向仓会错配。
- **负样本偏差**：只选亏损超过0.30U、最近8条，忽略成功案例、合规止损和正确no_trade；若频繁引用可能强化回避，但目前没有因果证据证明它已导致少交易。
- **费用符号**：经验库以commission < -0.2触发“手续费高”；需结合项目入库符号规范修正，不能假设交易所费用字段是负数。
- **跨profile副作用**：所谓query工具会写项目根 `knowledge/review_lessons.json`；路径不从profile注入，Demo/live可能覆盖同一导出。当前返回值来自当前DB，不据此断言已发生跨账本读取，但共享写入已破坏纯查询/只读发布包假设。
- **校准定义**：当前用桶中点而非平均预测值，用非负盈亏算赢，以绝对偏差指向过度自信，最小样本3；指标不足以指导放大仓位。
- **版本与日期**：日报默认UTC昨天，SQL字符串时间范围；校准全周期最多500条，未按当日/release/model区分。不能把日内报告中的校准表误认为当日效果，也不能把UI北京时间与风控UTC边界混用。
- **评分未完成**：scorecard的score固定0、notes为phase1，不是已评估的Agent能力分数。

### 7.4 目标复盘流程

```text
真实成交/资金费 → 生命周期和成本覆盖 → 合格Outcome
    → 事实统计（确定性）
    → 决策证据与执行轨迹复放
    → 归因标签：已证实 / 可能 / 未知
    → 可选模型提出改进假设
    → 独立审核 + 离线/影子实验
    → 人工批准新版本；原风险档不自动改变
```

拟议字段：`outcome_id / lifecycle_id / account_profile / source / side / release_id / model_route_id / cost_status / funding_coverage / review_version / attribution_status / evidence_refs / confidence_target / generated_at`。unknown不等于0；成本齐全不等于归因齐全，两种状态单独保留。

赢/输/持平分开计；最终净收益统计只使用成本完整记录，同时显示未知笔数与覆盖率。规则原因与统计因果分开：止损触发可以是已证实事实，“入场太急”除非有预定义特征与比较实验，否则只能作为假设。

经验检索改为只读、有界、可溯源：按当前symbol/周期/regime/策略匹配，包含正负案例与合规退出案例；只用决策时刻以前的历史样本；每条附证据与不确定性。导出作业如确有需要，写入profile下的数据目录，不能在查询时改knowledge。

置信度先定义目标事件：例如“按本策略既定退出规则闭合后的最终净收益>0”，与“价格在4小时内上涨”严格区分。持有未闭合单不可当失败；不完整Outcome不可当赢。校准使用平均预测值、方向性bias、Brier/ECE及样本/区间说明；时间隔离验证，按模型/策略版本分层，小样本只能展示不能用于自动调风险。

## 8. 影子情报如何进入未来决策

维持A/B/C的研究用途，但先修统计再讨论权重。当前A只复制open、B频繁按规则生成方向、C未配置为unknown，三组不是同一候选同一时点下的公平对照。数千个重叠B样本不能当成数千笔独立交易。

当前标签以评估实际取价时刻而非严格目标时刻计算，轮转还造成路径采样不足；固定费用/滑点与线性资金费估计不是实际成交成本。本报告不认可“B已证明有alpha”或“C无价值”的结论。

建议分三步：U06a先确保零执行权重、unknown、旧标签免责声明和资源隔离；U06b/U07再做固定时点、版本隔离、配对基线、无未来信息、重叠样本分块检验；最后单独申请情报进入决策的对照实验。

将B/C放进主AI提示词，即使写着“只供参考”，也已经可能改变决策，不能再称零影响影子实验。应建立隔离的候选模型上下文，复用同批EvidenceBundle，输出不下单；比较证据有效率、方向变化、成本调整后的收益分布与尾部损失，再决定是否推广。不能用“本轮只读API”证明其策略影响为零。

```text
    require exact profile/symbol/interval/evidence references
    require closed bars, fresh required sources, finite numeric values
    derive price geometry and RR from source values, not model prose
    require per-intent permission + existing risk rules + current readiness
    sign immutable intent hash + context version + expiry

build_review(outcomes, as_of):
    partition eligible / incomplete / unassigned
    stats = aggregate eligible only; display all coverage counts
    invalidation = verified trigger event, else UNKNOWN
    hypotheses = optional model summary of facts, never configuration writes
    persist versioned report via profile-specific background worker

query_lessons(context, as_of):
    select bounded eligible outcomes closed before as_of
    match lifecycle/regime/strategy; include positive and negative evidence
    return evidence references + uncertainty; no filesystem writes
```

DL02必须区分可程序验证的数值约束与策略主观判断；不应把所有主观论点都伪装成硬规则。审计trace“出现过某检查名称”不等于每条意图都完成该检查，签名需绑定精确意图集合。对close/reduce/adjust使用不同契约，不能让它们受新开仓证据要求误伤。

## 11. 多Agent交付与提交顺序

研发协作与运行时交易Agent分开：外部DeepSeek/Union可写代码、审补丁，但不得因此获得生产密钥或实时下单权限。当前尚未分派；双方须独立会话交叉审核，同一模型的共同偏差要明示，Q用独立夹具验收，不接受仅凭另一Agent口头“通过”。

建议提交顺序：

1. I登记本文增量、精确代码基线、共享文件所有权、契约与测试manifest；先冻结新职责，不同时重构整个graph/service。
2. A/C并行做账本/复盘纯函数与证据验证；B做管理/执行；F做身份/路径；E做调度恢复；D只做隔离与实验设计。依赖接口未集成前用固定夹具，不直接读生产库开发。
3. RV01–RV03、经验query无写入、模型身份/缺key负例分成可独立审核的小提交；数据库迁移与报表适配由I协调成兼容提交组。
4. 集成退出时效、数值验证、模型期限与数据质量适配；Q回放多意图、部分成交、断网与双环境场景。
5. 完成文档、报告免责声明、索引、有效配置页面与打包；按旧版本报告标记处理，不无记录地覆盖历史复盘结论。
6. 最终RC离线验收→受监督Demo部署→规定观察与告警/恢复演练→发布审查。实盘启动需用户另行批准。

各提交交付：变更目的、前后行为、风险档哈希不变证明、接口变化、测试命令与结果、迁移/回滚说明、独立审核意见。数据库迁移不得依赖简单回退Git恢复；回滚使用已验证的兼容策略与一致性恢复包。

## 12. 最终判断

整体逻辑具备继续改进的基础；“模型研究—程序执行”的权限边界应保留。首批优先顺序为：真实账本与复盘纠错、逐意图证据验证、独立持仓管理、模型/数据故障收敛、真实运行证据。完整影子实验、记忆增强、多模型协作和大规模模块拆分属于后续阶段。

本轮新发现的复盘错误会污染人和模型对系统的判断，应纳入首批可信性整改。只有让事实、解释、动作和结果能逐项核对，才能合理评估模型能力；更高推理档或更长时间运行都不能自动修复这些逻辑问题。

本文交付仅为报告与方案补充：没有改业务代码、参数或服务，没有启动实盘，没有提交Git或推送远程。完成报告不代表整改完成，更不代表发布门禁由NO_GO转为GO。
