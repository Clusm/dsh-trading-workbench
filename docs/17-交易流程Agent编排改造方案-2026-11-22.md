## 1. 现状编排

```
每 10 分钟（scheduler.js，固定 BTCUSDT）
  证据快照（service /api/cycles，11 币，主标的已预先选定）
   → analysis        LLM  p50 16.6s
   → red/blue 开场    LLM×2 并行  p50 ~15s / p90 ~27s   （红固定做多，蓝固定做空）
   → red/blue 回应    LLM×2 并行  p50 ~9.5s
   → scorecard        代码
   → decision         LLM  p50 12.3s
   → risk             LLM  p50 15.3s
   → execution_entry  LLM  p50 10.5s
   → 执行闸门（observe）→ P1 → P2（只支持 MARKET）
```

一轮 8 次 LLM 调用，约 5 万 token，耗时 p50 101s / p90 147s。一轮结束后什么都不留，下一轮从头再来。

## 2. 编排层面的实测诊断

| # | 发现 | 数据 | 含义 |
| --- | --- | --- | --- |
| D1 | **决策角色和代码规则的选择完全一致** | 至少一方过门禁的 69 轮里，决策角色的选择与 `selectDeterministicCase`（只看评分卡）**69/69 相同**；主动选“不交易”0 次，score_override 1 次 | 这个角色没有带来任何新信息，只带来了“计划复制校验”失败（当前配置 40 次调用里有 8 次） |
| D2 | **第二轮回应不改变任何结果** | 75 组回应：`tradeable` 一次都没翻转；信心变化都在 ±0.02 以内；门禁结果完全由开场信心决定（红队开场 <0.5 的 65 次全部失败，≥0.5 的 10 次全部通过） | 每轮多 2 次调用、约 10s、约 5k token，没有收益 |
| D3 | **固定立场辩论在单边行情里只剩一方有效** | 分析角色 75 次里 74 次偏空；被迫做多的红队开场信心均值 0.40，门禁失败 65/75 | 方向在分析阶段就定了，红队基本是陪跑 |
| D4 | **风控 AI 几乎是固定折扣** | 65 次输出：DOWNSIZE 62 次（倍数 0.5–0.8），REJECT 2，APPROVE 1。理由前两位是 `DERIVATIVES_PARTIAL` 47、`STALE_SOURCES` 36 | 主要理由都是数据健康信号，代码就能算，没必要每次调一个最高推理档位的模型 |
| D5 | **条件型 setup 被当场按市价判断** | R1 生成计划**那一刻**：给了入场区的 39 份里，34 份（87%）不含当时现价；另 33 份没给入场区。入场价相对现价 −1.04% ~ +1.46%。分析角色给的触发本来就是“15m 收盘跌破 73000、有效期约 2 小时”这类条件 | “价格离区”主要不是链路太慢，而是**把一个等待触发的 setup 当成了立即执行的订单**。下一轮又重新生成同一个 setup，又判离区 |
| D6 | **研判和执行绑在同一个 10 分钟节拍上** | 一轮 101–147s，执行只在最后一刻检查一次 | 触发条件在两轮之间满足也看不到；研判越慢，执行越错过 |
| D7 | **只研判 BTC** | `scheduler.js:27` 固定 `BTCUSDT`；77 次分析的 `symbols_analyzed` 都只有 1 个币 | 白名单形同虚设（16 号文档附录 1） |

结论：瓶颈不在某个角色写得好不好，而在**编排形状**。8 次调用里，真正改变结果的只有分析和蓝队开场两次，其余要么复述代码规则（D1、D4），要么不起作用（D2、D3）。最后再用“立即执行”的方式去处理一个“等待触发”的计划（D5、D6）。

## 3. 方案迭代

### v1：压缩链路
- 做法：去掉 decision 和 R2，风控和执行改成代码，只保留分析 + 红蓝开场 3 次调用。
- 评审：
  - ✅ 调用减少 60%，D1、D2、D4 的失败和耗时消失。
  - ❌ **D5 没解决**：setup 仍然当场判断，20/38 的离区不会减少，成交率基本不会变。
  - ❌ D3 没解决：红队仍然陪跑。
  - ❌ D6、D7 没解决。
- 结论：省成本，但不提高交易质量。**否决**，只作为过渡（即 16 号文档）。

### v2：研判和执行拆成两个循环
- 做法：
  - 慢循环（LLM）：只负责产出 **setup 卡**（方向、触发条件、入场区、止损止盈、有效期、失效条件）。
  - 快循环（代码，15–30s 一次）：盯住已挂起的 setup，触发后用新鲜标记价复核区间，再走 P1 → P2。
- 评审：
  - ✅ D5、D6 解决：触发条件在两轮之间满足也能执行。
  - ⚠️ setup 有效期约 2 小时，触发时行情可能已经和研判时不一样了，需要失效条件和必要时的复核。
  - ⚠️ 触发条件如果是自然语言（“伴随放量”），代码没法判定。
  - ⚠️ 多个 setup 可能重复或冲突。
  - ❌ 慢循环里仍然沿用固定红蓝 + 决策，D1–D4 的浪费还在。
  - ❌ 有持仓时谁来管理，没有回答。
- 结论：方向对，细节不够。进入 v3。

### v3：推荐方案（setup 驱动的双循环）

```
慢循环：研判（每 10 分钟，或异动 / 平仓等事件触发）
  ① 筛选          代码   20 币按趋势 / 波动 / 量能 / 异动排序，取前 3，每币一行摘要
  ② 提案          LLM×1  analyst：对前 3 名给出 0–2 个 setup，方向自选；
                          触发条件必须用评估器原语表达，否则不能挂起
  ③ 对抗审查      LLM×1  critic：只针对提案找致命缺陷，输出 veto / tighten（只能收紧）/ pass，
                          必须引用证据 ID；建议用与 analyst 不同的模型路由
  ④ 评分 + 风控   代码   评分卡按 setup 自身打分；风控折扣按数据健康确定性计算
  ⑤ 挂起          代码   通过 evaluateEntryPlan（强制有入场区 + valid_until）后写入 setup 表；
                          同标的同方向去重

快循环：执行（纯代码，每 15–30 秒）
  对每个已挂起的 setup：
    失效条件满足 / 已过期      → 作废并归档
    触发原语满足               → 新鲜标记价核入场区 → P1（当场取审批 token）→ P2 市价入场 → 消费
    （可选）距研判超过 30 分钟  → 一次低档位 LLM 复核，只能 veto，默认关闭

持仓循环：有持仓时
  慢循环切到 manage 模式（接上已写好但没调用的 execution_manage）；
  快循环只负责保护单巡检和 time_stop
```

### v3 自审：遗留风险
1. **原语表达力有限**：“放量突破”这类条件只能近似成 `all(candle_close, …)`，表达不了的条件，setup 就不能挂起。这是有意的取舍：宁可少做，不做无法验证的单。挂不上的 setup 要计数，作为将来扩充原语的依据。
2. **单一 analyst 的偏差**：去掉固定红蓝后，方向完全由 analyst 决定。对策：critic 用不同的模型路由；按方向统计胜率，偏差过大时报警。
3. **15m 收盘触发的滑点**：触发点在收盘时刻，市价入场有滑点。沿用 P2 的 `max_slippage_bps`，并在 setup 里限制入场区宽度。
4. **max_open_positions = 1**：多个 setup 同时触发时，先触发的生效，其余自动作废并记录原因。
5. **服务重启**：setup 表必须落在 service 的 SQLite 里，不能只放在 Host 内存。快循环放在 service 监督进程（现在 30s 一次心跳加对账）还是 Host 定时器，要看 P2 的租约要求。Host 持有租约，所以初版建议放在 Host，由 service 提供 `GET /setups/armed` 和原子的 `consume` 接口。**这一点要再核对 lease 代码后定稿。**
