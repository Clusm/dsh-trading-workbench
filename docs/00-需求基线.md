# 交易工作台 v1 需求基线

- 日期：2026-11-09（Asia/Shanghai）
- 状态：已与用户逐项确认，作为 v1 设计的唯一需求输入
- 范围：只做第一版插件**设计方案**，不做实现

## 1. 产品定位

把原 `multi-agent-trader` 的 FastAPI 控制台重做为 **DSH Harness 插件形态的模拟盘交易工作台**：
用 Harness 内置 AI 跑一条多 agent 决策链，在**币安 Demo** 上执行，实时展示权益曲线、当前仓位、
完整 AI 决策链路和交易复盘。原项目只作为代码/数据参考，**不启动其交易主循环**。

第一版目标不是验证某一套固定策略，而是验证"分析 → 红蓝辩论 → 决策 → 风控 → 操盘手"这套
AI 决策流程本身在 Demo 环境下的表现。

## 2. 已确认需求

| # | 维度 | 结论 |
|---|---|---|
| 1 | 交付形态 | DSH Harness 插件：一个主面板 + 侧栏入口，嵌在 Harness Web UI 内 |
| 2 | AI 调用 | **只使用 Harness 内置 LLM**，不接外部 LLM API、不配置外部 key；每个 agent 固定推理档 |
| 3 | 执行环境 | **币安 Demo**（`demo-fapi.binance.com`）；不接实盘，不存在 live 下单路径 |
| 4 | 操作权限 | 允许在 Demo 下单/平仓/挂保护单；禁止任何实盘写入 |
| 5 | 策略 | **不绑定具体策略**；分析 agent 做通用技术面 + 交易面分析 |
| 6 | 分析 agent | 原市场/宏观/链上情报合并为**一个**"技术分析与交易分析"agent |
| 7 | 红蓝辩论 | 红队、蓝队**各 1 轮陈述**，然后决策者裁决 |
| 8 | 决策者 | 决定"是否交易"以及"选红队方向还是蓝队方向" |
| 9 | 风控 | AI 建议 + **硬规则否决/降仓**；AI 不能突破硬上限 |
| 10 | 操盘手 | 执行决策者指令，并持续跟踪仓位变化 |
| 11 | 工具调用 | **v1 不做 LLM tool loop**；行情证据以预加载快照注入 prompt；后续可加"行情查询工具" |
| 12 | 触发方式 | 手动点"运行一轮" + 每 10 分钟自动跑 |
| 13 | 核心页面 | 权益曲线 + 当前仓位（核心）、AI 决策链、订单/成交、每日复盘、账户/资金分配 |
| 14 | 移除项 | 策略决策、策略通道、漏斗/策略评价等策略相关 UI 全部移除 |
| 15 | 视觉 | 全新现代交易终端风格，深色、高信息密度、桌面优先 |
| 16 | 使用场景 | 本机单用户；价格 1s、状态 10~15s 级刷新（细节由设计定） |
| 17 | 历史数据 | 旧 SQLite 只读参考；新工作台使用**新账本/新曲线**，不混入旧 demo 历史 |

## 3. 明确不做（v1 非目标）

- 实盘接入、live API key、真实资金下单
- 外部 LLM API（原项目 SenseNova/DeepSeek 网关、OpenAI 兼容网关等）
- LLM tool loop / 多轮工具调用（预留后续扩展）
- 策略决策模块、策略通道、策略漏斗、策略评价
- 回测与历史重放（v1 只做前向 Demo 验证）
- 多用户、远程访问、公网鉴权（v1 本机单用户）
- 移动端适配（桌面优先）

## 4. Agent 链（角色已确认，契约待设计）

| 顺序 | Agent | 职责 | 输入 | 输出 | 推理档 |
|---|---|---|---|---|---|
| 1 | 分析 agent | 技术面 + 交易面分析；合并原情报角色 | 多周期行情、指标、账户/仓位、近期交易 | 结构化分析：趋势、关键位、形态、动能、可交易性 | 待设计 |
| 2 | 红队 agent | 做多论证（结构、触发、失效点、目标） | 分析结论 + 行情证据 | 多头论点 + 交易计划草案 | 待设计 |
| 3 | 蓝队 agent | 做空论证（同上） | 分析结论 + 行情证据 | 空头论点 + 交易计划草案 | 待设计 |
| 4 | 决策者 agent | 是否交易；选红队或蓝队方向 | 分析 + 红蓝双方论点 | 决策 JSON：trade/no_trade、方向、信心、理由 | 待设计 |
| 5 | 风控 agent | 审核、否决、降仓 | 决策 + 账户/风险状态 + 硬规则结果 | 风控结论：approve/reject/downsize + 理由 + 限额 | 待设计 |
| 6 | 操盘手 agent | 把决策转成订单计划并跟踪 | 已批准决策 + 风控结论 | 订单计划 JSON；持仓跟踪结论 | 待设计 |
| 7 | 复盘 agent（每日） | 当日归因、经验沉淀 | 当日决策/成交/权益 | 复盘报告 | 待设计 |

说明：
- 红队/蓝队默认理解为"红队=做多、蓝队=做空"，最终以设计文档确认。
- 风控是"AI 建议 + 硬规则双保险"，硬规则由确定性代码实现，AI 不能突破。
- 具体 JSON schema、prompt、并行/串行、超时/重试、成本预算由设计任务产出。

## 5. 技术边界（设计必须遵守）

1. **AI 只在 Harness 内**：插件 Host 侧通过 Harness 的 LLM 服务调用；Client 侧不直接调模型。
2. **Demo-only 硬隔离**：任何非 `demo-fapi.binance.com` 的 base URL 必须拒绝启动/拒绝下单；
   配置中不得出现 live 密钥路径。
3. **密钥安全**：币安 Demo key 只放本机 `.env`/凭据存储，不进入插件配置、日志、设计文档、
   前端 bundle；日志脱敏。
4. **AI 输出必须结构化校验**：模型输出 JSON 后由代码做 schema 校验；校验失败走 no_trade/
   重试，不允许把自由文本直接当订单。
5. **订单安全**：客户端订单 ID 幂等；开仓必须带初始 SL/TP；下单前做硬风控；
   成交/持仓以交易所对账为准。
6. **行情数据**：币安 USD-M 公共数据；10 分钟慢循环 + 30 秒快循环；限流/418/429 处理；
   数据过期必须显式降级，不允许用陈旧数据下单。
7. **可审计**：每轮保存输入证据快照、各 agent 输出、风控结论、订单/成交、权益快照，
   UI 决策链可回看。
8. **原项目只读**：可以阅读/评估复用 `multi-agent-trader` 的指标、Broker、风控代码，
   但不修改、不启动其服务、不使用其运行数据目录写入。

## 6. 设计必须回答的问题

1. **插件与服务边界**：AI 编排放插件 Host；行情/撮合/账本/风控放本地 Python 服务，
   还是全部放插件？给出对比与推荐。
2. **Demo 执行复用**：复用现有 `BinanceFuturesBroker`/`PaperBroker`/审计库，还是新写轻量
   Demo 适配器？给出理由、改造量、风险。
3. **账户与账本**：使用现有 Demo 账户还是独立 Demo 子账户？本地账本如何对齐交易所权益？
   旧 demo 历史如何隔离？
4. **AI 契约**：6 个 agent 的 system/user prompt 结构、输入证据格式、输出 JSON schema、
   推理档位、并行策略、超时/重试、token/费用预算。
5. **红蓝辩论机制**：各 1 轮的具体流程、是否互相可见对方论点、决策者如何裁决、
   如何防止"和稀泥"或方向漂移。
6. **风控硬规则**：单笔风险、杠杆、最大持仓数、日亏、SL/TP 强制、最小名义、数据新鲜度、
   重复下单、异常行情等具体阈值与执行位置。
7. **行情与指标**：币种池、周期、指标集、证据快照结构、限流策略、数据质量标记。
8. **UI/IA**：页面结构、决策链可视化、实时刷新、空态/离线/过期/运行中状态、
   DSH 主面板与侧栏入口的注册方式、主题与中英文。
9. **进程与部署**：Python 服务如何启动/停止/健康检查；插件如何发现服务离线；
   端口、配置、日志、升级。
10. **失败路径**：Demo 不可用、LLM 超时、JSON 解析失败、下单部分成交、保护单失败、
    重复周期触发等场景的处理。

## 7. 设计交付物与验收

最终交付 `trading-workbench/docs/v1-设计方案.md`，必须包含：

- 架构图（组件、职责、数据流、一轮完整时序）
- 插件 Host/Client 结构、服务 API、状态模型/存储 schema 概览
- 6 个 agent 的输入输出契约（JSON 示例）、推理档、prompt 要点
- 风控硬规则表（阈值、执行点、失败行为）
- 币安 Demo 订单生命周期、对账、异常处理
- 行情/指标管线、证据快照 schema、刷新与限流
- UI 信息架构、页面/组件清单、关键状态
- 安全边界（demo-only、密钥、AI 输出、下单幂等）
- 里程碑拆分（M1 最小闭环 / M2 完整 UI / M3 复盘与优化）
- 未决问题清单（需要用户拍板的项）

设计评审必须给出：跨文档矛盾、遗漏、过度设计、风险与修正建议。
