## 0. 结论

1. **服务端这一半做得扎实，可以直接复用。** 确定性原语求值、P1/P2 两次服务端复核（`validate_entry`）、信号去重（`reserve_signal`）、执行租约、单次审批令牌、策略熔断、否决的事后回测都已经有了。
2. **Host 编排这一半有结构性问题。** 规则直通（rule_direct）号称“0 LLM 延迟”，但只在 10 分钟调度槽里求值；AI 辅助（ai_assisted）把一个确定性信号送进 8 角色辩论；多个候选时用 LLM 来选；触发是“水平”语义，频率和连亏风控默认关闭，存在反复入场的风险。
3. **生产库里从来没有挂载过策略**（`strategies` 表为空，`strategy_config` 为 `native / revision 0`），这条链路只在测试里跑过。所以现在重构几乎没有迁移负担。
4. **v3.1 的核心做法**：把“用户挂载的策略”和“AI 研判产出的 setup”统一成**可执行规则（Armed Rule）**，由一个独立的**触发引擎**（Host 定时器，15s / K 线收盘后 3s）驱动，共用服务端那一套求值和 P1/P2 复核。研判循环只负责产出 setup，不持有租约、不下单。

## 1. 现状链路（逐步，带代码位置）

### 1.1 挂载生命周期
```
草稿 PUT /strategies/{id}/draft
  → AI 澄清 strategies.js StrategyAssistant.analyze（LLM，45s，产出 rules）
  → 挂载 POST /strategies/{id}/mount（不可变版本，SQLite 触发器禁止改删 strategy_versions）
  → 授权 POST /strategies/{id}/authorization（enabled + generation CAS）
  → 运行模式 PUT /strategies/config {mode: native|mounted, revision CAS}
```
校验在 `strategies/validation.py:119-196`：7 种原语（`mark_threshold / candle_close / ema_cross / ema_compare / rsi_threshold / funding_threshold / all`），`all` 最多 4 个子条件；标的必须在 20 币白名单内。表达不了的条件 `execution_ready=false`，不能启用。**这一段设计正确，保留。**

### 1.2 执行链路
```
scheduler.js 每 10 分钟一个槽（symbol 固定 BTCUSDT）
  → preflight()（integration.js:3476）：有持仓 → POSITION_OPEN → 整轮跳过
  → run()：acquireLease → snapshot
     有持仓分支（:4007）……（自动调度不会进到这里）

       POST /strategies/evaluate-candidates（api/strategies.py:204）→ candidates / skipped
       StrategyAssistant.choose（strategies.js）：候选 >1 时调用 LLM 选一个（20s，350 token）
```

## 2. 问题清单

| # | 级别 | 问题 | 证据 | 后果 |
| --- | --- | --- | --- | --- |
| S1 | 高 | **策略只在 10 分钟槽里求值** | `evaluate-candidates` 只在 `integration.run()` 里调用，`run()` 只由 `scheduler.js:310` 每 10 分钟触发 | rule_direct 最长延迟 10 分钟；`mark_threshold` 在两个槽之间满足又回落就错过了。和 README 写的“0 LLM 延迟”不符：省掉的是模型延迟，没省掉调度延迟 |
| S2 | 高 | **水平触发 + 频率、连亏风控默认关闭** | `compute_signal_key` 只按时间分桶（`evaluator.py:173-184`）；`risk/config.py:258-259` 中 `enable_loss_streak=False`、`enable_frequency=False` | 条件持续成立时，每个新时间桶都是一个新信号。止损出场后，下一个 15m 桶就可能按同一条件再次入场，连续止损。示例策略 `mark_threshold gt 100` 在 BTC 上永远成立 |

| S9 | 低 | 旧版回退路径只支持 `mark_threshold` | `strategies.js eligibleStrategies` | 404 回退时其他原语全部失效，可以直接删掉 |

## 3. v3.1 目标架构

```
┌ 研判循环（LLM，每 10 分钟 / 平仓后 / 异动事件）
│   筛选（代码）→ analyst（LLM）→ critic（LLM）→ 评分 + 风控折扣（代码）
│   → POST /api/setups  ……不持有租约，不调用 P1/P2
│
├ 触发引擎（代码，Host 定时器）
│   mark 类：每 15s；K 线类：每根 K 线收盘后 +3s
│   POST /api/rules/scan → triggered[]（服务端已按确定性优先级排序）
│   对第一个（max_open_positions = 1）：
│     acquireLease → POST /api/cycles {purpose:'trigger', symbols:[sym]}
│     → P1（rule_context）→ [confirm_mode=veto 时，调用一次 LLM 复核]
│     → P2 → finalize → release
│
└ 持仓循环（二期）：有持仓时研判切到 manage 模式，触发引擎只巡检保护单
```

### 3.1 为什么触发引擎放在 Host，而不是 service
- `execution/service.py:1388/1495` 的 P1、P2 都要求 `_assert_lease`，租约设计就是“Host 持有、服务端校验”（`lease.py` 文件头）。放在 service 里就得绕开租约和审批令牌，等于拆掉 A01/A02 两项修复。
- `confirm_mode=veto` 需要调用模型，模型路由在 Host（`llm-config.js`）。
- Host 已经有一条现成的“代码 → P1 → P2”路径（rule_direct），改造量最小。
- **服务端仍然是权威**：触发是否成立、setup 是否有效、能不能下单，最终都由 P1/P2 里的 `validate_entry` 用服务端的新鲜行情判定。Host 只负责“什么时候去问”。

### 3.2 为什么触发时要新建一个 cycle
P1 的 R14 要求决策证据 ≤ 400s（`risk/config.py:241`）。setup 的有效期通常是 1–2 小时，所以触发时必须重新生成证据。实测 `POST /api/cycles` 从轮次开始到证据生成，中位约 0.3s，最长 5.2s（11-14/15 共 33 轮）；单币快照会更快。

**定稿修订 R2**：`cycles/service.py:510-518` 全局只允许 1 个 RUNNING cycle，研判（30–100s）会挡住触发。`cycle_runs` 增加 `purpose`（`research` / `trigger` / `manual`），按 purpose 各允许 1 个 RUNNING；触发引擎遇到 `E_CYCLE_RUNNING` **不得**像 `integration.js:4107-4123` 那样结束对方的 cycle，只能等待并重试，或者放弃本次派发。

## 4. 数据结构

### 4.1 统一的规则上下文 `rule_context`（替换 `strategy_context`）
```jsonc
// 用户策略（与现有 strategy_context 字段一一对应，加一个 kind）
{ "kind": "strategy", "strategy_id": "…", "version": 3, "generation": 7, "mode_revision": 2, "signal_key": "15m:1994…" }
// AI setup
{ "kind": "setup", "setup_id": "stp-20261122T101500Z-3f9a1c", "generation": 1, "signal_key": "setup:stp-…" }
```
- P1/P2 按 `kind` 分派：`strategy` 走现有 `validate_entry`；`setup` 走新的 `validate_setup_entry`。
- 过渡期继续接受 `strategy_context`，服务端内部转换成 `kind=strategy`。
- setup 的 `signal_key` 固定为 `setup:<id>`：**一个 setup 一生只能成交一次**，复用 `strategy_signals` 的唯一约束。

### 4.2 退出参数统一 `exit`
```jsonc
{ "mode": "pct",   "stop_loss_pct": 0.012, "take_profit_pct": 0.024, "time_stop_hours": 24 }   // 用户策略（现状）
{ "mode": "price", "stop_loss": "74120",   "take_profit": "72600",   "time_stop_hours": 12 }   // AI setup：结构位
```
`mode=price` 在触发时用当时的标记价复算：止损距离必须在 0.2%–5%（R09），盈亏比 ≥ `min_rr_at_fill` 且 ≥ 1.2（R10）。

### 4.3 入场接受条件：用“追价上限 + 成交时盈亏比”替代入场区
现在的 `entry.zone_low/high` 是模型拍出来的区间，87% 的区间在生成那一刻就不包含现价（17 号文档 D5）。改成两个确定性约束：
- `max_chase_bps`：触发时的标记价相对触发参考价（触发原语的阈值，或触发时刻所在 K 线的收盘价）最多偏离多少，默认 15bp，上限 50bp。
- `min_rr_at_fill`：按实际标记价复算的盈亏比下限，默认 1.5。

这比“是否在区间内”更贴近真实问题：**追得越远，盈亏比越差**，直接卡盈亏比就够了。

### 4.4 Setup 卡（analyst 输出，schema `setup/1`）
```jsonc
{
  "schema_version": "setup/1",
  "symbol": "BTCUSDT",
  "side": "short",
  "timeframe": "15m",
  "entry": { "kind": "all", "side": "short", "conditions": [
      { "kind": "candle_close", "operator": "lt", "value": 73000 },
      { "kind": "ema_compare", "fast": 1, "slow": 20, "operator": "lt" } ] },
  "invalidation": { "kind": "candle_close", "operator": "gt", "value": 73980 },  // 同一套原语，满足就作废
  "exit": { "mode": "price", "stop_loss": "73980", "take_profit": "71200", "time_stop_hours": 12 },
  "max_chase_bps": 15,
  "min_rr_at_fill": 1.5,
  "risk_pct": 0.5,
  "leverage_cap": 3,
  "valid_for_minutes": 120,                    // 服务端换算 expires_at_ms，上限 240
  "thesis": "1h 区间下沿 73000 失守后的延续……",   // ≤ 400 字
  "evidence_refs": ["ev:BTCUSDT:15m:close", "ev:deriv:oi"],
  "unsupported_conditions": []                 // 原语表达不了的条件如实列出；非空则不能挂起
}
```
- `entry` / `invalidation` **直接复用** `validation.py::_validate_entry`，不新增原语。
- analyst 每次研判最多输出 2 张卡（每个候选标的最多 1 张）。

### 4.5 Critic 输出（schema `setup_review/1`）
```jsonc
{ "schema_version": "setup_review/1", "setup_ref": 0,
  "verdict": "pass" | "tighten" | "veto",
  "tighten": { "risk_pct": 0.3, "valid_for_minutes": 60, "min_rr_at_fill": 2.0 },   // 只能收紧，服务端校验
  "fatal_flaws": [{ "code": "TREND_CONFLICT", "evidence_ref": "ev:BTCUSDT:4h:ema" }],
  "reason": "…" }
```

### 4.6 SQLite（service，增量迁移，沿用 `strategies/schema.py` 先备份再迁移的做法）
```sql
CREATE TABLE IF NOT EXISTS setups (
  setup_id TEXT PRIMARY KEY,                 -- stp-<UTC>-<6hex>
  source TEXT NOT NULL CHECK(source IN ('ai_research')),
  research_cycle_id TEXT NOT NULL,           -- 研判轮的 cycle，可追溯证据
  evidence_sha256 TEXT NOT NULL,
  symbol TEXT NOT NULL, side TEXT NOT NULL CHECK(side IN ('long','short')),
  timeframe TEXT NOT NULL,
  entry_json TEXT NOT NULL, invalidation_json TEXT, exit_json TEXT NOT NULL,
  max_chase_bps INTEGER NOT NULL, min_rr_at_fill REAL NOT NULL,
  risk_pct TEXT NOT NULL, leverage_cap INTEGER NOT NULL,
  priority REAL NOT NULL,                    -- 见 §6.3
  card_json TEXT NOT NULL, review_json TEXT NOT NULL, scorecard_json TEXT NOT NULL,
  prompt_versions_json TEXT NOT NULL,
  armed_at_ms INTEGER NOT NULL, expires_at_ms INTEGER NOT NULL,
  state TEXT NOT NULL CHECK(state IN ('armed','triggered','dispatched','filled',
                                      'expired','invalidated','superseded','cancelled','rejected')),
  state_reason TEXT, generation INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
-- 同一标的同一方向同时只能有一个 armed：新卡进来时旧卡转为 superseded
CREATE UNIQUE INDEX IF NOT EXISTS uq_setups_armed ON setups(symbol, side) WHERE state = 'armed';
CREATE INDEX IF NOT EXISTS idx_setups_state ON setups(state, expires_at_ms);
-- 交易参数在入库后不可改
CREATE TRIGGER IF NOT EXISTS setups_core_immutable
 BEFORE UPDATE OF entry_json, invalidation_json, exit_json, symbol, side, risk_pct, max_chase_bps, min_rr_at_fill ON setups
 BEGIN SELECT RAISE(ABORT, 'setup trading parameters are immutable'); END;

CREATE TABLE IF NOT EXISTS setup_events (       -- 只追加
  event_id TEXT PRIMARY KEY, setup_id TEXT NOT NULL, from_state TEXT, to_state TEXT NOT NULL,
  reason_code TEXT, facts_json TEXT NOT NULL, cycle_id TEXT, at_ms INTEGER NOT NULL
);

-- 边沿触发状态（用户策略和 setup 共用）
CREATE TABLE IF NOT EXISTS rule_eval_state (
  rule_key TEXT NOT NULL,                     -- strategy:<id>:<ver> 或 setup:<id>
  symbol TEXT NOT NULL,
  last_matched INTEGER NOT NULL, last_eval_ms INTEGER NOT NULL,
  last_bar_open_ms INTEGER, cooldown_until_ms INTEGER,
  PRIMARY KEY(rule_key, symbol)
);
```
- `strategy_signals` / `strategy_decisions` **不改表结构**。setup 写入时 `strategy_id='setup:<id>'`、`version=1`，现有的去重、归因和否决回测查询都能直接覆盖。
- **定稿修订 R4**：上一条里只有**去重**能直接复用。`attribution.py:list_attribution` 只遍历 `strategies` 表，否决回测的 `_rules_for` 读的是 `strategy_versions`，所以 setup 的归因、否决回测和熔断要扩展：按来源 `ai_research` 汇总成虚拟策略 + 每个 setup 一行；规则从 `setups` 表读取；AI setup 整体连亏时暂停挂起新 setup。
- `strategy_versions` 新增可选字段 `rules.trigger_semantics: 'edge'|'level'`。新挂载默认 `edge`，旧版本保持 `level` 并在界面上提示。

## 5. 接口

### 5.1 Service（新增 / 修改）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/setups` | body `{research_cycle_id, cards:[setup/1], reviews:[setup_review/1], scorecards:[…]}`。服务端逐张：schema → 原语校验 → `unsupported_conditions` 必须为空 → critic 为 veto 的不入库 → 合并 tighten（只能更紧）→ 用当前标记价做一次预检（止损距离、盈亏比；**当前已满足触发条件的卡拒绝挂起**，`E_SETUP_ALREADY_TRIGGERED`，防止研判一出来就追单）→ 同标的同方向的旧卡转 `superseded` → 落库为 `armed`。返回 `{armed:[id], rejected:[{index, code, detail}]}` |
| GET | `/api/setups?state=armed&limit=20` | 列表，供界面和 Host 使用 |
| POST | `/api/setups/{id}/cancel` | 人工撤销，需要 `generation`（CAS） |
| POST | `/api/rules/scan` | body `{now_ms, scope:'mark'|'kline'|'all'}`。对所有已启用的用户策略和 armed setup 逐条求值。**副作用只有**：armed→expired / invalidated，以及更新 `rule_eval_state`（幂等）。返回 `{triggered:[{rule_context, symbol, side, mark, trigger_ref, priority, facts}], waiting:[{rule_key, symbol, distance_pct}], transitioned:[…]}`。`triggered` 已按 §6.3 排好序，并且已排除冷却中、已消费的规则。`/strategies/evaluate-candidates` 保留为兼容别名 |
| POST | `/api/cycles` | 新增可选 `{purpose:'trigger', symbols:[sym]}`，只生成单币证据，满足 R14 |
| POST | `/api/risk/evaluate`（P1） | 接受 `rule_context`。`kind=setup` 时调用 `validate_setup_entry`：状态 armed 且未过期 → 失效条件未满足 → 用新鲜标记价 / K 线重新求值触发原语 → 追价 ≤ `max_chase_bps` → 按 `exit.mode=price` 复算止损距离和盈亏比 → 用 setup 的价格生成计划 → CAS `armed→triggered`（generation+1）。仓位只由服务端计算，**忽略请求体里的 qty** |
| POST | `/api/execution/order`（P2） | 消费令牌 → `validate_setup_entry` 再复核（不做状态迁移）→ `reserve_signal`（`signal_key=setup:<id>`，一次性）→ 下单 → `dispatched→filled/rejected`。P2 失败时 setup 停在 `rejected`，**不自动重新挂起** |

新增错误码：`E_SETUP_NOT_ARMED`、`E_SETUP_EXPIRED`、`E_SETUP_INVALIDATED`、`E_SETUP_CHASE_EXCEEDED`、`E_SETUP_RR_DEGRADED`、`E_SETUP_ALREADY_TRIGGERED`、`E_SETUP_UNSUPPORTED_CONDITION`、`E_RULE_COOLDOWN`。

### 5.2 Host

**新文件 `host/trigger-engine.js`**
```js
export const TRIGGER_ENGINE_DEFAULTS = Object.freeze({
  enabled: false,              // 阶段 2 影子运行时为 shadow
  mode: 'off' | 'shadow' | 'live',
  markIntervalMs: 15_000,
  klineCloseDelayMs: 3_000,
  confirmMode: 'off' | 'veto', // veto：触发后调用一次 trigger_confirm
  confirmTimeoutMs: 15_000,    // 超时一律视为否决（fail-closed）
  maxDispatchPerTick: 1,
})
class TriggerEngine {
  constructor({ integration, client, llm, config, logger, now })
  start(); stop()
  async tick(scope)            // 'mark' | 'kline'
  async dispatch(triggered)    // 租约 → cycle → P1 →（复核）→ P2 → finalize，写 data/rounds（trigger='rule'）
  status()                     // 供界面：上次扫描时间、armed 数、等待中最近距离、上次触发
}
```
- shadow 模式：只调 `/rules/scan` 并写归档（`outcome='shadow_triggered'`），不拿租约、不调 P1/P2。
- 一次 `dispatch` 的归档沿用现有 round 记录结构（`cycleSource='trigger'`），界面的“历史”页不用改。

**研判循环（改 `integration.run`）**
- 新增链路变体 `CHAIN_VARIANTS.SETUP = 'setup'`：筛选 → analyst → critic → 评分卡 → `POST /api/setups`。
- 变体为 `setup` 时，**不 acquireLease、不调用 P1/P2**，`outcome` 记为 `setups_armed:N` 或 `no_setup`。
- mounted 和 native 不再互斥：研判循环照常运行，用户策略交给触发引擎。

**`trigger_confirm`（替换 ai_assisted 的 8 角色链）**
- 输入：规则或 setup 卡、触发事实（标记价、K 线、指标）、单币证据切片（≤ 1,200 token）。
- 输出 `trigger_confirm/1`：`{verdict:'proceed'|'veto', reason_code, evidence_refs, note}`，`max_tokens 600`，推理档位 `low`。
- 被否决时照常写 `strategy_decisions(outcome='ai_vetoed')`，现有的 `_evaluate_veto_counterfactuals` 会自动统计“避险成功 / 踏空”。

**删掉的东西**
- `StrategyAssistant.choose()`：改由服务端确定性排序。
- rule_direct 分支里 Host 端的 qty / equity 计算（`integration.js:4462-4493`）。
- `eligibleStrategies` 旧版回退。

## 6. 关键规则

### 6.1 Setup 状态机
```
            POST /api/setups
                 │
              armed ──scan:到期──────────▶ expired
                 │  ──scan:失效条件满足───▶ invalidated
                 │  ──新卡同标的同方向────▶ superseded
                 │  ──人工撤销────────────▶ cancelled
                 │
            P1 通过（CAS）
                 ▼
             triggered ──P1 后超过审批 TTL（默认 120s，上限 300s）未提交──▶ rejected（令牌过期）
                 │
            P2 reserve
                 ▼
            dispatched ──成交──▶ filled
                      └─失败──▶ rejected（不自动重挂）
```

### 6.2 边沿触发与冷却（解决 S2）
- 只有当规则在某标的上从 `last_matched=0` 变为 1 时才产生触发；首次求值就为真的，只记状态、不触发（和 `E_SETUP_ALREADY_TRIGGERED` 同一个道理：不追已经发生的信号）。
- 规则开出的仓平掉后，`cooldown_until_ms = 平仓时间 + max(1 个周期, 30 分钟)`。
- **定稿修订 R5**：
  - **停机保护**：`rule_eval_state.last_eval_ms` 距今超过 3 个扫描间隔时，本次求值按“首次求值”处理，只更新状态、不触发，防止 Host / DSH 重启后迟到入场。
  - **重新武装**：规则派发过一次后（无论 P1 / P2 结果如何），必须观察到一次“不满足”才能再次产生边沿；P1 拒绝后额外冷却 1 个周期。周期桶去重（`compute_signal_key`）继续叠加生效。
  - **心跳**：触发引擎每次扫描写 `last_scan_at`，超过 60s 没有扫描就在界面上告警。
- **建议同时打开**挂载模式下的 `WORKBENCH_RISK_ENABLE_FREQUENCY`（单标的每天 3 次、全天 12 次）和 `WORKBENCH_RISK_ENABLE_LOSS_STREAK`（连亏冷却 4 小时）。这两项是现成的 R20 / R21，只是默认关着。

### 6.3 确定性优先级（替换 LLM 选择，解决 S4）
`/rules/scan` 按以下顺序排 `triggered`：
1. 用户策略优先于 AI setup（用户明确授权的规则比模型提案优先级高）；
2. 同类内按 `priority` 降序。用户策略取挂载时设定的 `priority`（默认 0），AI setup 取 `评分卡分 × critic 系数（pass 1.0 / tighten 0.8）`；
3. 再按 `armed_at_ms` 升序（先挂起的先执行）；
4. 每次扫描最多派发 1 个（受 `max_open_positions=1` 限制），没被选中的继续排队，下次扫描再判断。

### 6.4 有持仓时（解决 S6，二期补全）
- 触发引擎遇到有持仓：`triggered` 只记录、不派发。setup 保持 armed，直到过期。
- 研判循环在有持仓时切到 manage 模式。持仓管理链（接上 `execution_manage/1`）单独立项。
