# 代码维护规范

## 1. 目标

本规范用于降低多线程交易服务、交易所状态同步和 AI 决策链的维护风险。它吸收 Google
Python 编程指南中关于命名、文档、异常、导入和可读性的原则，同时保留项目现有架构。

## 2. 分层与依赖方向

```text
dashboard / scripts
        ↓
core.service / core.graph
        ↓
agents / signal_engine / intel
        ↓
exchange / data / audit
```

- `dashboard` 只负责展示和受保护的控制入口，不拥有交易规则。
- `core` 编排生命周期、资金、通道和确定性闸门。
- `agents` 产出结构化候选决策，不能绕过风控直接操作 Broker。
- 新开仓只能由 `core.graph` 的统一管线签发；RiskGuard 调整后对实际执行集合签名，
  Broker 工厂创建的实例必须验证签名。快循环只可提交 `no_trade` 以维护挂单和保护。
- `exchange` 是交易所边界，负责签名请求、幂等、镜像、对账和保护单。
- `audit` 是追加式审计边界；迁移必须向前兼容并有独立冒烟测试。
- `intel` 是只读侧车，当前不进入执行决策权重。

禁止形成从底层模块反向导入 Dashboard 或服务实例的依赖。

## 3. 注释与 docstring

核心类 docstring 至少说明：职责、线程模型、持久化状态和不能破坏的不变量。公开方法说明
输入口径、返回值、副作用和失败策略。局部注释只写以下内容：

- 交易所语义与本地语义不一致处；
- 并发锁的保护范围和锁顺序；
- 资金、价格、数量、百分比、毫秒等单位；
- 失败后为何重试、降级、阻断或继续；
- 看似可删、实际承担安全边界的代码。

不写“把变量加一”这类复述代码的注释。注释发生漂移时视为缺陷处理。

## 4. 命名与结构

- 文件、函数、变量使用 `snake_case`，类使用 `CapWords`，常量使用 `UPPER_CASE`。
- 布尔变量优先使用 `is_`、`has_`、`allow_`、`should_` 前缀。
- 带单位的数据写入名称，例如 `timeout_seconds`、`latency_ms`、`fee_bps`。
- 单个函数应只有一个主要职责；超过约 80 行时优先抽取纯函数，但不得为满足行数机械拆分。
- 交易所原始字段只停留在边界层；进入核心决策前转换为项目模型或明确口径的字典。

## 5. 异常与日志

- 禁止无说明的 `except Exception: pass` 出现在资金、下单、风控和状态写入主路径。
- 可恢复的公开行情/情报错误应保留最后有效值并标记 degraded。
- 下单结果不确定必须进入 Outbox `UNKNOWN`，不得盲目重试创建第二张订单。
- 状态不一致写入风险事件；同类持续故障由 incident 聚合，不删除原始审计。
- 日志不得包含 API secret、签名、Authorization 头或完整 `.env`。

## 6. 测试隔离

- 单元和冒烟测试使用 `tempfile` 创建项目根与数据库。
- 测试中不得实例化指向真实项目根的 `TradingService`。
- 网络测试与真实账户诊断必须显式命名为 `probe_`/`verify_*_live`，不进入默认回归集。
- 所有维护性提交至少通过语法编译、风险档锁、服务生命周期和 UI 隔离测试。
- 涉及决策或 Broker 的提交必须运行 `scripts/check_execution_boundaries.py`；新增直接
  `broker.execute` 调用视为架构缺陷，退出/保护恢复脚本须使用既有明确接口。

## 7. 脚本与运行产物边界

`scripts/` 按意图而不是按“是否能运行”分类：

- `run_*` 是受支持的启动或离线编排入口；`smoke_*`、`test_*`、`check_*` 是可重复、
  默认离线的回归与门禁入口；
- `create_recovery_bundle.py` 与 `restore_recovery_bundle.py` 是受支持的恢复工具。恢复先
  dry-run，且只能写入不存在的新目录；
- `probe_*`、`verify_*_live`、`diag_*` 是显式在线查询或本地诊断工具，不进入默认 CI；
  其输出、请求转储和账户快照必须写入 `data/` 或系统临时目录，不得写回源码目录；
- `cleanup_*`、`repair_*` 属于有副作用的维护工具。默认必须是预览或要求显式确认，输出
  运行环境摘要、精确目标、执行结果和后置核验；不能以“清理”为理由删除 UNKNOWN、
  历史审计、用户诊断脚本或运行状态。

新脚本从本地诊断提升为受支持入口时，必须补充中文模块说明、参数说明、临时目录/凭据
隔离以及相应冒烟用例。已有未跟踪诊断脚本属于操作者本地资产：本轮不自动移动、删除或
提交，纳入版本控制须单独审查其副作用与敏感数据处理。

## 8. 分批执行策略

1. 清理无引用的一次性脚本和过时文档。
2. 建立格式、静态检查和提交规范。
3. 为资金、风险、订单、保护单、服务生命周期补齐中文契约注释。
4. 将超大模块按稳定边界拆分；每次只迁移一个职责并保持 API 兼容。
5. 最后提高静态检查强度，禁止新增未使用导入、危险异常吞噬和循环依赖。

任何阶段都不得借“代码整理”改变风险参数、仓位上限、杠杆、白名单或情报执行权重。

## 9. 依赖与可复现构建

- `requirements.txt` 和 `requirements-dev.txt` 只声明允许升级范围。
- 本地部署与 CI 必须使用 `requirements-lock.txt` 或 `requirements-dev-lock.txt`。
- `scripts/verify_dependency_lock.py` 必须验证直接约束、当前平台传递闭包、已安装版本和
  `pip check`；质量门禁默认调用它。
- 当前锁在 Windows AMD64 / CPython 3.13 生成，并由 Windows / CPython 3.11 CI 再验证。
- 更新依赖必须整体重建锁、记录平台与 Python 版本并执行完整离线回归；不得在运行服务
  的虚拟环境中临时升级后跳过锁文件。

## 10. 性能基线

- 先测量再优化；行数多、数据库大或请求慢都不能单独证明瓶颈位置。
- `scripts/benchmark_runtime_baseline.py` 提供健康纯函数与临时 SQLite 读写的同机对照；
  它不访问真实账户、不进入默认 CI，也不产生交易阈值。
- 端到端 `/api/status`、快循环和交易所 API P95 必须从 Demo 观察窗口采样，记录环境、
  样本量、P50/P95/最大值和错误率。涉及缓存或并发的优化必须同时验证陈旧标记与恢复。

## 11. 发布包与打包清单维护

发布包（`scripts/create_release_package.py`）是**代码部署工件**，不是恢复包、也不是备份。
维护它的规则比普通脚本更严：一个错误的排除规则会让部署缺少运行文件，而这类缺陷在
单元测试里通常看不见。

### 11.1 每个已跟踪文件都必须被归类

打包器对仓库盘点逐文件归类（`_classify`），**未归类文件即构建失败**。新增文件时按下面
的顺序落到某一类，不要靠"它看起来像不像运行文件"临时判断：

1. **排除**（`EXCLUDED_DIR_NAMES` / `EXCLUDED_TOPLEVEL_DIR_NAMES` / `EXCLUDED_FILE_NAMES` /
   `EXCLUDED_SUFFIXES` / `EXCLUDED_PATH_PREFIXES`）：运行状态、缓存、凭据、日志、数据库、
   密钥、既有工件、评审证据与流程台账。每一条都必须写明理由字符串。
2. **运行必需脚本**（`RUNTIME_SCRIPTS`，显式清单，优先级最高）：启动/托管、健康守望、
   实盘预检、发布门禁报告、迁移与恢复工具、自检依赖。
3. **运行资产**（`src/`、`config/`、`knowledge/`、`docs/`、`REQUIRED_*` 顶层文件）：
   一律进包，且**不允许**被任何路径规则排除——`build_release_package` 对
   `RUNTIME_ASSET_ROOTS` 有硬断言，被误伤即失败。
4. **source-only**（`tests/`、`.github/`、冒烟/门禁/诊断/维护脚本）：只进 `source` 包。
   `scripts/` 下的脚本**必须显式登记**才成为 source-only：命中
   `SOURCE_ONLY_SCRIPT_PREFIXES` 的某个前缀（`smoke_`/`test_`/`check_`/…）或被列入
   `RUNTIME_SCRIPTS`。两者都不命中即视为**未归类 → 构建失败**——不允许"默认 source-only"，
   否则新加的启动入口会被静默降级、runtime 包悄悄缺文件（U10a 修复的失效模式）。

### 11.2 排除规则必须写明作用层数

**教训（U10a 修复的真实缺陷）**：早期实现把 `data` 当作"出现在路径任意一层即排除"的
目录名，于是 `src/data/`（限流、传输、行情查询等数据接入层，13 个模块）与
`src/dashboard/templates/*.html`（8 个模板）被**静默丢出**发布包——解压后既没有数据层
也没有界面模板。

**表述更正（U10a r2，独立复核反证）**：同一次核对曾把 `git ls-files` 缺 `-z` 也列为
"漏中文名文档"的成因，**这是错的**。反事实实验：给旧实现补 `-z` 前后，输出成员集合为
**0 差异**——旧实现丢中文文档的真正根因是 `SAFE_DOCS` 白名单只有 5 篇。`-z` 是真缺陷，
但后果不同：缺 `-z` 时非 ASCII 路径被 C 风格转义成伪路径，在**新实现**（全量归类）下
命中不了任何规则，构建会以"存在未归类文件"**硬失败**（fail-closed），而不是静默少文件。

配套的两条硬约束（本轮补强）：

- **必需项存在性**：`RUNTIME_SCRIPTS`/`REQUIRED_*` 里的路径**必须存在于仓库**，否则
  `--out` 直接失败。不要写成 `... and (root / relative).exists()` 之类的过滤——那会让
  "入口被重命名/删除"变成**静默出包**（包内一个启动器都没有）。
- **不得有静默兜底归类**：`scripts/` 下的兜底不允许是"一律 source-only"；未显式登记的
  新脚本按未归类处理并让构建失败。

因此：

- 状态/产物目录（`data`、`logs`、`cache`、`dist`、`build`）只在**项目根第一层**排除；
- 缓存与版本库目录（`__pycache__`、`.git`、`.ruff_cache`、`.venv`）任何深度都排除；
- 任何新增"按名字排除"的规则，必须同时回答"哪一层"和"会不会与源码目录同名"。

### 11.3 打包器与自检是同一份判定

`build_release_package` 与 `verify_release_package` 共用排除清单、必需清单与凭据口径；
`--verify` 可在解压目录独立运行，且不写被测目录（导入前关闭字节码写入，子进程用
`PYTHONDONTWRITEBYTECODE=1`）——否则第二次自检会被自己产生的 `__pycache__` 判为
"出现未登记文件"。

### 11.4 变更清单时要同步的三处

改动运行必需文件集合或脚本用途分类时，必须同批更新：

1. `scripts/create_release_package.py` 的清单常量；
2. `docs/运行与故障恢复手册_2026-09-06.md` §3.1 的"runtime 包内含"一段
   （`scripts/smoke_u10a_release_package.py` 会逐项比对两份清单，漂移即回归变红）；
3. 依赖锁、策略卡、配置清单若同时变化，还要核对包内
   `src/core/release_manifest.py` 的 `SAFE_CONFIG_FILES` / `DEPENDENCY_FILES` /
   `STRATEGY_CARD_FILES`：构建期交叉核对不一致会直接失败，这是"改锁文件/改策略卡
   必然改变发布身份"（F13）在打包侧的落地。

### 11.5 凭据口径只有一份

发布包的凭据扫描复用 `scripts/scan_tracked_secrets.py`（同一登记表与 KI04 范围豁免），
不得在打包器里另写一套模式或另建豁免名单。要放宽必须同时改扫描器与台账 KI04，并说明
范围与理由；否则打包器会如实报红。包内不得出现 `data/`、`.env`、日志、密钥与任何
运行状态，自检失败即不得发布。

### 11.6 发布包不含未实现能力的声明

手册、索引与维护规范里每一句"能够做到 X"都必须在当前代码里指认到实现；发布包自检、
清单比对与相对文档链接检查会把"文档指向未打包内容"直接变成构建/自检失败，这是刻意
设计：文档漂移应在打包阶段暴露，而不是留给运维点开断链。
