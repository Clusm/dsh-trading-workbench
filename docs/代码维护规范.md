# 代码维护规范

## 1. 目标

本规范用于降低多线程交易服务、交易所状态同步和 AI 决策链的维护风险。它吸收 Google
Python 编程指南中关于命名、文档、异常、导入和可读性的原则，同时保留项目现有架构。

## 2. 分层与依赖方向

```text
dashboard / scripts
        ↓
core.service / core.graph
        ↓
agents / signal_engine / intel
        ↓
exchange / data / audit
```

- `dashboard` 只负责展示和受保护的控制入口，不拥有交易规则。
- `core` 编排生命周期、资金、通道和确定性闸门。
- `agents` 产出结构化候选决策，不能绕过风控直接操作 Broker。
- 新开仓只能由 `core.graph` 的统一管线签发；RiskGuard 调整后对实际执行集合签名，
  Broker 工厂创建的实例必须验证签名。快循环只可提交 `no_trade` 以维护挂单和保护。
- `exchange` 是交易所边界，负责签名请求、幂等、镜像、对账和保护单。
- `audit` 是追加式审计边界；迁移必须向前兼容并有独立冒烟测试。
- `intel` 是只读侧车，当前不进入执行决策权重。

禁止形成从底层模块反向导入 Dashboard 或服务实例的依赖。

## 3. 注释与 docstring

核心类 docstring 至少说明：职责、线程模型、持久化状态和不能破坏的不变量。公开方法说明
输入口径、返回值、副作用和失败策略。局部注释只写以下内容：

- 交易所语义与本地语义不一致处；
- 并发锁的保护范围和锁顺序；
- 资金、价格、数量、百分比、毫秒等单位；
- 失败后为何重试、降级、阻断或继续；
- 看似可删、实际承担安全边界的代码。

不写“把变量加一”这类复述代码的注释。注释发生漂移时视为缺陷处理。

## 4. 命名与结构

- 文件、函数、变量使用 `snake_case`，类使用 `CapWords`，常量使用 `UPPER_CASE`。
- 布尔变量优先使用 `is_`、`has_`、`allow_`、`should_` 前缀。
- 带单位的数据写入名称，例如 `timeout_seconds`、`latency_ms`、`fee_bps`。
- 单个函数应只有一个主要职责；超过约 80 行时优先抽取纯函数，但不得为满足行数机械拆分。
- 交易所原始字段只停留在边界层；进入核心决策前转换为项目模型或明确口径的字典。

## 5. 异常与日志

- 禁止无说明的 `except Exception: pass` 出现在资金、下单、风控和状态写入主路径。
- 可恢复的公开行情/情报错误应保留最后有效值并标记 degraded。
- 下单结果不确定必须进入 Outbox `UNKNOWN`，不得盲目重试创建第二张订单。
- 状态不一致写入风险事件；同类持续故障由 incident 聚合，不删除原始审计。
- 日志不得包含 API secret、签名、Authorization 头或完整 `.env`。

## 6. 测试隔离

- 单元和冒烟测试使用 `tempfile` 创建项目根与数据库。
- 测试中不得实例化指向真实项目根的 `TradingService`。
- 网络测试与真实账户诊断必须显式命名为 `probe_`/`verify_*_live`，不进入默认回归集。
- 所有维护性提交至少通过语法编译、风险档锁、服务生命周期和 UI 隔离测试。
- 涉及决策或 Broker 的提交必须运行 `scripts/check_execution_boundaries.py`；新增直接
  `broker.execute` 调用视为架构缺陷，退出/保护恢复脚本须使用既有明确接口。

## 7. 脚本与运行产物边界

`scripts/` 按意图而不是按“是否能运行”分类：

- `run_*` 是受支持的启动或离线编排入口；`smoke_*`、`test_*`、`check_*` 是可重复、
  默认离线的回归与门禁入口；
- `create_recovery_bundle.py` 与 `restore_recovery_bundle.py` 是受支持的恢复工具。恢复先
  dry-run，且只能写入不存在的新目录；
- `probe_*`、`verify_*_live`、`diag_*` 是显式在线查询或本地诊断工具，不进入默认 CI；
  其输出、请求转储和账户快照必须写入 `data/` 或系统临时目录，不得写回源码目录；
- `cleanup_*`、`repair_*` 属于有副作用的维护工具。默认必须是预览或要求显式确认，输出
  运行环境摘要、精确目标、执行结果和后置核验；不能以“清理”为理由删除 UNKNOWN、
  历史审计、用户诊断脚本或运行状态。

新脚本从本地诊断提升为受支持入口时，必须补充中文模块说明、参数说明、临时目录/凭据
隔离以及相应冒烟用例。已有未跟踪诊断脚本属于操作者本地资产：本轮不自动移动、删除或
提交，纳入版本控制须单独审查其副作用与敏感数据处理。

## 8. 分批执行策略

1. 清理无引用的一次性脚本和过时文档。
2. 建立格式、静态检查和提交规范。
3. 为资金、风险、订单、保护单、服务生命周期补齐中文契约注释。
4. 将超大模块按稳定边界拆分；每次只迁移一个职责并保持 API 兼容。
5. 最后提高静态检查强度，禁止新增未使用导入、危险异常吞噬和循环依赖。

任何阶段都不得借“代码整理”改变风险参数、仓位上限、杠杆、白名单或情报执行权重。

## 9. 依赖与可复现构建

- `requirements.txt` 和 `requirements-dev.txt` 只声明允许升级范围。
- 本地部署与 CI 必须使用 `requirements-lock.txt` 或 `requirements-dev-lock.txt`。
- `scripts/verify_dependency_lock.py` 必须验证直接约束、当前平台传递闭包、已安装版本和
  `pip check`；质量门禁默认调用它。
- 当前锁在 Windows AMD64 / CPython 3.13 生成，并由 Windows / CPython 3.11 CI 再验证。
- 更新依赖必须整体重建锁、记录平台与 Python 版本并执行完整离线回归；不得在运行服务
  的虚拟环境中临时升级后跳过锁文件。
