# 测试与验收矩阵（2026-09-16）

本页汇总当前**质量门禁、离线回归、Demo 诊断验收、版本化发布就绪、在线探针、生产写入**
六类入口的脚本行为、默认命令、读写网络分类与证据边界。内容取自脚本实现本身，只描述
“脚本会做什么”，**不表示任何检查已被执行或通过**。

> 证据规则：没有实际执行输出（退出码、报告 JSON、日志）时，不得声称任何门禁通过。
> 本页不是通过证明，也不能替代运行证据。

## 1. 总览

| 类别 | 入口 | 默认安全命令 | 读/写 | 网络 | 能否作为上线依据 |
|---|---|---|---|---|---|
| 质量门禁 | `scripts/check_quality.py` | `python scripts/check_quality.py` | 不读写运行账本；可能写编译/工具缓存 | 否 | 必要但不充分 |
| 离线回归（67 脚本） | `scripts/run_offline_regression.py` | `python scripts/run_offline_regression.py` | 只写临时目录 | 否（默认禁网） | 必要但不充分 |
| Demo 诊断验收 | `scripts/report_demo_acceptance.py` | `python scripts/report_demo_acceptance.py` | 只读数据库 | 否 | 样本诊断，不等于发布就绪 |
| 严格版本化发布就绪 | `scripts/report_release_readiness.py` | 见 §5 | 只读数据库 + 可选写报告文件 | 否 | 是（需 `--strict --manifest`） |
| 在线探针 | `probe_*` / `verify_*_live`（如 `scripts/verify_llm_provider.py`） | 不在默认门禁内 | 视脚本而定 | **是** | 只作显式人工验证 |
| 生产写入 | `cleanup_*` / `repair_*`、`restore_recovery_bundle.py` 等 | 无“默认安全命令” | **写状态** | 可能 | 必须先预览目标并准备后置核验 |

分类命名约定（与《文档索引》一致）：`smoke_*` 为隔离冒烟；`probe_*`、`verify_*_live`
可能联网；`diag_*` 默认只读；`cleanup_*`、`repair_*` 会改变状态。

## 2. 质量门禁：`scripts/check_quality.py`

- 扫描范围 = **Git 已跟踪** + **未跟踪但未被 `.gitignore` 排除**的 `*.py`。
  - 2026-09-15 修正：旧实现只读 `git ls-files`，导致“新增但未提交”的脚本完全不进入
    门禁，与 L00 第 1 条冲突；实际后果是曾出现 9 个既不在离线回归、也不在质量门禁内的
    诊断/修复脚本。
  - 未跟踪文件策略：**纳入检查，但不因未跟踪而失败**（报错应指向代码问题，而不是
    “文件还没 add”）。发布清单另有独立白名单校验。
- 依次执行：`ruff check <files>` → `py_compile <files>` → `scripts/verify_profile_lock.py`
  → `scripts/verify_dependency_lock.py` → `scripts/scan_tracked_secrets.py`。
- 任一子命令失败，退出码原样传播。
- 边界：不访问网络、不创建交易服务、不读取或修改运行状态；`py_compile` 或工具自身可能
  写本地缓存，因此不能把它描述成严格的文件系统只读操作。

## 3. 离线回归：`scripts/run_offline_regression.py`（67 脚本）

- 脚本数 **67**，含审计后补入的 15 个冒烟脚本（`smoke_step0` 起至
  `smoke_takeover_compatibility`），其中**已包含** `scripts/smoke_minimum_research_gate.py`
  这一最小研究门禁冒烟。
- 每个脚本以 `cwd = 仓库根目录`、`check=True` 顺序执行；全部通过后打印
  `OFFLINE REGRESSION OK scripts=67`。
- 运行前环境被强制收敛（保证离线、无凭据）：
  - `EXECUTION_MODE=paper`，移除 `MTA_PROFILE`，`MTA_NO_PROXY=1`；
  - `PYTHONUTF8=1`、`PYTHONIOENCODING=utf-8`（避免中文测试名在非 UTF-8 控制台被误报失败）；
  - 清除所有名字含 `BINANCE`/`SENSENOVA` 且含 `KEY`/`SECRET`/`TOKEN` 的环境变量。
- **显式排除** `scripts/smoke_p0c.py`：其第 [6] 节直接调用 `query_symbol_detail` /
  `query_symbol_cards` 打公共行情接口，无网环境必然以退出码 1 失败。待该节改为离线替身
  后再纳入统一回归。
- 边界：全程离线、只写临时目录；不读真实 `data/` 与 `.env`，不构造真实 Broker，
  不发网络请求。

## 4. Demo 诊断验收：`scripts/report_demo_acceptance.py`

- 以 SQLite **只读** URI（`mode=ro`）+ `PRAGMA query_only=ON` 汇总，不触发 schema 初始化。
- 需存在 8 张表：`schema_migrations`、`shadow_decisions`、`shadow_outcomes`、
  `trade_outcomes`、`orders`、`positions`、`risk_incidents`、`order_outbox`；缺失或 SQL
  错误一律**失败**，不得退化成 0。
- 样本门槛：方向性候选 ≥ 200、可归因闭合交易（`trade_outcomes` 中 `CLOSED` 且
  entry/exit/qty/时间齐全）≥ 30、观察跨度 ≥ 7 天。
- 运行门槛：`critical` 未关闭风险事件 = 0、`order_outbox` 中 `UNKNOWN` = 0、
  `SUBMITTING` = 0。
- **证据边界**：`filled_order_rows`（`orders` 为 `FILLED`）与 `closed_position_rows`
  （`positions` 为 `CLOSED`）**仅作诊断**，不能替代 `trade_outcomes` 的闭合交易归因门槛。
- 退出码：默认 0；`--strict` 必须同时提供 `--manifest`，否则报参数错误；schema/IO 错误
  返回 2。

## 5. 严格版本化发布就绪：`scripts/report_release_readiness.py`

按 `release_id` 隔离的严格门禁，与 Demo 诊断共用 `core.release_evidence` 的报告构建逻辑。

```bash
# 严格模式（示例）：不是 GO 返回 1，schema/IO 错误返回 2
python scripts/report_release_readiness.py \
  --db data/agent_trader.sqlite \
  --manifest <release_manifest 生成的 JSON 清单> \
  --environment demo --since <ISO 时间> --until <ISO 时间> \
  --strict --out reports/release_readiness.json
```

- `--manifest` 必填（`--strict` 时缺失即报错）；`--strict` 下 `release_readiness != "GO"`
  返回 1。未提供 `--manifest` 时退化为 Demo 诊断汇总，返回 0。
- `--out` **只写报告文件**（临时文件 + 原子替换），不写数据库。
- 边界：只读数据库、不联网、不修改交易状态。

## 6. 在线探针与生产写入（不属默认门禁）

- **在线探针**：`probe_*` / `verify_*_live` 命名，需网络。例如
  `scripts/verify_llm_provider.py` 是显式在线协议检查，不读账户、不下单。此类脚本只在
  人工明确发起时运行，其结果不能替代离线门禁。
- **只读在线核对**：`scripts/preflight_live_account.py` 只读核对账户模式、仓位、订单与
  保证金；`scripts/health_watch.py` 为不构造 TradingService 的只读监控。
- **生产写入**：`cleanup_*`、`repair_*` 会改变状态；`scripts/restore_recovery_bundle.py`
  只写新目录恢复，`scripts/create_recovery_bundle.py` 生成停写一致性恢复包。执行前**必须**
  先预览目标、确认授权，并准备后置核验；不在自动化默认链路中。

## 7. 验收顺序与结论口径

1. **质量门禁** `check_quality.py`（静态与凭据边界）。
2. **离线回归** `run_offline_regression.py`（67 脚本，离线行为回归）。
3. **Demo 诊断验收** `report_demo_acceptance.py`（只读样本与运行门槛汇总）。
4. **严格版本化发布就绪** `report_release_readiness.py --strict --manifest`（唯一可作为
   GO/NO-GO 判定的严格门禁）。
5. 必要时（且仅由人工发起）**在线探针**。
6. **生产写入脚本**仅在具备授权、已预览目标并准备后置核验时执行。

口径限制：

- 第 1–3 步通过只说明代码边界与离线行为健康、Demo 样本达标，**不构成上线就绪**。
- 只有第 4 步在 `--strict` 下输出 `GO`，且保留对应报告与退出码，才可作为发布依据。
- 本文档不记录任何一次实际执行结果；任何“已通过”的结论必须以现场执行证据为准。
