### 1.2 关键事实复核（与 captain 三个重点相关）

**事实 A：`ctx.llm.stream` 不要求 Session/Agent 上下文。**

- `@deepseek-ai/dsh-llm` README 的 minimal composition 示例是：
  `ctx.llm.stream({ provider, model, messages })`，没有 `sessionId`、没有 Agent、没有 Session。
- README 明确该服务面向“agent loop、session-title generator、compaction summarizer 等任何 composition/plugin”提供唯一模型调用面。
- `GenerateOptions.sessionId` 在 README 中被描述为 “locally-declared brand”（本地声明的品牌类型），`lib/index.js` 的 `stream` 实现没有读取/校验 `sessionId`；`usage` 走流式 `usage` chunk。
- 结论：**`02` §3.5 把 `sessionId` 设为“不得为空，否则启动失败”是自加约束，不是平台约束**；`02` §3.1 的 `createUserMessage` 也与 `01` 的零依赖路线冲突。DSH 侧可行性成立，但 M1 仍应装一个最小探针插件实测一次（见 §12 验收）。

**事实 B：红蓝“互不可见”是独立多空论证，不是交叉辩论。**

- `02` §7 的设计是“同一 `debate_input`、并行、互不可见、各 1 次调用、无第二轮”，并要求各自写 `opponent_steelman`（反方最强点）。
- 用户原话是“红队、蓝队各 1 轮陈述，然后决策者裁决”。按“陈述”的字面，这满足；按“辩论”的强解释（看到对方后回应一次），这不满足。
- `00` §4 的红/蓝输入明确是“分析结论 + 行情证据”，并未要求看对方论点，因此 `02` 的设计与需求基线一致。
- 结论：**v1 默认采用“独立多空论证（互不可见）”**；把“是否要看到对方后再回应一次”列为用户解释项（U-06），不擅自改第二轮。若改成“各回应一次”，成本/延迟会显著增加（见 §8.1 U-06）。

**事实 C：`05a` v2 的 DSH 结论必须覆盖 t5/01 的旧写法。**

- `locale`/`inject` 是通用注册选项，`main`/`sidebar.panellist` 的 `locale` 可以保留。
- `panelInfo` 可通过 scoped `layout` 服务使用；`usePanelInfo()` 仍未证实。
- `sidebar.toggle.badge` 是 **single** 槽，没有 `id`；v1 建议不使用。
- live theme token 只有 14 个；`05` §11.1 与 `01` §3.4 的大量 token 名不存在。

## 3. Findings（按严重级别）

> 每条格式：**问题** / **影响** / **必须修正** / **验收** / **v1 处置**。
> “必须修”指进入 t7 整合稿前必须改；“可后置”指不阻塞 M1，但要在整合稿里标注。

### 3.1 Blocker（6）

#### B-01 · A3 未落地：Host/服务/行情三方都在“调度一轮”

- **问题**：`01` A3（`01:1063`）明确“Host 持有调度权，`POST /api/cycles` 按需生成证据，t4 慢循环只做数据刷新”。但：
  - `04` §7.1（`04:302`）P3 仍写“数据刷新 → … → 交 AI 链 → 交执行”；§7.2 步骤 9（`04:319`）明确“交给 AI 链”；§7.4（`04:361`）由慢循环入口生成 `cycle_id`。
  - `03` §6.2（`03:416`）仍列“L5 决策周期 600s”；§8.1（`03:705`）仍把 `POST /api/cycle/run` 描述为“手动触发一轮决策”。
  - `02` §8.1（`02:2803`）时序图的参与者是“调度器/市场(04)”；§8.4（`02:2964`）写“10 分钟定时：04 慢循环相位”。
- **影响**：两套调度器会各自创建轮次/证据；`slot_id` 唯一索引、`409 CYCLE_RUNNING`、`E_CYCLE_DUPLICATE_SLOT`、手动 <60s 复用快照的语义会互相打架；最坏情况同一 10 分钟出现 2 轮、双倍 LLM 成本、证据与 `cycle_id` 错配。
- **必须修正**：
  1. 在整合稿中写一张“调度与创建”表：**Host = 唯一调度器**；服务只提供 `POST /api/cycles`（原子完成门禁→证据→账户快照→`cycle_runs`）；行情慢循环只做刷新/预取；撤掉服务端决策循环。
  2. 更新 `02` §8.1/§8.4、`03` §6.2/§8.1、`04` §7.1/§7.2/§7.4；`/api/cycle/run` 只保留为 `POST /api/cycles` 的别名（A4），且不再“触发 AI”。
  3. 明确 `cycle_id`、`slot_id`、`requested_at` 的生成/传递责任（见 H-02）。
- **验收**：整合稿中只有 Host 定时器；服务文档不再出现“交 AI 链”“手动触发一轮决策”；时序图只有一条 `Host → POST /api/cycles → 服务` 的创建路径；增加“双触发只产生一轮”的测试。
- **v1 处置**：**必须修**。

#### B-02 · Demo-only 边界未决：01 允许主网行情、04 只用 demo、03 的静态扫描必失败

- **问题**：
  - `01` §11.1（`01:962-963`）把 `PublicMarket` 白名单写成 **仅** `fapi.binance.com`（主网）；§5.1 组件图（`01:281`）也画主网公共只读。
  - `04` §4.2（`04:146-148`）把行情 REST 改成 `demo-fapi.binance.com`，WS 保留 `wss://fstream.binance.com`，并声称“仓内不出现主网行情常量”。
  - `03` §3.5（`03:187`）要求全仓“排除 demo 前缀后 `fapi.binance.com` 命中 0”，且 T12（`03:1174`）按整仓扫描；但 `03` 自己 T10（`03:196`）又要构造 `base_url="https://fapi.binance.com"` 做负例——**T10 与 T12 不可能同时满足**；五份文档本身也含多处 `fapi.binance.com` 示例，扫描 `trading-workbench/` 会误报。
  - `01` A8（`01:1068`）和 `04` Q1（`04:1519`）把“是否允许只读主网行情”留成用户问题。
- **影响**：实现者无法同时满足“静态扫描 0 命中”和“Demo 行情/主网 WS”；要么偷偷加主网常量使 Demo-only 证明失效，要么行情不可用；安全边界也无法在评审中定论。
- **必须修正**：
  1. 把 **demo-only 限定为“签名交易/账户流量”**：`DemoBroker` 只允许 `demo-fapi.binance.com`，任何写请求/密钥不得离开该 host。
  2. **公共只读行情**单独定义 `MARKET_ALLOWED_HOSTS`：默认 `demo-fapi.binance.com` + `fstream.binance.com`；若用户批准 Q1，再加入 `fapi.binance.com`（仅 GET/WS、无 key、无签名）。
  3. 把静态扫描从“整仓”改成“生产交易代码”（如 `service/workbench_service/execution/**`），排除 `docs/`、测试负例与第三方代码；负例用字符串拼接或专用 `tests/fixtures/live_url.txt` 允许列表。
  4. `01` §11.1/§11.2、`03` §3.4/§3.5/§11.3、`04` §4.2 统一到同一张边界表；`04` 的 M1 探针失败时按 §6.3 的降级矩阵处理。
- **验收**：生产交易代码静态扫描 0 命中；`T10` 负例仍可运行；市场 transport 断言无 `X-MBX-APIKEY`/无签名参数；M1 探针记录 demo 行情是否可用。
- **v1 处置**：**必须修 + 需用户决定 U-01**。

#### B-03 · 紧急 kill switch 先撤保护单、后平仓：存在裸仓窗口

- **问题**：`03` §5.5（`03:340`）的“全局撤单（emergency）”写的是“撤该账户全部普通单 + Algo 单 → 平全部仓位”；§7.5（`03:660`）和 §9.3（`03:907`）也把“全平 + 撤单/撤保护”并列，未规定顺序。先撤 SL/TP 再平仓，如果市价平仓失败/延迟/部分成交，就会留下无保护的裸仓。
- **影响**：这是与 `03` 自己 I3（开仓必须带保护、保护失败即平仓）、I6（先挂新后撤旧）直接冲突的安全缺陷；在极端行情下会把“保护性操作”变成“放大风险”。
- **必须修正**：
  1. emergency 顺序固定为：**先以 `reduceOnly`/`closePosition` 平仓（可分批重试）→ 查询 `positionRisk` 确认 flat → 再撤残余普通单/保护单 → 写 `risk_events`**。
  2. 平仓失败时保留现有保护单，不得先撤；返回 `E_PROTECTION_FAILED`/`E_EMERGENCY_CLOSE_FAILED` 并要求人工。
  3. `03` §5.5/§7.5/§9.3、`05` 的“紧急停止”文案、T43 验收用例统一；测试断言调用顺序（平仓 API 先于 cancel API）。
- **验收**：T43 增加“mock 平仓失败时不得撤保护”的断言；emergency 状态机图把平仓放在撤单前。
- **v1 处置**：**必须修**。

#### B-04 · 轮次/agent/AI 审计没有唯一落库 owner，且 `cycle_agents` 主键与“多次尝试”矛盾

- **问题**：
  - `01` §9.2（`01:825-848`）只列了 `cycle_runs/cycle_agents/cycle_events` 等表，没有 `02` §12.1（`02:3462-3469`）的 `ai_runs/ai_calls/ai_outputs/ai_run_events/ai_breaker/ai_budget`。
  - `02` I11（`02:80`）要求“每次 LLM 尝试、每次状态迁移、每次风控合并、每次下单都落审计”；`02` §12.1 的 `ai_calls` 是 per-attempt（含 failed/repair），但 `01` 的 `PUT artifacts`（`01:606`）只按 `cycle_id + agent` 覆盖最终结果，`cycle_agents` 的主键是 `(cycle_id, agent)`（`01:832`），无法存 `attempt=2` 的历史；`01` API 文字又说“带 attempt 则追加历史”，与主键矛盾。
  - `02` §12.1 的 `risk_verdicts`（`02:3466`）与 `01` §9.2 的 `risk_verdicts`（`01:845`）**同名但列完全不同**（一个偏 AI 合并结论，一个偏 P1 审计/token）。
  - `01` 明确 Host 无状态（`01:87`），所有持久化在服务库；但 `02` 的审计表没有对应服务端 API。
- **影响**：无法满足“每轮可审计回看”和 I11；重试/修复历史丢失；重启恢复没有 `ai_runs` 状态；两个 `risk_verdicts` 会让实现者建错表或覆盖数据。
- **必须修正**：
  1. 指定 **服务 DB 为唯一 owner**：建 `ai_runs/ai_calls/ai_outputs/ai_run_events/ai_breaker/ai_budget`（或把 `cycle_agents` 主键改为 `(cycle_id, agent, attempt)` 并补 `ai_run_id`），并在 `01` §8.2 增加写入端点/字段（例如 `PUT artifacts` 接受 `attempts[]`，或 `POST /api/cycles/{id}/calls`）。
  2. 解决 `risk_verdicts` 撞名：要么合并成一张（带 `kind`），要么改名（如 `risk_ai_merges`），并在 `01/02/03` 只保留一个定义。
  3. 明确 `cycle_events`、`ai_run_events`、`order_events` 的边界；不要三套事件表各写一遍。
- **验收**：给出“表 owner 矩阵”；`cycle_agents` 能存 >=2 次尝试；`ai_calls` 每次尝试一行；重启后能按 `ai_runs` 恢复/收口；schema 中不存在两个 `risk_verdicts` 定义。
- **v1 处置**：**必须修**。

#### B-05 · `02` 的 LLM 调用契约与 `01` 的“零依赖、无 Session”直接矛盾

- **问题**：

> 本节不是否定设计质量，而是把“完整设计”与“M1 必须实现”分开。五份文档合计约 500KB、30+ 张表、26 条风控规则、28 条降级路径、95 张 UI 表——对“第一版 Demo 验证决策链”而言，M1 应更窄。

### 10.1 建议的 M1/M2/M3

| 里程碑 | 必须做 | 可以后置 |
|---|---|---|
| **M1 最小闭环** | 6 个链路 agent（分析/红/蓝/决策/风控/操盘手）；1 轮互不可见；P1/P2；市价开仓 + SL/TP；Outbox/UNKNOWN；核心 R01–R19/R22–R25（R20/R21 可先代码保留）；总览 + 决策链骨架；手动一轮；服务 health/ready；日志脱敏；Demo 探针 | 每日复盘；5 视图完整；20 币 index/衍生品；证据抽屉 5 页签；`score_override`；`hard_only_half`；`exposure_guard`；外部模式/升级/备份 UI；`R20/R21` 可先保留代码但不开 |
| **M2 完整 UI/自动** | 5 视图；10 分钟自动；SSE/轮询；复盘；订单/成交/资金；控制态/危险区；i18n/主题 | 多窗口对比；跨视图迷你状态条；toast 去重；回放/重算 |
| **M3 优化** | 权益归因；成本/延迟看板；规则调档；多仓 v2 评估；tool loop v2 | 策略/通道/漏斗（基线已移除） |

### 10.2 过度设计/范围蔓延的具体点

| 来源 | 过度设计 | 建议 |
|---|---|---|
| 02 | `score_override`、`hard_only_half`、14 项 preflight、8 张审计表、完整 tool loop 扩展 | `score_override`/`hard_only_half` v1 关闭；preflight 可先用 7 项核心；审计表保留必需的 4 张；tool loop 只留接口 |
| 03 | 26 条规则 + 20 条失败矩阵 + 31 条测试 + 11 表 | M1 先实现 R00–R19/R22–R25（其中 R18/R19/R24 必须有）；R20/R21 可后置；测试按 M1 gate 裁剪 |
| 04 | 20 币 index + 衍生品 + 30 天证据 + 回放/重算 + P4 | M1 可先 8 deep + 3 周期；index/衍生品在 M2；回放/重算 M3 |
| 01 | 20 表 + external 模式 + 升级/回滚/备份 + 日志文件 | M1 managed only；备份做每日轻量；升级/回滚 M2 |
| 05 | 5 视图 + 95 表 + 5 页签抽屉 + 对比/多窗口 | M1 2 视图（总览/链）；M2 全量；对比/多窗口不做 |

### 10.3 不建议削减的安全项

- P1/P2 双闸、`approval_token`、Outbox/UNKNOWN 只查不重发、保护失败即平仓、权益不可用禁开仓、过期数据禁开仓、kill switch/latch、日志脱敏、demo-only 静态扫描。
- 这些是“少做会带来真实风险”的项，不属于过度设计。

## 11. 成本、延迟、容量复核

### 11.1 LLM 成本/限流

| 项 | 02 的数 | 评审意见 |
|---|---|---|
| FULL p50 | 35k input / 7.4k output | 按 6 次 system + 10.8k 证据 + 上游输出细算合理；需用真实 tokenizer 校准 |
| 硬上限 | 45k / 12k | 合理；但 `max` 档 reasoning token 可能被计入 output，需实测 |
| 每日 | 7M / 1.8M；144 轮 | 5.0M/1.07M p50；最坏 144×12k=1.73M output，接近限值 |
| 成本 | 示例 ¥11.7–26.8/日（¥2/M in、¥8/M out） | **不是报价**；Harness 模型单价未知；必须让用户配置并显示 |
| 调用数 | 6/轮，≤12/轮 | 864 次/日；provider RPM/TPM 未评估；需限流/退避/熔断 |
| 降级 | 80% 降频、100% 只管理 | 合理；但“80% 降为每 20 分钟”会与 Host 10 分钟调度冲突，需在 Host 实现预算检查 |

### 11.2 延迟

| 项 | 值 | 评审意见 |
|---|---|---|
| 数据段 | ≤6s p95 | 04 的进度合理；但 24h ticker 40 权重/10min、衍生品请求可能拖长；需实测 |
| AI p95 | 90–97s | 接近 110s；`max` 档 + 429 重试可能超；建议 100s 硬截止 |
| P1/P2/保护 | 1–10s | 若按 110s 只剩 10s；建议 AI 100s，留 20s（B-03/H-12） |
| 证据门禁 | 120s | 建议“AI 100s + 执行 20s”，余量 20s；若沿用 110s 则门禁 130s |
| 数据权重 | 14–19 weight/min | 本地 600 预算的 2.4–3.2%；健康；但 10s L1 执行快照另占 ~72/min，需合并计算 |

### 11.3 容量

| 项 | 04 估算 | 评审意见 |
|---|---|---|
| bars | 12–14MB | 合理 |
| 证据 | 1MB/天，30 天 30MB | 合理；若 45KB 原始 JSON 含 20 币，gzip 7KB 可能偏乐观，需实测 |
| 主库 | 未估算 | 订单/成交/权益/审计表会增长；需加容量与清理 |
| 日志 | 50MB | 合理 |
| 合计 | <120MB | 可接受；但 01 的主库/备份/证据另算，需统一口径 |

- [ ] **LLM 探针**：最小插件 Host 调用 `ctx.llm.stream`（无 sessionId、无 tools），拿到 `finish` 与 `usage`；记录 `NO_ADAPTER/MISSING_CREDENTIAL/AUTH` 的 UI 表现。

- [ ] **Schema**：02 的 9 个 schema + 10 个示例用 `jsonschema`/`ajv` 校验；`additionalProperties:false`；语义测试。
- [ ] **P1/P2 安全**：token 过期/重放/plan 篡改；P2 无 token 必须拒绝；Outbox UNKNOWN 不重发；保护失败平仓；emergency 顺序。
