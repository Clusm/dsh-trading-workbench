# USD-M 数字货币合约系统运行与故障恢复手册

适用范围：`multi-agent-trader` 本地 Binance USD-M 数字货币 USDT 永续系统。本文不授权切换实盘、不修改风险档、不删除交易所订单。

## 1. 正常状态判据

同时满足以下条件才视为正常：

1. `GET http://127.0.0.1:8000/api/health` 返回 `ok=true`。
2. `GET http://127.0.0.1:8000/api/ready` 返回 `ready=true`；若仅查看或管理存量仓位，ready=false 不代表服务不可用。
3. `broker_mode` 与预期一致，当前默认应为 `demo`。
4. `startup_safety.ready=true`，保护覆盖核验没有未知状态。
5. `runtime.last_fast_cycle_error`、`runtime.last_slow_cycle_error` 和
   `runtime.last_latest_refresh_error` 为空；最后一项非空表示控制台仍在展示上次有效资金/通道快照，应先排查数据刷新。
6. `/api/intel` 中 `execution_weight=0`；情报模块不得拥有下单权。
7. `scripts/verify_profile_lock.py` 输出 `PROFILE LOCK OK`。

## 2. 启动、停止与重启

正式无人值守部署只使用 Windows Service Control Manager（SCM）和同一份
`config/windows_service.json`。该配置只描述本机回环 Web、项目内解释器/入口、停机时限、
重启退避和日志轮转；执行模式仍由 `.env`/`config/settings.yaml` 解析，代理也由统一入口
`run_web.py` 解析，不在服务模板或包装器中写入覆盖值。

安装前在项目根目录只读校验：

```powershell
.venv\Scripts\python.exe scripts\validate_windows_service_plan.py `
  --config config\windows_service.json --require-files --print-install
```

校验通过后，在受控的管理员终端人工执行脚本打印的三条 `sc.exe` 命令；本校验脚本不会
自动安装服务。安装后核对：

```powershell
sc.exe query MultiAgentTrader
Get-NetTCPConnection -LocalPort 8000 -State Listen -ErrorAction SilentlyContinue
```

服务入口为 `scripts/windows_service_host.py`，它复用 `scripts/run_web.py`，收到 SCM stop
后先停止接受新任务，再让 Uvicorn 有界退出，最后调用 `TradingService.close()`。服务配置的
默认停机预算为 30 秒，日志达到 10 MiB 后在 `data/web_console.log.1` 至 `.5` 内轮转。
`scripts/start_web_detached.py`、`scripts/run_web_service.py` 和 `start_web.bat` 仅保留作
诊断/隔离演练入口，不得与正式 SCM 服务并行运行。

手工前台隔离演练（不会注册 SCM）：

```powershell
.venv\Scripts\python.exe scripts\windows_service_host.py --foreground `
  --config config\windows_service.json
```

服务地址为 `http://127.0.0.1:8000`。停止 SCM 服务时使用：

```powershell
sc.exe stop MultiAgentTrader
sc.exe query MultiAgentTrader
```

确认端口已退出后才能再次启动；不要在还有慢决策线程时直接删除锁文件。

重启前检查：

```powershell
Get-NetTCPConnection -LocalPort 8000 -State Listen -ErrorAction SilentlyContinue
.venv\Scripts\python.exe scripts\verify_profile_lock.py
```

如果端口没有监听但 `data/trading_service.lock` 存在，先确认没有 Python 服务进程。只有确认原进程已经退出，才允许按实例锁工具的既定恢复路径处理；不得盲删锁后同时启动第二个交易服务。

服务异常退出时由 SCM 按配置的退避策略重启；重启后必须先查看 `/api/health`、`/api/ready`、
Outbox UNKNOWN 和保护覆盖，再决定是否恢复开仓。SCM 的自动重启只解决进程存活，不代表
交易所网络、账户对账或版本发布门禁已经通过。

## 3. 上线后核验

按顺序检查：

- `/api/health`：账户、私有流、镜像、Outbox、保护单、强平流和数据库状态；`runtime` 中包含最近快/慢循环耗时，`database_writes` 是已纳入追踪的数据库写入次数、错误数与延迟。它们用于发现性能退化，不能单独作为交易或风控信号。
- `/api/ready`：开仓前置条件；失败原因在 `reasons`。
- `/api/status`：500 U 会话起点、当前权益、持仓与控制状态。
- `/api/intel`：情报新鲜度、错误、20 币覆盖、A/B/C 样本进度。
- `/decisions`：人工查看情报与决策链，不以单一影子方向作为交易建议。

决策页按 Guardian、市场与链上情报、策略、AI、统一检查、RiskGuard 和执行结果展示。
`PASS/WARN/BLOCK/NOT_EVALUATED` 是检查结论，`shadow/enforce/off` 表示作用方式；
shadow 的 BLOCK 只记录。Guardian 当前应显示 shadow，未经独立晋级提交不得改为 enforce。

观察窗口：启动后 5 分钟检查一次，30 分钟检查快慢循环和镜像，24 小时检查重连、数据库增长和备份。

服务运行时可用以下只读脚本记录本机端到端 P50/P95、最大值和失败率 `[source 包]`；
它不读取凭据，公共 Binance 网络测量必须显式开启，不能把公网延迟混同于本地应用回归：

```powershell
.venv\Scripts\python.exe scripts\benchmark_demo_endpoints.py --samples 20
.venv\Scripts\python.exe scripts\benchmark_demo_endpoints.py --samples 20 --include-binance-public
```

观察样本可运行 `.venv\Scripts\python.exe scripts\report_demo_acceptance.py` 只读汇总。
`filled_order_rows` 和 `closed_position_rows` 仅用于发现归因链缺口，不能替代
`demo_closed_trades`；只有 `trade_outcomes` 的闭合记录计入30笔验收门槛。

发布门禁必须绑定同一份清单、环境和窗口：

```powershell
.venv\Scripts\python.exe scripts\report_release_readiness.py `
  --db data\agent_trader.sqlite `
  --manifest data\release_manifest.json `
  --environment demo --strict --out data\release_readiness.json
```

严格模式返回码 `0=GO`、`1=门槛未满足`、`2=清单/数据库/输入错误`。当前一次
`ready=true`、HTTP 200 或服务存活都不能替代发布报告中的 7 天观测、200 个去重候选和
30 笔完整归因闭合样本；报告是只读重算结果。

Live 评估建议显式传入 `--db data\live\agent_trader.sqlite` 与
`--manifest data\live\release_manifest.json`。当前工具在省略 `--db` 时会按
`--environment live` 自动选择 Live 账本；显式传入仍是发布核验时更清晰、可审计的写法。

最终提交、清单和严格报告核对无误后创建代码发布包（目标必须不存在）：

```powershell
New-Item -ItemType Directory -Force dist | Out-Null
.venv\Scripts\python.exe scripts\create_release_package.py `
  --manifest data\release_manifest.json --kind runtime `
  --out dist\multi-agent-trader-release.zip
```

发布包是代码部署工件，不是恢复包；已有同名包会失败，需由操作者选择新的目标，
不得覆盖旧工件。

### 3.1 两种包类型与强制自检（U10a）

唯一实现是 `scripts/create_release_package.py`（库入口 `build_release_package` /
`verify_release_package`，两者是同一份判定，不存在第二套口径）。

| 参数 | 实际行为 |
|---|---|
| `--kind runtime`（默认） | **可部署运行工件**：启动与 SCM 托管入口、健康守望、实盘预检、发布门禁报告、迁移与恢复工具、全部有效配置、策略卡、运行所需源码与模板、发布包自检入口 |
| `--kind source` | 在 runtime 之上补齐 `tests/`、`.github/` 与其余脚本（冒烟、门禁、诊断、维护），用于复现完整仓库行为 |
| `--self-check` | 构建到系统临时目录 → 解压 → 自检，**不写 dist/**；发布前最低证据 |
| `--verify <解压目录>` | 只自检一个已解压目录，不构建；只读，可在只读介质上重复运行 |

```powershell
# 发布前最低证据：构建→解压→自检（退出码 0=通过、2=不通过）
.venv\Scripts\python.exe scripts\create_release_package.py --self-check --kind runtime

# 解压后在目标机上复核（不启动服务、不读 .env、不绑定端口）
Expand-Archive dist\multi-agent-trader-release.zip -DestinationPath C:\deploy\mta
.venv\Scripts\python.exe scripts\create_release_package.py --verify C:\deploy\mta
```

自检逐项结论（任一不通过即退出码 2，报告为 JSON）：`package_manifest_present`、
`release_manifest_present`、`release_identity_matches`、`no_unlisted_files`、
`file_hashes_match`、`forbidden_paths_absent`、`credentials_absent`、
`runtime_state_absent`、`dotenv_absent`、`required_assets_present`、`doc_links_resolve`、
`python_syntax_ok`、`windows_service_config_valid`。其中 `doc_links_resolve` 对包内
每篇 markdown 的**相对链接**逐个解析，目标不在包内即失败——文档指向未打包文件
（例如把只存在于源码仓库的流程记录当成现行材料）会在构建/自检阶段暴露，而不是留给
读者点开断链。

包内**必然包含**（缺任一项即构建失败）：`src/` 全部已跟踪文件（含 8 个
`src/dashboard/templates/*.html`、`src/strategy_runtime/PROVENANCE.md`）、
`src/data/` 数据接入层、`config/` 六个配置文件、`knowledge/strategy_cards.json`
（K01 策略身份来源）与其备份、`requirements*.txt` 与 `pyproject.toml`（依赖锁）、
`README.md`、`CONTRIBUTING.md`、`.env.example` 脱敏模板、运维与自检脚本。必需清单与
包内 `src/core/release_manifest.py` 的 `SAFE_CONFIG_FILES` / `DEPENDENCY_FILES` /
`STRATEGY_CARD_FILES` 在构建期交叉核对，两侧不一致即失败（名单漂移会让锁文件或
策略卡改动漏出发布身份）。

包内**必然不含**（构建期按路径规则拒绝，自检期按包内容实际扫描复核）：`.env` 及
任何真实凭据文件、`data/`、日志、SQLite 与其 WAL、私钥/证书、缓存、`.venv`、既有发布
或恢复工件、未跟踪的临时诊断脚本，以及 `docs/dispatch/**` 下的评审证据、待应用补丁、
RESUME、w0 盘点与交接说明。凭据判定复用仓库唯一扫描器
`scripts/scan_tracked_secrets.py`（同一登记表与 KI04 流程记录范围豁免），不新建第二套
豁免。内容扫描只输出"文件:行号 + 规则名 + 行指纹"，不打印匹配值。

> **范围豁免随包时必须如实列出（不得静默跳过）**：机器可读编排台账
> `docs/无人值守升级任务清单_2026-09-19.json` **在包内**——包内多篇文档以相对链接引用
> 它（其中 `docs/contracts/README.md` 属不得改动的冻结契约目录），排除它会直接让
> `doc_links_resolve` 报断链。它命中仓库扫描器的 KI04 范围豁免，因此自检报告的
> `credentials_absent.detail.repo_exempt_files` 会**显式列出**它是未参与内容扫描的成员；
> 离线冒烟对该"如实列出"有断言。要把该台账移出发布包，必须**同批**改掉 4 篇引用文档的
> 链接（跨任务动作，见 `docs/文档索引.md` 的"执行编排"一节）。

仓库每个已跟踪文件都必须被显式归类（入包 / 排除并写明理由），未归类文件即构建失败；
`package_manifest.json` 的 `inventory` 与 `excluded_files` 给出"仓库应有文件"与
"包内清单"的完整对照，供人工复核而非"已忽略"一句话带过。

> **集成状态（必须如实标注）**：本节的打包、自检、清单交叉核对与 §3.2 第 1、2、4、5 步
> 都已在本仓实现（`scripts/create_release_package.py`，无需共享改动）。§3.2 第 3 步的
> **"发布包解释器 fail-closed"** 依赖两项共享适配补丁，它们属于 `src/core/windows_service.py`
> 与 `scripts/run_web.py`，**在集成前不在本分支内**：
> `docs/dispatch/patches/U10a/` 下的 `02_core_windows_service_package_interpreter.diff`
> （解释器必须位于包内）与 `01_run_web_verify_package.diff`（`run_web.py --verify-package`）。
> 未合入前：`--verify-package` 不存在（脚本报 `unrecognized arguments`），且
> `validate_windows_service_plan.py --require-files` 在包内缺解释器时仍会**回退**到进程
> 解释器。合入后行为即如上文；两侧都有离线冒烟
> （scripts/smoke_u10a_release_package.py 第 [5] 节按运行时行为探测，补丁在/不在都断言）。

**本手册命令的包适用性**：标 `[source 包]` 的离线验证命令只存在于 `source` 包或源码
检出（它们是开发/验收期工具）；`runtime` 包内含 `scripts/run_web.py`、
`windows_service_host.py`、`validate_windows_service_plan.py`、`health_watch.py`、
`preflight_live_account.py`、`report_release_readiness.py`、`report_demo_acceptance.py`、
`create_recovery_bundle.py`、`restore_recovery_bundle.py`、`ops/verify_recovery_plan.py`、
`ops/verify_runtime_paths.py`、`verify_profile_lock.py`、`verify_dependency_lock.py`、
`smoke_db_migrations.py`（迁移校验）、`create_release_package.py`（自检）、
`scan_tracked_secrets.py`（自检用的凭据扫描器）与 `start_web.bat`（诊断启动批处理）。
在只有 runtime 包的机器上执行 `[source 包]` 命令会立即报"文件不存在"，不会假装通过。
该清单与 `scripts/create_release_package.py` 的 `RUNTIME_SCRIPTS` 由离线冒烟
（scripts/smoke_u10a_release_package.py）逐项比对，文档漂移会直接让回归变红。
同一冒烟还会扫描本手册的**每个命令块**：引用 source-only 脚本的命令块必须带
`[source 包]` 标记，否则回归变红（防止"照着手册做但 runtime 包内没有"）。
> 已知边界：该比对按 **basename** 进行，且只识别反引号/裸 `scripts\...` 形式；
> 若将来把两个不同目录的同名脚本分别列为 runtime/source，它分辨不出（当前无此情形）。

### 3.2 从解压目录启动

1. `--verify` 通过（见 §3.1）；发布包内**没有** `.venv`，需在包目录内按
   `requirements-lock.txt` 建立虚拟环境。
2. 依 `.env.example` 创建 `.env`（包内不含真实凭据）；`.env.example` 只是字段模板，
   它不含任何密钥值。
3. 复核 SCM 计划：`.venv\Scripts\python.exe scripts\validate_windows_service_plan.py
   --config config\windows_service.json --require-files --print-install`。
   包目录含 `package_manifest.json` 时，解释器**必须**位于包内
   （`core.windows_service.is_release_package_root` 与 `resolve_python_executable`
   的 `require_in_root`）；包内没有可用解释器时该命令 fail-closed 并给出原因，
   不会静默把 `binPath` 指向构建机或其他检出的解释器。确需外置解释器时用
   `MTA_PYTHON` 显式声明，或在调用时显式传 `require_package_interpreter=False`。
4. 停写状态下按 §5 准备状态与恢复包。**发布包不包含任何运行状态**：用它换代码目录
   不会带来账本、资金基线或控制状态；若期间有交易所已成交订单，必须先按 §5 全量对账，
   再解除开仓阻断（F14）。
5. 启动横幅的 `state:` 一行会打印状态根、profile 与实例锁名；包内 `package_manifest.json`
   的 `release_id` 应与 `data/release_manifest.json` 一致，不一致说明代码与清单不是同一次
   发布，应停下复核（F13：改依赖锁/模型覆盖/profile/策略卡/参数必然改变发布身份）。

## 4. 常见故障处置

### 风险事件与 incident 生命周期

`risk_events` 保留每一次原始审计；`/api/incidents` 将同类待处置事件按类型和作用域聚合，显示出现次数与 `OPEN / ACKNOWLEDGED / RESOLVED` 状态。健康接口和导航红点只统计未解决的 critical incident，避免同一错误重复出现时持续放大告警。

确认已知问题使用 `POST /api/incidents/{incident_key}/acknowledge`；问题真正恢复并完成核验后使用 `POST /api/incidents/{incident_key}/resolve`。两个写接口都需要控制台 CSRF token。RESOLVED 后若同类问题再次出现，会自动重新打开 incident。

### 情报状态 degraded

查看 `/api/intel.errors`。单个 OI、盘口或比率请求失败只降低该标的质量，不影响 Broker、保护单或风险闸门。公开 GET 已做有限重试；等待下一轮自动恢复。连续三轮仍失败时检查网络出口和币安限流，不要提高情报权重。

### 钱包跟踪或 Token Audit 为 unconfigured

这是明确的未知状态，不是中性信号。钱包跟踪需要只读地址、角色和 Etherscan key；Token Audit 需要显式的链 ID、合约地址到 20 币白名单的映射。不得按代币简称猜测合约地址。

2026-09-23 影子接入试点：`config/settings.yaml` 只映射 Uniswap 官方以太坊主网 UNI 合约至 `UNIUSDT`，由 GoPlus Token Security API 提供代币审计；不涉及交易所合约本身，也不改变下单决策或风险档。接口不可达、响应无该合约或质量未知时保持 `unknown`，不得解释为“安全”。官方合约依据：<https://developers.uniswap.org/docs/ecosystem/governance/technical-reference>；审计接口：<https://docs.gopluslabs.io/reference/tokensecurityusingget_1>。

钱包跟踪使用 Etherscan V2 `account/tokentx`。先由负责人提供经核实的公开 EVM 地址、链 ID、地址角色，再填入 `web3_intel.watched_wallets`；把只读 Etherscan key 放入运行环境变量 `ETHERSCAN_API_KEY`，不要写入 YAML、日志或 Git。普通转账、交易所充值和钱包归集不能直接判为买卖意图，影子输出也不能自动晋升执行权重。接口说明：<https://docs.etherscan.io/api-reference/endpoint/tokentx>。配置改动需重启 Demo 进程才会载入；重启前 `/api/intel` 仍显示旧快照。

### ready=false

按 `/api/ready.reasons` 处理。保护覆盖未知、账户不可用、Outbox UNKNOWN、控制状态非 normal，或快循环/保护对账超过配置时效时，不得通过放宽风险参数绕过。存量减仓、平仓和保护同步仍应保持可用。LLM 慢循环耗时不会把独立快循环误判为停止。

### pipeline_open_blocked 或 pipeline_bypass_blocked

前者表示候选缺证据、缺检查或命中已启用的强制规则；后者表示 Broker 收到未经统一
管线运行时签名的开仓。先在 `/decisions` 查看具体阶段和原因码，再核对调用入口。
不得通过手工填写授权字段绕过；退出、减仓和保护同步仍应可用。

### Guardian REVIEW_DUE / INVALIDATED

`REVIEW_DUE` 表示缺原始开仓论点、闭合 K 线或数据质量证据，需要人工核对交易所保护单
和审计记录。`INVALIDATED` 表示闭合 K 线满足结构证伪条件；当前 shadow 配置只记录。
若未来完成独立调度、跨周期幂等、UNKNOWN 收敛和 Demo 观察，必须用单独提交晋级。

### 权益突然归零或跳变

先停止服务，保存 `capital_state.json`、`channel_state.json`、数据库和日志副本；核对交易所钱包、当前持仓和最近成交。不要运行会创建真实 `TradingService` 的测试脚本。资金重锚必须在无未确认交易且口径明确后执行，并在重启后再次确认 500 U 起点与当前权益。

### 服务无报错但端口消失

检查进程是否被父会话或 Windows Job Object 回收，再查 `data/web_console.log`。这类情况不等同于应用崩溃。重新启动前先确认旧进程和端口均不存在，避免双实例。

### 策略扫描连续报公开行情冷却

先查看事件中的原始 HTTP 状态。429 表示请求额度不足，客户端会尊重 `Retry-After` 并
立即停止本次重试；418 表示出口 IP 已被临时限制，进入更长的全局冷却。冷却期间策略
扫描和 AI 行情工具 fail-closed 属于预期行为，不应通过放宽数据新鲜度或绕开冷却恢复
开仓。确认代理是否被多个程序共享、全量 ticker 是否只产生一次请求，并等待下一轮正常
扫描自动解决 `market_universe_full_scan_fail` 与 `signal_scan_error` incident。冷却状态会
原子写入 `data/public_rate_limit_state.json` 并跨重启恢复，不要通过删除该文件绕过封禁。

## 5. 数据库备份与恢复

系统使用 SQLite 在线备份，默认目录为 `data/backups`，保留 14 天。在线备份用于数据库日常容灾；发布、迁移或完整恢复演练必须在服务停写后创建包含关键 JSON 的恢复包。备份回归 `[source 包]`；runtime 包内含的是 `scripts/smoke_db_migrations.py`（迁移版本与向前兼容）与
`scripts/ops/verify_recovery_plan.py`（恢复计划核验）：

```powershell
.venv\Scripts\python.exe scripts\smoke_db_backup.py
.venv\Scripts\python.exe scripts\smoke_recovery_bundle.py
```

创建完整恢复包：

```powershell
# 先正常停止服务；工具会竞争服务使用的同一单实例锁，并安全接管已死亡 PID 的陈旧锁
.venv\Scripts\python.exe scripts\create_recovery_bundle.py
```

恢复包包含经 `quick_check` 验证的 SQLite、capital/channel/control/account-risk 状态、可用的来源台账和市场池状态、风险档锁及 SHA-256 manifest；明确排除 `.env` 和任何密钥。脚本在整个创建窗口持有服务单实例锁：活动实例会被拒绝，确认死亡的陈旧 PID 锁会被安全接管，服务也不能在检查后竞态启动。恢复包默认仍位于本机 `data/recovery_bundles`，应由操作者复制到加密的独立磁盘或受控对象存储；仓库不会上传它。

复制到独立磁盘后，先 dry-run，再恢复到与备份介质不同卷的一个**不存在的新目录**。
例如恢复包在 D 盘，演练目标应在 C 盘；D→D 不满足 `independent_volume`：

```powershell
.venv\Scripts\python.exe scripts\restore_recovery_bundle.py D:\backup\recovery_xxx `
  --target-dir C:\restore-drill\mta --expected-environment demo --require-independent-volume

.venv\Scripts\python.exe scripts\restore_recovery_bundle.py D:\backup\recovery_xxx `
  --target-dir C:\restore-drill\mta --expected-environment demo `
  --require-independent-volume --execute
```

工具会校验 manifest 自身哈希、成员白名单和哈希、SQLite、迁移版本、JSON 与执行环境，
并生成 `restore_receipt.json` 和耗时。它绝不覆盖既有目录，也不会自动替换当前运行项目；
同盘临时目录测试只算程序回归，只有 `independent_volume=true` 才算异盘演练证据。

恢复流程：

1. 停止服务并确认 8000 端口退出。
2. 保留当前 `agent_trader.sqlite`、`-wal`、`-shm` 文件副本。
3. 优先选择最近一个完整恢复包，逐项核对 `manifest.json` 的哈希、Git commit、环境和资金锚点；只有数据库在线备份时按受限恢复处理。
4. 使用上述工具恢复到全新临时路径，并确认 `independent_volume=true`、`quick_check=ok`；正式切换前可另行运行 `PRAGMA integrity_check`。
5. 将同一恢复包中的数据库和关键 JSON 恢复到配置路径，不得混用不同包的状态。
6. 启动前保留 UNKNOWN，不得按年龄删除；启动后检查迁移版本、账户/订单镜像、保护覆盖和 500 U 资金口径。
7. 与交易所当前持仓、成交和 Algo 订单逐项对账后，才能把控制状态恢复为 normal。

不得在服务运行时用普通文件复制替换 SQLite 主库，也不得只复制主文件而忽略尚未检查点的 WAL 状态。

## 6. 版本回退

代码回退只关闭或恢复应用功能，不回滚交易所真实状态：

1. 记录当前 Git commit、风险档哈希、执行模式、权益、持仓、挂单和 Outbox 状态。
2. 有 UNKNOWN 订单或保护覆盖异常时禁止发布/回退。
3. 停止服务，切换到已验证提交，再运行迁移和冒烟测试。
4. 启动后按第 3 节完整核验。

禁止使用 `git reset --hard` 清除用户工作区；禁止通过删除数据库事件、撤销未知订单或覆盖资金基线来制造“回退成功”的假象。

## 7. 情报影子晋级规则

A/B/C 均为零执行权重。任何组只有同时满足以下条件才可进入人工评审：

- 至少 200 个有效方向样本；
- 至少连续观察 7 天；
- 扣除手续费、滑点和资金费后的平均净收益为正；
- MFE/MAE、最差净收益和稳定性没有恶化；
- 风险档哈希与交易白名单保持不变。

系统没有自动晋级路径。即使 `promotion_ready=true`，也只表示可以人工评审，不表示可以自动接入真实决策。

### 9.3 必须共享的状态及原因

**唯一有意共享的是限流状态**（同一出口 IP，两进程必须互相看见冷却与额度）：

- **路径（实际位置）**：`data/public_rate_limit_state.json` 及其锁
  `data/public_rate_limit_state.json.lock`。
  > ⚠️ 设计稿 §2.2/§4.4 写的是 `data/shared/public_rate_limit_state.json`，
  > 实际实现 `Settings.rate_limit_state`（`config_loader.py:61`）返回
  > `data/public_rate_limit_state.json`（位于 `data/` 根），磁盘上文件也在 `data/` 根。
  > `data/shared/` 现在只放 `data/shared/llm_coordination/`（见下）。**以实际路径为准。**
- **`data/shared/llm_coordination/`**：两进程共用同一 SENSENOVA 凭据的 LLM 并发协调
  （`llm.coordinator.max_concurrency: 1` 的跨进程约束）。机制细节以代码为准。

**为什么限流必须共享**（已读 `src/data/rate_limit.py`，三额度作用域不一致）：

| 额度 | 实现位置 | 作用域 | 共享后行为 |
|---|---|---|---|
| 418/429 冷却 | `reserve_request()` 在 `_state_file_lock` 临界区内读 `cooldown_until`、且 `note_418`/`note_rate_limit` 持久化到共享文件 | **跨进程**（读/写共享文件） | 一个进程登记冷却，另一进程立即拒绝发送 |
| `futures/data` 5 分钟窗口 | `reserve_request()` 统计共享 `request_events` 中 `group=="futures_data_5m"` 计数，`_DATA_REQUEST_BUDGET_5M=800` | **跨进程**（共享计数器） | 两进程共用同一个 800 池 |
| 分钟权重 | `reserve_request()` 在文件锁内对共享 `request_events` 统计最近 60s 的 `weight` 之和，与 `_LOCAL_WEIGHT_BUDGET_1M` 比较 | **跨进程（共享计数）** | 两进程**合计**被同一个 600 封顶 |

**关键更正**：设计稿 §3 曾建议「每进程预算 600→300」，但落地实现（`rate_limit.py` 的
分钟权重判定已改为基于共享文件窗口累计）使两进程**合计**共享同一个 600，
`settings.yaml` 的 `binance_market_data.local_weight_budget_1m` 仍为 `600`，
`service.py:90` 对两个 profile 都读这个值。因此**不要把 live 预算改成 300**——
改 300 会在只跑一个进程时浪费一半额度，且与当前实现不符。

**反例**：若给两个 profile 各配独立限流文件，demo 触发 418 后 live 毫不知情，
会继续以 600/分钟打同一被封 IP——这正是历史 418 事故形态。

### 9.4 停止单实例与停止全部的顺序

- **停单实例**：先通过端口定位对应 PID，再停；不得按进程名批量结束所有 Python。
  - demo（detached）：通过 8000 端口定位 PID；
  - live（detached）：通过 8001 端口定位 PID（日志见 `data/live/web_console.log`）；
  - 未来若启用 SCM：再使用 `sc.exe stop <服务名>` 和 `sc.exe query <服务名>`；
  - 停止后用
    `Get-NetTCPConnection -LocalPort 8001 -State Listen` 确认端口释放。
- **停全部（推荐顺序：先 live 后 demo）**：先冻结真实资金暴露（live:8001），再停模拟
  （demo:8000）。每个都按 §2 的统一停止链路走，停止后分别探活端口确认已退出。
- **禁止**：在还有慢决策线程/子进程时直接删除 `trading_service.lock`；
  盲删锁后同时启动第二个同 profile 实例。

恢复/重启前检查（每个 profile 各做一遍）：

### 9.6 常见误操作

1. **在控制台里用下拉框切到实盘**：profile 下 `mode-select` 已禁用，`POST /api/mode`
   返回 409。正确做法是**启动第二个控制台**（`--profile live`），不是解锁下拉框。
2. **手工 `python scripts/run_web.py` 直连启动**：不走 `start_web_detached.py` 的代理注入，
   `.env` 的 `MTA_NO_PROXY=1` 会强制直连 → 币安 ConnectTimeout。源码检出/source 包内
   live 一律用 `start_web_detached.py --profile live` `[source 包]`
   （自动 `MTA_NO_PROXY=0` + 注入 `HTTP(S)_PROXY`）；**runtime 包内没有该脚本**，
   需先自行配好代理，再用 `scripts/run_web.py --profile live` 启动（见 §9.1）。
3. **把 live 的 `local_weight_budget_1m` 设成 300**：错误。两进程共享同一 600 上限，
   改 300 反而浪费额度，且与当前实现不符（见 §9.3）。
4. **给两 profile 配独立限流文件**：会让 418 冷却互不感知，重演历史 418 事故。
5. **删除 `data/public_rate_limit_state.json` 绕过 418 冷却**：冷却状态跨重启恢复，
   删文件会破坏跨进程互斥，属高危误操作。
6. **以为改 `EXECUTION_MODE=live` 就能切实盘账本**：profile 优先于 `EXECUTION_MODE`
   （`factory.py:40`）。若只改 `EXECUTION_MODE` 而不加 `--profile live`，会出现
   「broker=live 却写 demo 账本」的危险错配。启动实盘**必须** `--profile live`。
7. **盲删锁文件后同时拉起两个同 profile 实例**：触发「交易服务已在运行」或账本竞争。

### 9.7 与设计的差异（实际代码为准）

- 没有新建 `src/core/profile.py`；等价能力由 `Settings.runtime_path()` /
  `Settings.rate_limit_state` / `Settings.console_port` 承载（`config_loader.py`）。
- 分钟权重预算未按「各 300」实施，而是改为共享文件窗口累计、两进程合计封顶 600。
- 共享限流文件实际在 `data/public_rate_limit_state.json`（非 `data/shared/`）。
- live 的 SCM 配置 `config/windows_service.live.json` 尚未创建，live 暂只能走 detached 启动
  （源码检出/source 包；runtime 包内用 `scripts/run_web.py --profile live` 前台启动）。

## 10. 独立只读健康守望

健康守望不构造 `TradingService`、不持有交易密钥、不发订单，也不修改控制状态。它只读取
实例锁和审计库的最新提交；SQLite 使用 `mode=ro` + `query_only`，以便正确读取运行中 WAL，
不能改成会忽略 WAL 的 `immutable=1`。

```powershell
# 单次检查
.venv\Scripts\python.exe scripts\health_watch.py --profile demo --once
.venv\Scripts\python.exe scripts\health_watch.py --profile live --once

# 临时连续观察；正式无人值守仍需未来的 SCM/任务计划与已批准告警通道
.venv\Scripts\python.exe scripts\health_watch.py --profile live `
  --interval-seconds 30 --count 20
```

退出码：`0` 表示健康且外部告警通道已验证，`1` 表示发现健康异常，`2` 表示系统健康但
外部告警通道尚未验证。当前项目未配置已批准的外部告警通道，因此健康实例返回 `2` 是
预期状态，不能误判为交易服务故障，也不能声称已具备无人值守告警。

离线验证 `[source 包]`（`smoke_db_migrations.py` 与 `ops/verify_runtime_paths.py` 在 runtime 包内）：

```powershell

.venv\Scripts\python.exe scripts\smoke_release_observation_freshness.py
.venv\Scripts\python.exe scripts\smoke_fault_matrix.py
```
